# ChatBI · 制造业经营分析（作品二）

> 载体定位：接进 `Local-AI` APP 的**智能问数模块**。
> 路线：**独立 Python 本地服务 + HTTP 接口**（不写进 Rust），全离线、本地模型。

## 与作品一的关系

| | 作品一 · RAG-Embedding | 作品二 · ChatBI（本目录） |
|---|---|---|
| 回答什么 | 「制度怎么规定的」 | 「数字是多少」+「帮我生成单据」 |
| 数据 | 19 份制度文档（291 块） | `制造业Demo.db` 6 表 1537 行 |
| 检索/计算 | BM25 + 重排 + 拒答 | **语义层模板 SQL** + 只读护栏 |
| 服务端口 | 8092（+ 8000 生成 / 8085 重排） | **8095**（问数）· **8096**（编排入口） |
| APP 里的入口 | 「知识库问答」模式 | 「智能问数」模式（**一个模式三条链路**，包 7） |
| 典型失败模式 | 检索不到、编造引用 | **SQL 合法但口径错**（数字看着对）／ 单据数字与依据不一致 |
| 边界控制 | 拒答（三层互补：检索不到 / 库外主题 / 答不上） | **权限白名单**（角色不许就不做，HTTP 403 硬拒）—— 都坚持「拒绝要给出路」 |
| 留痕 | 拒答原因落应答 | **审计 JSONL**：每次动作调用留痕（角色 / 动作 / 参数摘要 / 依据切题 / 落盘 / 被拒理由） |

两个作品的语料与评测集**物理隔离**，避免分母互相污染。

> **包 5 起，作品二的编排层会调用作品一** —— 8096 是用户唯一的入口，知识问答由它转发给 8092
> （HTTP，不 import）。语料仍物理隔离，只是服务之间有了调用关系。

## 一个入口，三条链路（包 5 起）

```
用户问题 ──► 意图路由（确定性优先 + 模型兜底）
              │
   ┌──────────┼───────────────┬──────────────────┬───────────────┐
   ▼          ▼               ▼                  ▼               ▼
 知识问答   数据问数        动作执行          模型兜底        （默认）
 RAG 8092  ChatBI 8095     动作.py           三选一          数据问数
 「制度怎么  「数字是多少」   「帮我出一份…」
   规定的」
```

| 链路 | 回答什么 | 依据 | 端口 | 典型失败模式 |
|---|---|---|---|---|
| 知识问答 | 制度 / 流程 / 规定怎么写的 | 19 份制度文档（检索 + 重排 + 拒答） | 8092 | 检索不到、编造引用 |
| 数据问数 | 某个数字是多少 | 供应链与生产数据库（语义层模板 SQL） | 8095 | **SQL 合法但口径错**（数字看着对） |
| 动作执行 | 帮我生成一份单据 | 查询结果 → 业务单据草稿 | 本地 | **单据里的数字与依据不一致**（最严重：单子要发出去） |

**三条链路的失败模式完全不同 —— 这正是要把路由做对的原因。** 送错链路不只是「答得差」：
把「制度怎么规定的」送进 SQL 链路，会拿真实表硬答一个不存在的口径，而用户无从对照。

**路由为什么「确定性优先」**（不是偷懒，是判据问题）：模型分类的答案**不可复现** ——
包 4 实测同一提示词开 / 关生成端前缀缓存会翻到另一个分支。路由一旦不可复现，
「为什么走了这条链路」就没人能回答。所以：**能被证伪的规则放前面，模型只在规则判不出时兜底，
且兜底要留下痕迹**（应答里带 `路由.依据 = 确定性 | 确定性-动作嫌疑 | 模型`，五态分明 —— 含「默认」与「强制」）。

**ReAct 只用在动作链路**（刻意的收窄）：知识问答 / 数据问数的输入**就是问题本身**，
不需要补参数 → 单步委派，快且稳。动作链路需要「依据」（单据里的数字必须来自查询）
→ 这才需要多步：先查数据（Observation）→ 再生成单据（Action）。**多步是需求，不是炫技。**

## 链路 · 问数链路内部（包 2 骨架 + 包 8 的环节位置）

```
自然语言 ──► 前置判定（拒答 / 元问题 · 确定性关键词，**不调模型**）
              │  库外主题 → 拒答（说明没有 + 本库能答什么）
              │  问数据本身 → 元问题（直接答元信息）
              ▼
        B-4 身份解析（令牌优先；无效**不退回**裸角色）
              │  解析不出角色 → 401（/ask 与 /spec）；/feedback 不需要身份
              ▼
        A-1 会话取上文 ──► 意图解析（模型，唯一参与的一步）
              │              ▲ B-2 语义缓存（问句+上文 → 意图；**提示指纹变即作废**）
              │              │   缓存只存**成功**的解析，失败不缓存
              │  本轮意图为空则 A-1 兜底合并（本轮非空覆盖；维度是替换不是并集）
              │  越界 → 澄清（不猜）
              ▼
        语义层渲染（确定性拼 SQL：口径 / 时间 / 别名 / 表前缀全不由模型决定）
              ▼
        只读护栏（只读连接 + 单条 SELECT 白名单 + 超时 + 表白名单）
              ▼
        B-5 行级权限（**temp view 遮蔽** · 加在 SQL 层）
              │  裸表名先解析 temp 再解析 main → CTE / 指标 / 基础查询**一处覆盖**
              │  建视图后立刻 `SELECT * FROM 表 LIMIT 0` 探一次（SQLite 不校验视图体）
              │  遮蔽失败 → **阻断**（「部分遮蔽」比「不遮蔽」更危险）
              ▼
        执行 ──► B-3 脱敏（掩码 `***` · 在**结果层**）
              │      喂 A-2 解读时**整列摘掉**（不是喂星号）
              ▼
        A-2 一句话解读（模型）──► 防编造出口检查 ──► 丢弃 / 采用
              ▼
        应答 = 表格 + 口径 + 解读 + 图 + 「系统改了什么」+ 会话承接 + 身份来源
               + A-3 评价条（👍/👎 + 纠错框 → JSONL 台账）
```

> **顺序不能反**：先判「该不该答」，再问模型「怎么答」。反过来的后果（实测）：
> 问「上月员工工资总额」，模型会挑一张真实表硬答 —— SQL 合法、数字来自真实数据、
> **只有主题是错的**，而且无从对照检查。详见 `scripts/拒答.py` 模块头。
>
> **另三处「位置不能错」**（位置错了功能看起来一样是好的，所以每处都配了反例判据）：
> **行级在 SQL 层**（结果层过滤会让聚合 / 排名 / 总数的分母含看不见的行）；
> **脱敏在结果层**（改 SQL 会让聚合口径跟着变）；
> **脱敏在喂模型之前**（否则敏感值多一份流向，而且流向的是一个会把它写进回答的地方）。

#### 包 2 的判据补强（2026-10-17）：模型给的槽位**类型**也不可信

补跑回归时 50 题里有 6 题（全是「排名」类）**HTTP 500**。根因不是 SQL，是**解析层假设了类型**：
4B 模型把 `排序` 写成字符串（`"排序": "降序"`），代码直接 `排.get("按")`。

| 现场 | 后果 | 危险度 |
|---|---|---|
| `"排序": "降序"` / `"排序": "采购金额"` | `AttributeError` ⇒ **服务 500** | 中（响） |
| `"过滤": {…}`（单对象而非数组） | `for 条 in dict` 迭代出**键名字符串**再 `.get()` ⇒ 500 | 中（响） |
| `"维度": "供应商"` | **逐字符迭代** ⇒ 维度变成「供」「应」「商」 | **最高（不报错）** |

修法：抽 `_规整容器槽位()`，**一条判据一处实现**（原先三处各自假设类型）。分寸两条线：

- **能无歧义还原的就还原** —— 方向词、单值维度、单个过滤对象。措辞级失误不该罚成失败。
- **还原不了就阻断** —— 丢掉过滤 = 条件消失 = 范围变大 = **数字错但看着正常**，比 500 危险。

⚠️ 改了解析行为就必须作废缓存：`解析规则版本` **r7 → r8**（新增 `容器规整:v1`）。否则旧意图缓存会**复活旧行为且不报错**。

**根因**（两条，同源）：`问数服务.py` 有**两个**地方会产出「澄清」——

### 补丁（2026-10-15 深夜）：跨指标前置规则 —— ≥2 个指标词 → **直接澄清、不进模型**

**症状**：有一类问句**同时提到两个指标**（例：「各供应商的**不良率**和**准时交付率**分别是多少？」）。
模型把两个指标**都识别对了**，却顺手给了个「能跑的结构」——
`SELECT COUNT(*) AS 供应商数 FROM 供应商`。**宁可答非所问，也不说「我一次只能答一个」。**

**为什么交给纯规则，而不是继续训模型**：

1. 「两个指标词共现」是**字面可判**的 —— 交给模型等于用 26 分钟 GPU 买一个字符串匹配能做的事；
2. 判断发生在**前置层**（`问句 → 前置判定（纯规则）→ 意图解析（模型）`），
   与 `拒答.py` 的元问题/拒答**同层同顺序**，是既有架构里早已定好的一格。

**落点**

| 文件 | 改动 |
|---|---|
| `scripts/跨指标.py` | 规则本体（纯函数 + CLI，`--问题 "…"` / `--词表`）；词表**从 YAML 取、不手抄** |

**三条设计纪律**（都是踩过才写的）

1. **最长优先 + 区间不重叠**：别名互为子串是常态（「交期达成率」⊃「达成率」），
   不按最长匹配就会把**一个**指标数成两个 → 正常单指标问句被误判成跨指标。
2. **按指标去重**：同一指标的名称与别名同时出现（「来料不良率」⊃「不良率」）是同一件事。
3. **宁可漏判，不可误判**：漏判 = 照旧走模型（最坏等于现在）；
   误判 = 能答的问题变成答不出，**而用户无从察觉**。

**定向澄清不经过 `拒答.反问补强`** —— 那段给的是**通用**五类清单（质量/交期/库存/工单/采购），
会把「一次只能按一个口径算 + 这句命中了哪几个指标」这份**定向**信息稀释掉。

### 补丁（2026-10-15 深夜）：意图缓存两处修正 —— **键里缺模型身份** + **开关被 `"0"` 静默改掉**

**症状**（在微调 lab 里炸出来的，一次真实事故）：同一句话，**无论哪个模型来解析都命中同一条缓存** ——
于是「未微调 / v1 / v2 / v3」四轮对照里 **31/40 题根本没调模型**，四轮结果逐字相同，
被读成「微调没效果」。更糟的是那批缓存**混着 LoRA 轮写下的条目**，
被后面每一轮当成基线的答案（`T16 / T30` 的「硬答」就是这么来的）。

**生产上的同形问题更严重**：在 APP 里把模型从 Spark-4B 换成 Qwen3-8B，
**旧模型写下的意图照样被照用**，而页面上不会留下任何痕迹。

**修法**

| 文件 | 改动 |
|---|---|
| `scripts/意图缓存.py` | `键()` 并入**生成端身份**（`CHATBI_GEN_URL` + `CHATBI_GEN_MODEL`）。⚠️ `提示指纹()` **刻意不含**模型身份 —— 它是对账脚本的「两轮可比性令牌」，含了会让「微调前 vs 微调后」的指纹必然不等 |
| `scripts/评测-盲测集.py`、`评测-链路准确率.py` | **不关缓存就 `return 1`**；逐题记 `意图缓存` 字段；收尾若出现「命中」→ **作废本轮** |
| `lab/跑对照.py` | 起跑前**真跑一次 subprocess** 的探针，把「语义缓存 / 前缀缓存 / 跨指标开关」三项报出来，任一不达标**当场中止** |
| `scripts/跨指标.py` | `关规则()` 加固：`"0" / "false" / 空` 一律算「不关」 |

**为什么探针要真跑一次 subprocess，而不是读自己刚设的变量**：开关漏设**不报错**。
10-14 那次漏设 → 四轮数字漂亮地趋同 → 被读成「题集没分辨力」。
**让被验证的东西自己报出来。**

> 🔴 **顺带抓到的坑：环境变量永远是字符串，`"0"` 是*真值*。**
> `CHATBI_NO_CROSS_METRIC=0`（本意「不关」）实际把跨指标规则**关掉了** ——
> 后果会是 A/B **两条臂都是关的**，得到一组「这条规则没影响」的数字，**而且不报错**。
> 这回是起跑探针当场拦住的（`实测 1（应 0）—— 中止`），一粒脏数据没跑出来。
> 已补 5 条自检断言钉住（含「`=0` 仍开」那条）。
> **规矩：要「开」就 unset，别写 `"0"`。** 同族风险：`关缓存()` / `关提示缓存` 用的也是 `bool(...)`。

**同一夜追加的一条更正（重要 —— 免得文档自相矛盾）**：
事故查证过程中，先后提出过两个「真变量」假设，**两个都被实测否掉**：
① 「换一次会话就不可复现」—— 同壳内两遍一字不差，**两个独立壳进程判据 0/40、意图 0/40**；
② 「慢态 / 机器状态就是那条变量」—— 第三跑后段**自己劣化到 3.7~4.0 tok/s**，
**输出 token 数与健康态逐条相同、意图全同**（同一数值路径慢 5.6 倍，答案不变）。
**第三个候选 = SDPA 开关集**（当晚只有一台壳把 `mem_efficient` / `math` 关掉）——
**该候选的实验已做（2026-10-15 傍晚，`lab/实验-只切SDPA.py`）**：
结论不是「开关集让答案偏移」，而是「**`cudnn`-only 那条路本身不可复现**」——
**全开**同壳两遍 **8/8 一致**，**`cudnn`-only** 同壳两遍 **1/8**（7 题两遍就变）。
→ 「慢」因此分两种成因：① `cudnn`-only（**不可复现**）② 机器劣化但开关全开（**仍可复现**）。
⚠️ 所以**不要**把「起服务的解码速度」当「答案可比性判据」（那句无实测支撑，已按成因分档）；
**新判据是「哪一套 `SDPA` 开关集」** —— 壳的 `/health` 现在回读 **`SDPA开关集`**
（`LAB_SDPA` 可切，**默认「全开」= 生产路径**），`scripts/诊断-生成端可复现.py`
会**先打印它**、并在非「全开」时告警（那条路上「两跑不一致」是**预期**，别当引擎坏了）。
细节 → 训练营 `D23-微调最小版/微调前后对比报告.md`「四·补六」补六-2 ／ 第七节 #14。

> 🔴 **同轮追加（2026-10-15 傍晚）：超时只能有一份定义。**
> 拿一台**已知健康**的壳做本脚本的**正向对照**时，它**在第 4 次生成上超时退出**。

#### 包 4 抓到的坑：**生成端的「提示前缀缓存」会翻答案**

包 3 自检里 D16「这个月怎么样？」稳定判 **SQL 硬答**，包 4 评测里同一句话稳定判 **澄清** —— 同一提示词、同一模型、同一请求体。隔离实验（`scripts/诊断-生成端可复现.py`，直连 8000）：

| 请求（同一提示词） | 结果 | 用时 |
|---|---|---|
| 默认（提示缓存开） | `{"指标":"来料不良率","时间":"本月"}` | 0.5 s |
| 再次（缓存开） | 同上 | 0.5 s |
| **`cache_prompt: false`** | `{"澄清":"需要明确具体指标（如来料不良率、准时交付率等）"}` | 2.0 s |
| 再次 `cache_prompt: false` | 同上 | 2.0 s |
| `cache_prompt: true` | 回到 `{"指标":…}` | 0.56 s |

**根因**：开缓存时复用多少前缀**取决于上一条请求**，预填充的批组成随之变化 → 浮点路径不同 → 近 tie 的 token 翻分支。（与作品一「多槽浮点不可复现」同一条机理，只是这次主角是**前缀缓存**而不是槽数。）

**处理**：`意图解析.调模型` 显式给 `cache_prompt`，由环境变量 `CHATBI_NO_PROMPT_CACHE` 控制 —— **评测 / 自检关缓存拿可复现数字，生产默认开（首 token 快 ~2 倍）**。

> ⚠️ 环境变量名必须 ASCII：bash 的标识符只允许 `[a-zA-Z_][a-zA-Z0-9_]*`，中文名会被当成命令名（`CHATBI_关提示缓存=1` → `command not found`，实测）。

**代价与已知边界**：关缓存后平均模型用时 1.37 s → 2.28 s（全量 50 题 91.9 s）。**生产默认（缓存开）在同一句话上不保证稳定** —— 这是本轮新暴露的已知边界，写进报告第 6 条。

| 3 | 制度词 → 知识 | 「怎么规定 / 流程是什么 / 在哪份文件」… | **优先于数据词**：「采购流程怎么规定的」含「采购」（数据词），但问的是流程 —— 送进 SQL 只能编 |
| 4 | 时间限定词 → 数据 | 「这个月 / 上月 / 最近 / 近三个月」… | 兜不住就固化（见下） |
| 5 | 元问题短语 → 数据 | 「准不准 / 有多少条数据」… | 这些短语只可能在数据链路被回答（ChatBI 有 0 秒的确定性前置判定） |
| 6 | 数据词 → 数据 | 表名 / 指标 / 维度 / 别名（**由定义自动收集，105 个**） | 不手抄 —— 新增指标不必改路由 |
| 6.5 | **动作嫌疑** → 动作（改判） | 单据名 / 处置动词（整改·补货·发函·追责…），且**无**问数信号、**无**制度词 | **挡在模型兜底之前**：「要不要做单」不能交给不可复现的模型决定（见下） |
| 7 | 都不命中 → 模型兜底 | 三选一 | **兜底要留痕**：应答里标 `依据=模型` |

> **规则 4 是实测逼出来的**：「这个月怎么样？」不含任何数据词、也不含制度词 → 交模型 →
> 模型选了「知识问答」→ 知识库答「资料不足」。而它真值该走**数据问数**
> （ChatBI 会反问「哪个指标：质量 / 交期 / 库存…」—— 那才是有用的下一步）。
> **兜底不可靠，就把可靠的特征固化成规则**；放在制度词之后，所以「上月的制度培训」仍走知识。

**ReAct 实测（真模型，2 步）**

```
用户：给东莞精诚出一份质量整改通知
路由：动作执行（确定性 —— 命中动作动词「出一份」）
  第 1 步  查数据 {"问题":"东莞精诚的来料不良率"}
           观察：查询成功（1 行）：供应商 / 不良率 ‖ 东莞精诚五金制品有限公司 , 4.79
  第 2 步  生成质量整改通知 {"供应商":"东莞精诚五金制品有限公司"}
           观察：→ 质量整改通知-东莞精诚五金制品有限公司-20261012-175656.md
```

模型自己完成了两件事，都没人教它：**把动作型问句改写成查询型问句**，
以及**把用户说的简称对齐到库里的规范全名**（观察里带回了全名）。单据里的 4.79
就是第 1 步查出来的数字 —— 不是模型写的。

**带纠偏的实测（真模型，4 步）** —— 同一个入口，这次下游给了一个不切题的依据：

```
用户：帮我起草一份补货申请
路由：动作执行（确定性 —— 命中动作动词「起草」）
  第 1 步  查数据 {"问题":"低于安全库存的物料有哪些"}   → 观察：物料数 ‖ 30（只有计数！）
  第 2 步  （依据不切题，退回重查）                       ← 编排层的确定性检查，不是模型选的
           观察：⚠️ 下游把问题理解成了「计数」查询 —— 单据要的是明细清单
  第 3 步  查数据 {"问题":"低于安全库存的物料明细有哪些"} → 观察：物料数 ‖ 30（还是计数）
  第 4 步  生成补货申请 → 单据产出（附「依据仍不切题」警告）
答复开头：⚠️ **本单据的依据可能不切题** …… 请核对下方依据后再使用。
```

**这次退回重查没能救回来 —— 因为根因在下游**：8095 开着提示缓存时，
同一句问法的输出被稳定地翻到「计数」分支（包 4 的发现）。编排层能做的两件事都做了：
**换问法重查**，以及**在答复最前面加粗标明依据有问题**。

> **为什么最后一版仍要生成，而不是「拒绝产出」**：单据本身长得完全正常，
> 异常只存在于「这张单据的依据其实不支撑它」这件事里。**给一份看起来正常的废单据
> 比说「没生成」更危险** —— 所以选择生成 + 显式警告，而不是沉默地产出。
>
> **已知边界**：要拿到切题的依据，**下游问数服务也须以 `CHATBI_NO_PROMPT_CACHE=1` 启动**
> （编排层控不了下游进程的环境变量）。这是包 4 那条边界的延续，不是编排层能修的。

**「动作请求被误判成查询」—— 一个不报错的坑（2026-10-17 修）**

现场：用户说「东莞精诚的整改通知」。这句**不含**任何动作动词（没有「出一份」），
规则 1/2 不命中；它也不含数据词与时间词 → 落到模型兜底。模型把它当成查询 →
下游返回「东莞精诚的不良率 4.79%」。**这个数字是对的，问题是用户要的单据根本没做。**
不报错、不违反任何既有判据、用户不会察觉 —— 因为返回的那行数字看起来完全正常。
比直接报错危险得多。

修法分三层，每一层对应一种「静默」：

| 层 | 做法 | 为什么不能只做前一层 |
|---|---|---|
| ① 判定 | `动作嫌疑`：单据名 / 处置动词（整改·补货·发函·追责…）任一命中 | 动作词表是正向覆盖，总会有说法盖不住 |
| ② 改判 | 嫌疑成立、原判是**只读链路**或**模型兜底** → 改判动作执行，`依据=确定性-动作嫌疑` | 只加提示救不了「看到数字就以为是答案」的人 |
| ③ 可见 | 答复前置「已按动作执行处理（原判只会返回数据）」；执行不出单据时写「**未生成任何单据**」并说明轨迹里的数据不是单据 | 改判本身也得可解释，否则下一次用户以为原话就够了 |

两道闸（缺一条就会把正常查询劫成单据）：

- **问数信号**（多少 / 几份 / 哪些 / 排名 / 分布 / 占比 / 情况…）→ 否掉嫌疑。
  「这个月整改通知发了多少份」必须留在数据链路 —— 评测集里作为反例 `R38`。
- **制度词** → 否掉嫌疑。「整改通知的流程是什么」必须留在知识链路（`R06`）。

三条顺带钉住的边界：

1. **不进模型兜底**：嫌疑判定是确定性的，`R37/R39` 才能在「确定性题必须全会」这一节里被要求必过。
2. **不绕过权限**：改判换的是链路，不是人。操作员说「东莞精诚的整改通知」→ 改判动作 →
   撞白名单 → **HTTP 403、产物 None**（`自检-编排` 第三节有断言）。
   「静默降级成查询」正是 `权限.py` 明令禁止的那件事。
3. **无产物 ≠ 没查**：动作链路里模型可能只查了数就收工。此时回答必须显式写
   「未生成任何单据」，否则用户会把轨迹里那行数字当成结果。

实测（真机，管理员角色，6.9 s）：

```
用户：东莞精诚的整改通知
路由：动作执行（确定性-动作嫌疑 ← 原判 数据问数 / 模型兜底）
  改判：原链路 数据问数 ｜ 证据「整改通知」｜ 否因 无
  第 1 步  查数据 {"问题":"东莞精诚的来料不良率"} → 4.79
  第 2 步  生成质量整改通知 → 质量整改通知-东莞精诚-20261017-181046.md
答复开头：ℹ️ 这句没有「出一份 / 起草」这类明确说法，但提到了动作类词汇「整改通知」，
         已按**动作执行**处理（原判「数据问数」只会返回数据、不生成单据）。
```

> **代价（有意接受）**：动作链路要真调模型。模型在动作链路里不稳时（7B 常见：
> 空动作名、反复查数），用户看到的是「**未生成任何单据**」—— 比「一个看起来正常的错数字」
> 好，但仍是失败。这条修复买的是**失败可见**，不是**成功率**。

#### 10-18 续：先量，再改 —— 产出率 30% → 60%，病灶不在 ReAct

改判上线后「口语化动作还是做不出来」，直觉都指向 ReAct 的 4 步预算。**先量了一下，结论相反。**

`scripts/评测-口语化动作.py`：10 句**不含**「出一份 / 起草」这类显式动词的人话（这才是要检验的对象），
逐题记「进了哪条链路 / 有没有产物 / 卡在哪个结束原因」。**这是量，不是判** —— 不设通过线。

| 轮次 | 产出率 | 路由层卡住 | 执行层卡住 |
|---|---|---|---|
| 扩词前 | **3/10 = 30%** | **6 题**（3 知识 / 3 数据） | 1 |
| 扩词后 | **6/10 = 60%** | **0 题** | 4 |

**7 题失败里 6 题根本没进动作链路** —— 病灶在「处置动词」词表没覆盖人话说法
（退货 / 约谈 / 谈谈 / 处理一下 / 得补 / 补单 / 记下来），跟 4 步预算毫无关系。
按直觉去动 ReAct 预算，等于给一场「没进对门」的失败加座位。

扩词只影响 `动作嫌疑`（不进链路判定的主词表），且每个新词都配反例钉住：
「这个月退货**多少**」被问数信号闸住、「退货**流程是什么**」被制度词闸住、
「不合格品应该**怎么处理**」本来就命中制度词。`自检-编排` 加两条表驱动断言
（6 句必须改判 + 6 条反例不许被劫），确定性路由仍 **35/35**。

**剩下 4 题的失败现在各不相同**（这正是下一节容忍额度的用处）：

```
连续 2 次没给出动作名      ×2
连续 2 次输出不是合法 JSON ×1
模型给出最终答案（不该收工时收工）×1
```

改前这 4 题会**全部显示「达到步数上限」** —— 看起来像「预算不够」，实际是「模型不会挑工具」。

#### 容忍额度：坏一次不许判死，三种坏态不许同形

| 坏态 | 改前 | 改后 |
|---|---|---|
| 输出不是 JSON | **一次就 `break`**（4 步里只用 1 步就收工） | 喂回格式纠正，连续 2 次才收 |
| 动作名为空 | 记轨迹但**不 break**（注释写「结束」），结束原因被后续覆盖 | 喂回「二选一：给动作，或给最终答案」+ **可选动作名**，连续 2 次才收 |
| 动作名不存在 | 同上，且观察只说「没有这个工具」（模型无从改） | 观察里列出**全部可选动作**，连续 2 次才收 |

三条结束原因**分别命名**，不许同形：`连续 2 次输出不是合法 JSON` / `连续 2 次没给出动作名` /
`连续 2 次选了不存在的工具`。它们与 `达到步数上限`、`模型给出最终答案` 一起，
共同回答「这次到底卡在哪」—— 并且通过 `应答.结束原因` 传到给用户看的那段话里。

**「连续」不是「累计」**：坏-好-坏-好累计两次但从不连续，说明模型已经纠正过，不许罚
（有一条专门的假模型用例钉住 —— 把计数写成累计，只有它会红）。

**判据设计（三处刻意的选择）**

1. **两个数字分开统计**：`确定性准确率` 只统计规则判的题（必须全会，规则可证）；
   `兜底准确率` 只统计模型判的题（不要求全会 —— 它的用途是把「规则盖不住的说法」
   的真实水平**量出来**，而不是藏进总准确率里靠规则的好成绩掩盖兜底）。
2. **边界用例占约 1/3（11/39）**：含单据名却问流程（必须走知识）、含数据词却是动作请求（必须走动作）、
   含时间词却含制度词（制度优先）、含单据名却在问数量（不许劫成动作）。**全典型题的评测集测不出路由的真实水平。**
3. **路由依据五态分明**（`确定性 / 确定性-动作嫌疑 / 模型 / 默认 / 强制`）：若只报「走了哪条链路」，
   就无法区分「规则判对了」与「模型蒙对了」—— 而这两者的**可维护性完全不同**；
   「改判过」也必须单独一态，否则改判这件事会变回静默。

**第六节 / 第四节的判据为什么必须注入假模型**

真模型的行为每次不一样，**「模型跳过取数直接生成」这个分支用真模型几乎测不到** ——
而它恰恰是本包最危险的分支（单据里的数字会变成模型编的）。做法是给
`执行动作链路(调=假模型)` 注入一段固定输出，确定性地逼出该分支：

| 注入的假模型输出 | 期望行为 | 结果 |
|---|---|---|
| 直接调「生成质量整改通知」（跳过取数） | **编排层补一步取数**，单据必须带依据 | ✅ |
| 调一个不存在的工具 | 记进轨迹并结束，不崩 | ✅ |
| 输出根本不是 JSON | 优雅结束，不崩 | ✅ |
| 直接给「最终答案」 | 结束且**无产物**（不算成功） | ✅ |
| 反复要求查数据 | 在 `最大步数` 处停下 | ✅ |
| 查回一个「计数」结果就去生成单据 | **退回重查**（换问法），第二次仍不切题才带着它生成 | ✅ |

**「依据切题」护栏 —— 一个不报错的坑**

演示时发现：`帮我起草一份补货申请` 被模型改写成查「需要补货的物料信息」→
下游返回 `{"基础查询":"计数","目标":"物料"}` → **列只有一个「物料数」，值 30**。
**单据照样生成了、数字也是真的，但依据完全无法支撑处置** —— 这类错不报错、
也不违反任何已有判据（缺参数会报错、越界会报错，这个不会）。

根因是下游的生成端提示缓存把同一问句翻到了另一个分支（见包 4），
但**编排层不该假设下游永远正确** —— 于是加一道确定性检查：`动作表` 里声明
`要明细`，编排层比对下游应答里的 `意图.基础查询`；判为「计数 / 枚举」或
「单值结果」就**把结论喂回去让模型换问法重查**（只喂回一次，否则任务永远完不成）。

> 🔴 **这条判据第一版写错过**，被自检当场抓出来：最初打算匹配列名里有没有
> 「物料名称 / 物料编码」，结果 `["物料数"]` **含「物料」子串** → 误判成切题。
> 而下游应答里本来就有 `意图 = {"基础查询":"计数","目标":"物料"}` ——
> **它已经明说了这是什么查询**。改成照 `意图` 判之后，精确且不需要维护词表。
> （与「唯一事实来源」同一条纪律：信息已经在了，不要再造一个近似判据。）

**包 5 抓到的五个坑**

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 自检跑到最后一节**整个崩了** | 判据里有「非法输入必须回 400」，而 HTTP helper 只在 2xx 时返回 → **服务规规矩矩回了 400，脚本却抛异常退出**，于是「服务对了」被记成「自检失败」 | helper 返回 `(状态码, 对象)`，接住 `HTTPError`。**与包 3 的 `耗时 or 9` 同类：判据自己出错** |
| 2 | `调用(动作名, 供应商=…, 物料=…, 依据=…)` → `TypeError: unexpected keyword argument` | 调用方统一传全部参数，而不收该参数的函数直接炸 | 按**动作表声明的参数**过滤后再传（调用方「记得传什么」是不可靠的，加一个动作就会被漏掉） |
| 3 | 关键词规则漏一种说法 → **静默送错链路** | R05「供应商降级处理的**规定**在哪份文件里？」含「规定」但不匹配「怎么规定 / 什么规定」这类**前置疑问构型** → 落到数据词规则 → 走了数据问数。**而命中的那个词看起来还挺合理** | 补「求出处」类词（`的规定` / `哪份文件` / `文件里` / `出处`）。**规则漏了，下一条规则会「合理地」接住它** —— 关键词路由最需警惕的失效方式 |
| 4 | 单据依据完全**不切题**（单据照出、数字也真） | 模型把「起草补货申请」改写成查「需要补货的物料信息」→ 下游判成「计数」→ 依据只有一个「物料数 30」。**这类错不报错、不违反任何已有判据** | 加「依据切题」护栏（`要明细` 标记 + 照下游的 `意图.基础查询` 判），不切题就**退回重查一次**（见上） |
| 5 | 用户要单据，系统**静默答了另一个问题** | 「东莞精诚的整改通知」不含动作动词 → 规则判不出 → 模型兜底当查询 → 返回「不良率 4.79%」。**数字是对的，单据没做，用户不会察觉** | 加 `动作嫌疑`（单据名 / 处置动词）+ 两道闸（问数信号 / 制度词），嫌疑成立即**改判动作**；不出单据时回答必须写「未生成任何单据」（见上） |

**动作层的两条纪律**

1. **单据正文一律模板拼，绝不调模型。** 单据要发出去、要对方签字，数字必须与查询结果
   **逐字一致**。模型只允许出现在「决定生成哪种单据 + 填哪个对象」这一步。
   判据：同一依据跑两次，正文必须**逐字节相同**（自检第四节覆盖）。
2. **业务库永远只读，产物只写 `outbox/`。** 越界路径直接抛错（自检覆盖）。
   包 6 的权限白名单就挂在这一层 —— 白名单外的路径一律拒绝，且拒绝要能在审计里看见。

**回归**：包 1 校验 **15/15 + 5 组对照**（包 5 未改任何已有文件 —— 新增 4 个脚本 + 1 个页面 + 1 个评测集）。

### 包 6 ✅（2026-10-13）：权限白名单 + 审计日志

一句话：**动作链路能产出要发出去的单据，所以「谁可以发起」必须能回答，且每次调用要留痕。**

| 交付物 | 作用 |
|---|---|
| `scripts/权限.py` | 角色 → 允许动作的白名单；越权**硬拒**（不生成、不落盘、不静默降级） |

**角色白名单 —— 按「对外程度」分档，不按「职级」分**

| 角色 | 边界 | 动作 |
|---|---|---|
| 操作员 | 只读留痕 | 导出异常台账 |
| 主管 | 加**内部**申请（给采购部） | + 生成补货申请 |
| 管理员 | 加**对外**发文（给供应商，对方要签字） | + 生成质量整改通知 |

职级是组织问题，**对外程度才是风险问题** —— 一张发给供应商、要对方签字的整改通知，和一张内部台账，本来就不是同一类动作。HTTP 入口不传角色时默认 **操作员**（最少权限）。

**三条设计纪律**

1. **默认最少权限**：白名单里没写的动作 = 不许做。不给「没配就放行」的方便 —— 那种方便在演示里看不出代价。
2. **越权是硬拒**：不生成产物、不落盘、**不静默降级**。把「发整改通知」悄悄改成「查一下数据」比拒绝更危险：用户以为事办了，其实没办，连可核对的对象都没留下。
3. **拒绝要给出路**：理由里说清「这个动作需要哪个角色」（与包 3 的拒答同一条纪律）。

**权限与审计都收在 `动作.调用()` 一个关口上**

```
编排层  →  动作.调用(动作名, 角色=…, 依据切题=…)  →  权限检查 → 落盘 → 审计
                        ↑ 唯一必经关口
```
放在这里而不是编排层：**只要有人能拿到 `动作.调用`，这一关就绕不过去**；分散到各调用方 = 加一条新链路就漏一处。编排层只传上下文（角色 / 依据切题），自己**不判**权限 —— 多一处判断就多一处口径分叉。

`角色=None` = **内部直调**（脚本 / 自检 / 单测），不启用权限检查 —— 这是**显式**边界，且审计里记成「（内部）」，不是静默放行。

**HTTP 403 是必要设计**：状态码本身就得说明「你被拒了」。只把被拒写在 body 里，前端要「记得查 body 里有没有被拒」—— 那是**漏写就静默当成功**的判据，不能作为权限的对外表现。

**审计为什么必须记「依据不切题」**

包 5 真的产出过一张「正文数字都对、但依据不支撑它」的补货申请单（依据只有一个「物料数 30」，而补货申请要的是缺料**清单**）。这类错**不违反任何已有规则** —— 缺参数会报错、越界会报错，它不会。
**白名单只防得住「不许做的事」，留痕才防得住「做了但做错的事」。**

**包 6 抓到的坑**

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 自检「明明隔离了」，真实 `outbox/` 与审计里还是多了记录 | **子进程有自己的模块状态** —— 自检把 `动作.产物目录` / `审计.审计目录` 改成临时目录，但 HTTP 段启动的 `编排服务.py` 子进程**看不到**；只有环境变量能传过去 | 加 `CHATBI_OUTBOX_DIR` / `CHATBI_AUDIT_DIR` 两个覆盖（同时也是**部署要用的旋钮**：产物与审计常需落独立盘）。判据：自检前后 outbox 与审计**逐字节不变** |
| 2 | **回归判据自己错了** | 拿**全量**基线 34/1/0 去比 `--跳过HTTP` 跑出来的 29 项；更糟的是全量里含**兜底路由题**（走真模型、每次答案可能不同）—— 拿不可复现的数字当回归判据，判据自己先坏 | 改用 `--跳过HTTP --跳过模型` 的**确定性**基线 **24/0/2**。与包 3 的 `耗时 or 9`、包 5 的 HTTP helper 同类：**判据自己出错** |
| 3 | 越权后「让模型换个动作试试」看起来很合理 | 但**没权限是人的权限问题，不是模型的问题**；模型绕开一次，权限就等于不存在 | 硬拒 + **终止**（`结束原因=权限不足`），不重试、不换动作 |
| 4 | 白名单写成「生成补货申请单」（多了「单」字） | 手写字符串，写错**不报错** —— 只表现为那个角色**永远**权限不足，看上去像权限设计而不像笔误 | `权限.校验配置()` 双向对齐：白名单里的动作必须真实存在；每个真实动作至少有 1 个角色能做。**配置错了却表现为「正常拒绝」，是最难查的一类问题** |

**判据设计（三处）**

1. **期望矩阵手写，不读 `权限.角色表`** —— 拿被测对象自己的数据当判据，等于让它给自己打分，白名单写错了照样全绿。
2. **必放 + 必拒双侧**，且各记一笔 —— 只测「必拒」会把「一律拒绝」当通过；只测「必放」会把「一律放行」当通过。
3. **自检不污染真实产物与审计** —— 隔离目录 + 结束 `rmtree`；子进程靠环境变量隔离（坑 1）。

**回归**：包 5 确定性部分 **41/0/2**、确定性路由 **35/35**（2026-10-17 动作嫌疑后 33/0/2，2026-10-18 口语化处置词后 41/0/2）；包 1 校验 15/15 未受影响。
包 6 **改了 3 个已有文件**（`动作.py` / `编排.py` / `编排服务.py`）—— 这是本系列包首次改动已有文件，所以回归判据必须比以往更硬。

**已知边界**

- 审计是 **append-only，但不是防篡改**：谁能删 `logs/审计-*.jsonl` 本身是个权限问题。真实部署应把审计落到**独立目录 / 只追加权限**的盘上（已留 `CHATBI_AUDIT_DIR` 这个旋钮）。
- 权限只管**动作链路**。知识问答与数据问数是只读的，**不按角色拦** —— 真要拦，拦的是「哪些数据可见」（行级/列级授权），那是另一个问题；混在一起会让白名单说不清自己在管什么。
- 角色是**单一角色**，没有做「多角色并集 / 角色继承」。演示够用；真实组织要加，也只需扩展 `权限.角色表`（记忆里记一笔）。

### 一、`scripts/启动-服务.py` —— 统一启动器

回答一句话：**「这套服务该怎么起、起对了没有？」**

| | 谁 | 为什么 |
|---|---|---|
| **本脚本起** | 问数 8095 · 编排 8096 | 作品二自己的两个进程 |

🔴 **为什么只检查不代起：一个进程只能有一个主。** 两个仓库各写一份「起 8092」的命令，
就会出现「谁的版本对」「谁改的端口生效」这类查不清的问题。作品二只**探活 + 报告**，
缺了就把话说清楚：「去作品一的启动器起它」。

**四个档位**：默认（体检 → 起缺的 → 自证）· `--状态`（只读）· `--演练`（只打印命令）·
`--停` / `--重起` / `--强制` / `--前台`。

**沿用作品一那套被坑出来的纪律**（不是重抄，是同源）：

| 纪律 | 由来 |
|---|---|
| 起之前先数端口上有几个 PID | Python 能多进程绑同一端口，**不报错、请求随机分流** —— 「我明明重启了，改动就是不生效」的根因 |
| 发现问题不静默重起，要 `--强制` | 脚本最该防的就是「以为重启了」 |
| 起完自证，且用**能区分版本**的判据 | 编排服务看 `/health` 有没有 **`权限`** 块（包 6 新增的键）；**banner 不能当版本判据** |
| `--演练` 与实际执行走**同一个命令拼装函数** | 否则「预览的命令」与「真跑的命令」各写一份 = 同一份事实两处定义 |
| 端口在听却不应答时，分开报「没起来」与「被卡住」 | 后者是控制台被鼠标拖选，**按 Esc 即可，不用重启** |

**自证里刻意不断言的一项**：下游链路（知识问答 / 数据问数）不可达时**只警告不计失败** ——
缺的是**别的归属**没起，不是本脚本的产物。**判据不能把别人的问题算成自己的失败。**

**实测**：`--状态` 5 个端口全部单实例；8096 报 `版本 1.1`、有 `权限` 块、**下游链路 3/3 可达**、

### 包 7 附 ✅（2026-10-13）：问数页图表（ECharts）

数据题的结果集（`列` + `行`）本来就够画图 —— **服务端只加了一条静态资源路由，问数逻辑一行没改**，
图表全在页面侧加。

**三个设计决定**

| 决定 | 做法 | 理由 |
|---|---|---|
| 库从哪来 | `web/vendor/echarts.min.js` **本地落盘**（5.5.1 · 0.98 MB · Apache 2.0） | 不引 CDN：内网 / 断网都得能画。服务端配一条**白名单**路由发它 |
| 怎么判能画 | 整列非空值**全是数字** → 度量列；否则维度列 | 服务端**不给列类型**（应答里只有 `列` / `行`），只能这样推。这套推断**只有一份**：出图与否 / 默认图型 / 饼图可否都调它 |
| 画什么图 | 默认：类目 ≤ 12 柱状、> 12 折线；**不猜语义** | 猜「这是不是时间轴」，猜错就画出一条误导人的趋势线。类别多时默认折线只是显示偏好，用户一键可切 |

**不出图的情形**（都照常出表，不硬画）：无数值列 / 0 行 / 1 行（一根柱子没有可比性）。
饼图另有门槛：单度量 + 类目 2~8 + 无负数 —— 不满足时**按钮留在原地并置灰 + 给出理由**（`title`）；
直接消失会让人以为「这功能没有」。

**判据**：`scripts/探针-问数页.js` 第七节 **29 条** —— 桩掉 `echarts` 的 `init` / `setOption`，
断言 X 轴类目与 series 数据**来自应答而非页面写死**（后者是最像真图、也最有欺骗性的一种错）。
合计 **78 通过 / 0 失败**。服务端 `自检-问数服务.py` **61 通过 / 0 失败**
（含 vendor 正例 + 白名单外 4 条负例必须 404，其中 2 条带 `../`）。

🔴 **踩过的三个判据坑（共同点：拿什么当基线）**：
1. 起初拿「上月哪家供应商不良率最高？」当图表基线 —— 它**只回 1 行**，而「1 行不出图」是设计如此，
   于是判据报「图表功能没实现」。**先查真实应答行数，再挑基线**（换成「各仓库库存总量」→ 3 行）。
2. 「连续渲染只 init 一次」最初读的是**累计**计数 —— 但前面每小节都调过 `桩.清()`，
   读到的是个跟本节无关的数字。改成该段**自己先清空再计数**。
3. 白名单负例最初用**中文路径**，`urllib` 在发请求前就抛编码错（到不了 HTTP 层）→ 判据永远红，
   看着像服务端有洞。改用 `http.client` 直发 request-line（`urllib` 还会把 `../` 规范化掉，
   那样测的是客户端行为）。

### 包 8 ✅（2026-10-13）：A/B 档十项改进 —— 把「能演示」补到「像产品」

来源是 `docs/外部调研-同类项目与最佳实践.md` 里的四个闭环缺口（**没被评价过**、**没有多轮**、
**口径变了不知道影响谁**、**权限只到「谁能调哪个工具」**）。

**A-4 的结论（这才是这一项的价值）**：按问法类型拆开看失分面 ——

| 问法类型 | v1（提示词 A） | v2-全权（提示词 B） | 两版对着看能看出什么 |
|---|---|---|---|
| 真实日志原句 | 100% | 100% | 两版都稳 —— 这类题走的是拒答 / 澄清链路，提示词影响小 |
| 跨指标、需要组合条件的 | 100% | 83.3% | B 有一条「该澄清」答成了硬答 |
| 错别字 / 语序颠倒 | 100% | 66.7% | B 在错别字上丢了列、错了行数 |
| 同义改写（换词不换意） | 70% | **50%** | **B 更差** —— 该组 4 条失分里有 3 条是同一个形态（见下） |
| **口语化（「最近这阵子哪家拖得最凶」这类）** | **50%** | **75%** | **B 更好了** —— 口语本来就是 B 想修的那一项 |

**v2-全权 的头号失分形态：问「最高的**是哪家**」时丢了维度列。**
`T01 / T02 / T11 / T24` 四条（分属同义改写、口语、错别字三类）全是同一形态 ——
归一后的意图里**只有指标、没有维度**：`{"指标": "来料不良率", "排序": {"按": "度量"}, "限制": 1, "维度": []}`，
于是 SQL 只查出 `不良率` 一列，用户可以知道「最高是 8.3」，但**不知道是谁**。
它甚至不是「答错」，而是**答了一半**：结果集比对判的是缺列，人眼看上去却很像个答案。
同一个问句在 v1 里给的是「口径错」（行数对、取值错）——**两版的错法不一样，所以两版都得看逐题，不能只看总分。**

→ **两件事**：
1. **最短的板是「问法覆盖面」，不是「模型能力」**：口语化 / 同义改写明显低于其他三类。
   50 题集上的 97.5% 是**在自己出题、自己迭代过的分布**上测出来的，换个说法就掉。
2. **提示词 B 不是「全面退化」，是换了一块短板**：口语化 +25 pp，同义改写 / 错别字 −20~−33 pp。
   只看 v2 的 39.1% 会以为「改崩了、赶紧回滚」，拆开才知道**其中 21.8 pp 是权限污染**，
   提示词的真实代价是 13.0 pp —— 而下一轮该改的是**「问『是哪家』要补维度」这一条**，
   不是把提示词整体推倒重写。

→ 九条结论：
**① 「提示词 B 之后盲测从 73.9% 掉到 39.1%」这个说法是错的** —— 掉下去的一大半（21.8 pp）是权限，
与模型无关；**② 提示词确实改坏了 13.0 pp** —— 方向在提示词上，但幅度不是 34.8 pp。
**只看 v2 那个数就去重写提示词，等于按错误的幅度改错了对象。**
**③ 修「问『最高的哪家』丢维度」是目前收益最大的一次提示词改动：+30.4 pp。**
头号失分形态是「问『最高的是哪家』→ 归一意图里 `维度: []`」→ SQL 只出一列不良率，
**答了一半**（知道最高是 8.3，不知道是谁）；v2-全权 里 T01 / T02 / T11 / T24 四条全是这个形态。
**④ 去练题污染之后，分数没掉。** v4 把抄进提示词的题面例子全部改成模板式表述
（只教规则、不抄句子），T01 / T02 / T11 / T24 **依然全对**，总分还高了 4.3 pp
（那 4.3 pp 来自同批一起改的「场景优先」闸门 —— 它把 T15 从「澄清」恢复到答对）。
**说明这些题转绿靠的是规则本身的泛化，不是背例子**；但这一条必须专门跑一次才算数，
否则「87% 里有多少是练题」是说不清的。
**⑤ 这套评测的噪声是 0 —— 这一条把「单题翻转」的解读方式定死了。**
v5 同版本连跑两次，40 题逐题**完全一致**。所以「某题这轮过、下轮不过」**不能当采样噪声放过**
—— 它必然是**改动的真实后果**。实测就有一条：T13「v3 通过 → v4/v5 失败」，
上一轮我猜它是噪声，被这一测**否掉**了（→ 包 10 已按真回归处理）。

**⑥ 「加一条更强的规则」会打回别的题 —— 同一个坑第二次。**
v6 为修 T08 / T13（「有哪些 → 枚举」「一共多少 + 量词 → 求和」），在清单与规则 5 里加了
**🔴 加粗展开**的判据。T08 / T13 确实转绿，**但「哪些 / 一共有多少」这些字面也把别的题一起拽进了
「基础查询」路径** —— 净效果 **91.3 → 78.3（−13.0 pp）**：

|---|---|---|---|
| T05「哪些料号有缺料风险？」 | 指标「库存安全水位」·4 列 | `计数 + 物料` → `SELECT COUNT(*) FROM 物料` | **业务语义整条丢掉** |
| T17「各家仓库的库存加起来有多少？」 | 「分组」·有 `GROUP BY` | `求和 + 维度[仓库名称]` → **SQL 无 `GROUP BY`** | **意图对、渲染丢维度**（暴露了既有缺陷） |
| T02「…最高的是哪家？」/ T11「…头名是谁？」 | 指标路径·答对 | 输出退化成**单字「供」** → `就近()` 里 `"供" in "供应商"` 与 `"供" in "供应商类别"` 同时成立 → 判歧义 → 澄清 | **输出退化**（那条诡异的「『供』可能指…」） |
| T03「宁波恒力的交期达成率是多少？」 | 过滤「供应商名称 模糊 宁波恒力」 | **过滤丢了** → 88.40 ≠ 62.10 | **条件丢失**（数字错但看着正常） |

→ 与纪律 5 同源：**提示词的注意力是有限资源**。包 9 修 T15 时踩过一次（规则 12 把 T15 从
场景路径拉到指标路径 → 加「场景优先」闸门），这次方向相反、是同一类事故。

**⑦ 「按产物自洽性纠错」的兜底，抓不到「产物整体偏离语义」的错 —— 所以 v7 零效果。**
v7（v5 提示词 + 包 10 系统兜底）与 v5 **逐题完全一致**，T08 / T13 一条都没修好。
看模型这两题实际吐出的归一意图就明白了：

| 题 | 模型给的归一意图 | 兜底为什么不救 |
|---|---|---|
| T08「库房都有哪些？」 | `{"基础查询":"计数","目标":"库存记录"}` | 类型与目标**自洽** —— 「库存记录」**本来就在计数池里** → 兜底不认为是错 |
| T13「八月的单子一共抽了多少件？」 | `{"基础查询":"计数","目标":"到料检验"}` | 同上（「到料检验」也在计数池里） |

模型错的方式是**类型和目标一起错**（把「有哪些库房」理解成「有多少条库存记录」），
不是「两者打架」。而兜底的判据锚在**产物内部一致性**上（「目标不在当前类型的池里才纠」）
→ 对自洽的错误**完全免疫**。**推论：纠错判据的锚点必须是「问句语义」（字面模式 / 目标池），
不能是「产物自身自洽」。** 这是「全绿只证明实现与判据一致」那条铁律的镜像 ——
兜底把「实现自洽」当成了「正确」。

**⑧ 「锚点选问句」有效，「锚点选产物」无效 —— ⑦ 和 ⑧ 是同一件事的两面。**
v8 把 ⑦ 的推论**兑现了**：同一份提示词（逐字仍是 v5）、同一个模型输出，
只把纠错判据的锚点从「产物自洽」换成「**问句字面模式**」→

| | v7（锚在产物） | v8（锚在问句） |
|---|---|---|
| **T08** 模型原始意图 | `计数 + 库存记录` | `计数 + 库存记录`（**与 v7 一模一样**） |
| 判据看到了什么 | 目标在计数池里 → **自洽 → 不动** | 问句含「都有哪些」+ 实体「库房」→ **改判** |
| 归一后 | `计数 + 库存记录` | `枚举 + 仓库名称` |
| SQL | `SELECT COUNT(*) …` 1 行 | `SELECT DISTINCT 仓库名称 …` 3 行 |
| 结果 | 🔴 | ✅ |

→ **91.3 → 95.7（+4.4 pp）、逐题差异只有 1 题、零回归**，且转绿有**机器凭证**：
v8 的 `归一提示` 里记着「问句是「列举取值」型（问句里的「库房」）—— 查询类型「计数」按**问句**
改判为「枚举」」—— 是**规则**改的，不是模型这次恰好给对。

为什么这条非走系统侧不可 —— **提示词的注意力是有限资源**（结论 ⑥ 的 −13.0 pp 就是代价），
而字面模式是**规则问题**，规则就该让代码判：`问句要枚举()` 窄口径四关
（含列举词 ∧ 不含数量词 ∧ 不含指标/比较信号 ∧ 未出现别的池的名字），**任何一关不过就不介入**。

```python
# 目标列从 YAML 实体别名取（唯一事实来源），不硬编列名
列举词 = ("都有哪些", "有哪些", "有哪几种", "有哪几类", "包括哪些", …)
数量词 = ("多少个", "多少件", "多少家", "合计", "一共", "加起来", …)   # 「有几个」是计数
指标信号 = ("率", "风险", "水位", "达成", "排名", "最高", "超标", "超过", …)
```

三条边界（都写进自检的反例了）：
**① 带时间的问句不介入** —— 枚举渲染（`语义层.py` `类=="枚举"` 分支）**没有 WHERE**，
改判等于把时间**静默丢掉**（与「基础查询没有过滤槽位」同源的事故形态）；
**② 定位不到枚举列就不猜**（「供应商有哪些？」—— 枚举池里没有「供应商名称」）；
**③ 前缀不许误伤**（「物料类别都有哪些？」里的「物料」是计数池表名，
但它是枚举列「物料类别」的前缀 → 先把问句里的枚举列名**遮掉**再判他池）。

🔴 **T13 仍是红的，且是刻意不修 —— 但它的「为什么」被实测改写了一次（包 12），又被一次对照题钉死了（包 13 / v9，见结论 ⑨）。**
它要的是「**求和**」，目标应是数值列 `抽检数量`。**原来的说法（「表下有两列 → 定位不唯一」）是错的。**
做了一次**最小变量对照**（每次只改问句里的一个成分，看模型的类型判定怎么变）：

| 变体 | 问句 | 模型给的 | |
|---|---|---|---|
| A | 八月的单子一共**抽了**多少**件**？ | 计数 + 到料检验 | 🔴 |
| B | 只换动词 → 一共**抽检了**多少件？ | **求和 + 抽检数量** | ✅ |
| C | 只换表名 → 八月**份到料检验**一共抽了多少件？ | 计数 + 到料检验 | 🔴 |
| D | 只换量词 → 一共抽了多少**数量**？ | **求和 + 抽检数量** | ✅ |
| E | 全换（「…来料单一共抽检了多少数量」） | **求和 + 抽检数量** | ✅ |

**「抽检」或「数量」任一个出现就够了；把表名写全（C）完全没用。** 这说明：
**模型根本没走到「选哪一列」—— 它在第一步「求和 vs 计数」就判错了**（把「多少件」读成
「多少张单子」）。「定位不唯一」是我**在「假设类型已经判对」的前提下**推出来的，
而实测证明那个前提根本不成立 —— 属于「编了一个自洽但错的故事」。

真实原因：**「件」在中文里既能量单据、也能量货**，字面区分不了 —— 把「件 / 个」当数量量词，
会让 T06「一共有多少个厂家？」（计数）一起中招。按纪律（不为单题定制字面规则、不硬编列名）
→ **留在红榜**；而且模型选的读法**自洽**（「八月有多少张检验单」），这正是本题想测的
**confidence wrong**（看起来答了、其实答的是另一件事）。**留在红榜，比用一条猜出来的规则凑绿更诚实。**

> 作者给的改写（变体 E）**实测能过**。但**改题 = 改标尺**：40 题的十轮历史会因此不可比，
> 而且这题是「B 档 · 口语」—— 改成书面语就丢了这个测点。
> **✅ 已按「保留原题 + 另立一道「无歧义版」当对照」落地（包 13 / v9）**：
> `eval/对照题集-1题.json` 的 `C13`（同语义、同金标准 SQL），`--加对照` 挂上跑，
> **主尺一字未动、对照单独成节**。实测 **C13 ✅ 且无系统干预** → 归因彻底闭合（见结论 ⑨）。

**缓存必须跟着一起改（否则规则等于没生效）。** 这是本轮唯一的暗坑：
`意图缓存` 原来是**只按提示词**作废的（`提示指纹 = hash(提示词)`），而 B 方案**不改提示词**
→ 规则改了、旧缓存照样命中，**而结果看起来完全正常**（不报错、不告警）。
现在 `提示指纹 = hash(提示词 || 解析规则版本)`，规则版本是 `r2:问句枚举:v1`，
并加了一条自检断言盯住「`问句规则签名 ∈ 解析规则版本`」——
**改规则忘了 bump 版本 → 自检红**，不靠人记得。
（副作用：同一份提示词在新旧口径下的指纹不同 —— v5 那份是 `6c310174bad22359` →
`e8c8a50aabe6c9ab`，留档 README 已注明，历史值不要直接跟 v8 起的报告头比。）

→ ⑧ 与 ⑥ 合成本项目对「该改提示词还是改代码」的判据：
**能写成确定性规则的，一律别塞进提示词**（⑥ 是反例，⑧ 是正例，中间差 17.4 pp）。

**⑨ 「改题 = 改标尺」，要两全就另立一道对照 —— 不动主尺。**
包 12 把 T13 的归因从「列定位不唯一」纠成「**「件」的口语歧义**」后，剩下一个可判定的问题
——「**同语义说全了，能不能过？**」。回答它的做法有三种，选了**第三种**：

| | 做法 | 代价 |
|---|---|---|
| ① | 就这么留红 | 少 1 题，但保留「口语省略」这个测点 |
| ② | **按作者的改写改掉 T13** | 🔴 **改题 = 改标尺**：40 题的十轮历史全部断代，「口语」测点也丢了 |
| ③ | ✅ **保留原题 + 另立一道「无歧义版」当对照** | 分母口径要**分开**（所以主尺一字不动，对照单独成节） |

落点是一个**独立的附加题集** `eval/对照题集-1题.json`（编号 `C13`，与 T13 **同语义、同金标准 SQL**），
用 `--加对照` 挂上跑。**关键设计**：对照题的记录带 `对照: True`，汇总时**先按这个标记切分**——
主尺照旧 40 题（历史可比），对照单独报一节，**绝不并入执行准确率**。

**v9 的结果同时给出了两条结论**：

1. **主尺 v8 → v9 逐题差异 `0/40`** —— 加对照题**没有扰动主尺**。这是「它敢叫附加」的机器凭证，
   不是「我觉得应该没影响」。
2. **C13 = ✅，且 `归一提示 = []`** —— 判据 `{"基础查询": "求和", "目标": "抽检数量"}`，
   逐格一致，**没有任何系统干预**（提示列表为空 = 规则没插手、模型自己答对）。
   → 同语义**说全**就能过 ⟹ **T13 的失败是「问法歧义」，不是模型不懂求和，更与「列」无关**。

这条把包 12 的纠错从「5 句最小对照（过程证据）」升级成「**独立同金标准的题（结果证据）**」：
两次证据方向一致，且这次是**跑完整评测链路**（含 SQL 渲染 + 结果集比对）拿到的。

→ 方法论：**要证「某题失败是问法问题」，最干净的做法不是改题、也不是争论，而是「另立一道同金标准的对照」。**
主尺不动 = 历史不断代；对照单列 = 结论可判定。

**纪律 1 · 评测必须用「证明过不受限」的角色。**
`/ask` 不带角色 → 服务端默认「操作员」→ B-5 行级遮蔽 + B-3 脱敏**同时生效**。实测后果：
`T17「各家仓库的库存加起来有多少？」→ 实测 1 行 vs 基准 3 行`（权限把两个仓库遮掉了）、
`T19「上月哪家供应商不良绿最高」→ 实测 (***, 7.66)`（脱敏把列掩成了星号）。
**这两条都不是模型的错**，而「少了两行」这个现象，在「模型不会分组」与「权限不让看」下**长得一模一样** ——
判据分不开，就会跑去改提示词（方向错到底）。
→ `评测-盲测集.py` 现在起服务后先跑 `确认全权()`（走 `/spec`，不调模型）：**证明不了就中止**，
角色同时写进报告头。

**纪律 2 · 敏感列名必须与语义层「实际会产出的列名」对得上。**
B-3 原来的四列（采购单价 / 标准单价 / 订单金额 / 供应商评级）业务上都该限，
但**语义层当前一个都产不出来**（五个指标的渲染列名只有 供应商 / 物料 / 物料类别 / 月份 /
仓库名称 / 不良率 / 准时率 / 水位百分比 / 达成率 / 采购金额）。后果是一条**永不触发的钩子**：
`自检-B档.py` 里那条「HTTP 上验脱敏」的断言**从写下起就不可能通过**（它期望一个不存在的列被掩码），
界面上「脱敏生效」也**永远演示不出来**。
→ 补上「采购金额」（按供应商汇总的采购额可反推份额与议价结构，且它是真会出现在结果里的列）；
→ 新增 `脱敏.挂空清单(定义)`，`/health?deep=1` 直接报「哪些敏感列永远不会出现」。

**纪律 3 · 子串匹配不能做「反向包含」。**
`是敏感列` 原来写成 `敏 in 名 or 名 in 敏`。反向那一半让**短列名命中所有以它为前缀的敏感列**：
`是敏感列("供应商")` 命中「供应商**评级**」→ **供应商名整列被掩成 `***`**（T19 现场）。
反向匹配还带**歧义**：`"单价" in "采购单价"` 与 `"单价" in "标准单价"` 同时成立，
取第一个 = 用了一组可能不对的「可见角色」。
→ 只保留正向包含；要支持「列名更短」就**显式写别名**（映射要写下来，不要算出来）。
→ ⚠️ 更要紧的是：**自检里原来有两条断言把这个错钉成了期望行为**（「短列名也命中」），
所以自检全绿而真机上整列变星号。**判据写歪了，全绿只证明「实现与判据一致」，不证明功能对。**

**v2 提示词本身的失分形态**（排掉上面两条污染之后仍然存在的）：

| 形态 | 例子 | 说明 |
|---|---|---|
| **维度丢失** ×4 | T01/T02/T11/T24「最高的三家厂商」→ `{"指标":…,"排序":…,"限制":3,"维度":[]}` | 排序与限制都在，**分组维度没了** → 答成「全公司一个数」。判据显示「缺一列」，实际是答的不是那件事 |
| **瞎加限制** ×2 | T04/T21「各厂商的采购额排名？」→ 自己加了 `限制 10` | 问句里没有「前 10」。v1 不加，这一版加了 —— 「排序 → 顺带加限制」被学过头 |
| **计数/枚举混淆** | T08「库房都有哪些？」→ `{"基础查询":"计数","目标":"库存记录"}` | 本该枚举仓库名；v1 是对的 |
| **时间序列被排序** | T09「最近半年的走向」→ 加了 `排序:降序` | 走向题排序会打乱横轴 |

→ 这四类都是**「修一条、坏另一条」**：v2 的提示词是按 v1 的失败题逐条加的
（第 9/10/11 条甚至直接引用了 T01/T02/T13/T17），它修好了 T16（硬答→澄清）与 T05/T15 的场景触发，
却把「维度」「限制」的既有行为带偏了。**这是「照着失败题改提示词」的固有代价** ——
也正是为什么这一版的数字必须与「没改过的那版」**并排看**，而不是单独报一个高分。
⚠️ 括号里那句「直接引用了 T01/T02/T13/T17」，当时只当作「说明书要写具体一点」，
**包 9 才发现它是污染源** —— 见纪律 4。这也正是为什么它值得单独立一条纪律。

**纪律 4 · 改完提示词，先查「评测题有没有被抄进提示词」，再跑评测。**
包 9 修「问『最高的哪家』丢维度」时新加的规则 12 举了三个例子，其中
`「八月份 IQC 不良率最高的是哪家？」` 与 `「上月不良率头名是谁？」` 和盲测
**T02 / T11 一字不差**，`「上个月不合格率最高的三家厂商是谁？」` 比 T01 只少一个「的」
—— **等于照着答案出题**。v3 因此跑到 **87.0%**（比预期 78.3% 还多 3 题），看着像大涨。
而且**不是本轮才有的**：规则 11 的「实测记录」里嵌着 T01 的原句、规则 10 里嵌着 T05（都是包 8 留的），
**人眼审提示词筛不干净这种**。
→ 新增 `scripts/诊断-提示词污染.py`，判据三层：题面整句命中 → 🔴；
去掉「的」后命中（中文里多一个「的」不构成改写）→ 🔴；最长公共子串 ≥ 8 字 → ⚠️ 人工确认
（可能是**合法词表**：「厂商 / 供货商」这类「X 是 Y 的口语说法」本来就必须写进提示词，
属于词汇知识、能泛化到别的指标）。退出码 0 = 干净 ｜ 3 = 有污染。
**它必须能自证**：拿 v3 那份留档跑，要报出 4 条、退出码 3 —— 否则「全绿」只说明没检查。
→ 提示词按轮次留档在 `logs/提示词留档/`（`v2全权` / `v3` / `v4` / `v5` / `v6` + v2-全权、v6 的**源码副本**），
目录里另有 `README.md` 写清「哪一版是哪一版、指纹多少」——
**版本本身要有唯一可查的来源，不能靠时间戳倒推**（纪律 6 的延伸）。

**纪律 5 · 「跑完了」与「没跑完」必须在报告里一眼可区分。**
v5 首跑撞上生成端卡死（`/slots` 拿不到锁、CPU 增量 0、4 条 `CLOSE_WAIT`；起手探活也是超时），
脚本按设计中断并**照实记录** —— 但报告头写的是 `执行准确率 83.3%（10/12）`，
**分母是已跑的 12 题**，与跑满 23 题的轮次**长得一模一样**；`总用时 42.1 s` 也是假的：
异常题没记 `耗时秒`，被静默当 0，而那一题实际等了 **180 s**（`请求()` 的默认超时）。
→ 报告头现在打 `⚠️ 未跑完：已跑 12/40 题` + 中断原因，结论表每行标
`🔴 只跑了 12/23 题，未跑满`；`判一题` 的异常分支也记耗时；请求异常后**当场探活止损**
（不再等到批边界，白跑一整批）。
→ 同一条纪律的另一面：**超时值本身就是「掐客户端」**。那次 180 s 超时把 slot 卡死了
（与「外层 `timeout` 掐评测」是同一条因果链，已两次实测复现），
所以**给客户端的超时应当大于模型最坏耗时** —— 宁可慢，也不要制造卡死，因为卡死要人工重启。

**纪律 6 · 三轮对照里必须交代「哪一版是什么」——而这一条没做到满分。**
`v1` 报告**没有提示词指纹行**（跑在加指纹功能之前），`意图解析.py` 也**没有 git 历史**
（ChatBI 目录不是 git 仓库），所以「v1 用的就是提示词 A」是**间接推断**，不是实测：
① 报告时间 15:51 早于 `意图解析.py` 的 mtime 16:20；② v1 报告里没有指纹行、v2/v2-全权 都有；
③ 失败形态结构不同（v1 的 T01 是「口径错：行数对、取值错」，v2 系是「缺列供应商」）。
→ **要真做严格对照，就得在改提示词之前先把指纹和文件快照落下来** ——
这也是「唯一事实来源」那条纪律的延伸：**版本本身也要有唯一可查的来源，不能靠时间戳倒推。**

**B 档的统一设计取向**：三项都是「**在正确的位置做**，而不是在显眼的位置做」——
脱敏在**结果层**（改 SQL 会让口径跟着变）、行级在 **SQL 层**（结果层过滤会让聚合/排名/总数的分母含看不见的行）、
身份在**入口层**（`角色 is None` = 内部直调，与 `权限.检查` / `行级.应用` 同一条边界）。
位置错了功能"看起来一样是好的"—— 所以每一项都配了反例判据。

**包 8 期间额外沉淀的一个排错判据（`scripts/诊断-生成端卡死.py`）**：
模型服务出现过「`/health` `/props` `/v1/models` 全部 200 且 0.00 s，但**任何生成永不返回**」。
现场是：**唯一 slot 被一个中途断开的客户端占死**（端口上留下 `CLOSE_WAIT`），
进程 68 个线程全部 `Wait`、5 秒 CPU 增量 0。
三步判（不用看任何日志）：**① 免锁路径是否秒回 → ② `/slots` 是否拿不到锁 → ③ CPU 增量是否为 0**。

**这条因果链已经实测复现过（不再是推断）**：一次盲测跑到 120 s 被外层 `timeout` 发 `SIGTERM` 掐掉，
**紧随其后**的探活就拿到 `CLOSE_WAIT` 1 条 + `/slots` 6 s 拿不到锁 + CPU 增量 0.02 s。
⚠️ **推论：跑任何会调模型的长任务，不要让外层超时去掐它。**
本项目的 Bash 工具默认 120 s 超时**自己就会发 `SIGTERM`** ——
所以盲测 / 自检 / 评测这类任务一律走**后台任务**，不要用 `timeout` 包一层
（包一层 = 亲手制造一次 slot 卡死）。
处置从「手工去 APP 里点停止 → 启动」升级成一条命令：`scripts/重启-生成端.py`。
它**只杀不代起** —— 杀掉引擎后由 **APP 自带的看门狗**（`service_watchdog_loop`，
每 5 s 一轮 `child.try_wait()`）调 `start_service_core()` 把它拉回来；
进程的主自始至终是 APP，界面状态也跟着同步（APP 日志里 `watchdog: restart succeeded` 已实测命中：
1.5~3 s 新进程就位，全程约 5 s）。
🔴 **不要自己 spawn 一个 llama-server 顶上** —— 那会出现「两个主」，APP 的界面状态、
下次 `recover_service()` 的 reattach 判断、显存账本全对不上（`启动-服务.py` 立过的规矩）。
🔴 **「重启 Local-AI APP」不是解法**：APP 启动时 `recover_service()` 只要端口健康就直接 reattach
（`A healthy port means the old process is still serving`），而**卡死态的端口恰恰是活的**
（`/v1/models` 秒回）→ 重启 APP 很可能把那个坏引擎**原样接管回来**。而且全仓库**没有任何**
退出时清理子进程的代码（无 `Drop`、无 `RunEvent::Exit`）→ 关掉 APP 后引擎变孤儿，继续占着 8000 和显存。
所以正确顺序只能是：**先杀掉引擎，再让它被重新拉起**。
两条工程纪律：**给客户端的超时要长于模型最坏耗时**（砍一次请求可能卡死一次引擎）；
**生成端可以开 `--parallel 2`**（向量/重排必须为 1，生成端没必要）。
🔴 「服务没起」与「服务活着但 slot 卡死」在「问数超时」这个现象上一模一样，
所以 `自检-问数服务.py` 第六节把这两种情况**分开报**，不合并成一个「生成端不可达」。

### 已知边界

- 页面（`web/index.html`）**目前不传角色与令牌**，走的是「不传身份 → 默认角色（操作员）」这条路。
  服务端 B-4/B-5 已经就位（`/catalog` 已经把 角色 / 敏感列 / 行级 三份清单吐出来了），
  页面上还没把它们展示成可切换的 UI —— **这是 B 档剩下的最后一段前端接线**。
- **图表色与页面色板是两份**：`图表色[0]/[1]/[4]` 取自 `:root` 的 `--accent` / `--ok` / `--err`，
  改主色要连它一起改（探针第八节会回来对这三个值）。
- **`vendor/echarts.min.js` 与页面一样是启动时读进内存的** → 换版本同样得重启服务。
- 首页 6 条示例 chips 里**只有「各仓库的库存总量分别是多少？」天然出图**
  （其余是 1 行结果或纯文本列 → 按规则不出图）。想让图表被看见，得先点到它 ——
  这不是 bug，是「示例问题没考虑演示动线」，记在这里。
- **探针里的「图表」与「色板」两节编号**：原第七节保持不动，新增的 A-2/A-3 节插在中间，
  原来的「八、三页共用 CSS 变量」顺延为**第九节** —— 引用节号的地方（含本节）都要跟着改。
- **A-2 解读的防编造是「宁可不说」**：把 `7.66` 说成 `7.7` 会被判成编造（`7.7` 这个数在结果里不存在）。
  这是有意的偏严（一句含凭空数字的解读比没有解读危害大得多），
  但代价是「模型做了合理四舍五入」时会被丢弃 —— **要不要放宽容差，等有了真实模型样本再定**，
  现在不改（改了就把「编造」的判据放空了）。
- **B-2 语义缓存的 key 不含角色**：同一问句在不同角色下会命中同一条意图。
  这在当前设计里**是对的**（意图解析阶段不接触数据，行级 / 脱敏都在它下游执行），
  但如果将来把「角色影响意图」做进去（例如操作员问「全部供应商」自动限定），key 必须加上角色。
- **`--parallel 1` 的取舍**：向量（8092）/ 重排（8085）服务**必须** 1（多槽会让浮点结果不可复现，
  见作品一）；但**生成端（8000）没必要** —— 开 2 可以避免「一个卡死的 slot 拖垮全部请求」。
  当前仍是 1，所以才有 `scripts/诊断-生成端卡死.py`（诊断）+ `scripts/重启-生成端.py`（一键恢复）这一对补丁。
- **`chatbi_base_url` 的三处一致**（`utils/chatbi.ts` / `settings.rs` / `编排服务.py` 的 `默认端口`）
  靠**注释 + 约定**维持，没有自动化护栏 —— 与 `kb_base_url` 同样的已知弱点。
- **三页共用同一套视觉语言**：`web/index.html`（8095）· `web/助手.html`（8096）·
  作品一 `RAG-Embedding/web/index.html`（8092，**基准**）。同一套 CSS 变量、同一个版式骨架
  （居中 hero + 状态徽标 → 大输入框 + 圆形发送键 → 居中结果卡 → 页脚）。
  🔴 但那是**复制**不是共享（两个仓库、没有构建期变量抽取）→ **改色板要三处一起改**。
  判据：`scripts/探针-问数页.js` 第九节逐项断言三页的 `:root` 变量一致。
- **页面是启动时读进内存的**（`处理器.页面内容 = 句柄.read()`）→ **改完页面必须重启对应服务**
  才生效；只刷新浏览器没用。重启要用**后台任务**方式起（见根 `MEMORY.md` §二）。
- 启动器**只管作品二自己的两个端口**；跨仓库的启动顺序（8000 → 8085/8092 → 8095/8096）
  由 `../AI大模型应用开发实战训练营/整合演示/一键启动.py` 统一编排。
  🔴 那个脚本**同样是「委派」不是「代起」**：它只调本仓库的启动器，
  **不复制本仓库的任何服务命令**（一个进程只能有一个主）—— 见该目录 README 第一节。

**包 10 挖出的两个方法论问题**：

  → **「机制说得通」不能代替「噪声测过」**。判「某题翻转」之前，先花一次跑批的代价
    测出**同版本的噪声**；否则要么把真回归当噪声放过，要么反过来把噪声当成成果邀功。
- **纠错兜底的锚点必须是「问句语义」，不能是「产物内部自洽」。** v7 证明了包 10 的

**包 13 挖出的两个方法论问题**：

- **要证「某题失败是问法问题」，最干净的做法是「另立一道同金标准的对照」，而不是改题。**

  **附加物必须自证没扰动主体** —— v9 的「主尺 v8 → v9 逐题差异 `0/40`」就是这个凭证，
  不是「我觉得应该没影响」。
- **同一结论要拿「过程证据 + 结果证据」两次钉。** 包 12 用 **5 句最小变量对照**（只改问句
  一个成分）证明 T13 的失败不在「选列」；包 13 用**一道独立题、跑完整评测链路**（含 SQL

  只有过程证据时，它仍是「机制说得通」（本项目最贵的那类错）。
