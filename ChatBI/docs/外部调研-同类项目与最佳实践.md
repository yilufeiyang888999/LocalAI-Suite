### 🔴 这张表本身给出了一条判据

**「没归档」不等于「在维护」。** Dataherald 的 `archived=false`，但最后提交停在 **2024-07-24** —— 靠「有没有归档标记」判断生死会漏。

**判维护状态要看 `pushed_at` 的间隔，不看 `archived`**：

| 判据 | 分辨得出什么 |
|---|---|
| `archived` | 只抓「官方主动关掉」这一种 |
| `pushed_at` 间隔 < 7 天 | 活跃 |
| `pushed_at` 间隔 < 90 天 | 在维护 |
| `pushed_at` 间隔 > 365 天 | 事实停更（无论 archived 是什么） |

**高星项目更容易被文章反复引用**，于是「搜到的」和「能用的」会是两批东西。

## 三、我们和他们：路线对照

**结论：我们这条路（模型只出意图 + 语义层拼 SQL）不是偏门，是主流里最难但也最对的那一支。**

| | 自然语言 → | 中间层 | → SQL | 谁在做 |
|---|---|---|---|---|
| **纯端到端** | 模型直接出 SQL | 无 | 模型生成 | Vanna、Dataherald、SQLBot（Prompt+RAG） |
| **语义层中间表示** | 模型出结构化意图 | **有**（口径/指标/维度治理） | 确定性程序拼 | **WrenAI（MDL）、SuperSonic（S2SQL）、我们（语义层 YAML）** |
| **逻辑表达式** | 转结构化自然语言表达式 | 有（受控逻辑模型） | 符号逻辑生成 | 北极九章（Text2Logic2SQL） |

**我们的位置**：语义层这一支里，**最简单的一档** —— 单机、单库、5 指标、3 模板。
他们那一档的规模（20+ 数据源、几百个指标、多人维护）正好对应我们 `选型决策.md` 第七节里
「指标数量到几百 / 多人维护 → 重估 D4」那条触发条件。

**所以：架构不用动，动的是规模。**

## 四、ChatBI 最佳实践（带证据强度）

> 每条标 **证据强度**：🟢 有公开评测数据支撑 / 🟡 行业共识（多家实践文章一致）/ ⚪ 观点

### ① 收益最大的是语义层，不是模型 🟢

同一套 o1-preview agent 框架在三个基准上的执行准确率（Spider 2.0 发布时的数据，ICLR 2025）：

| 基准 | 特点 | 准确率 |
|---|---|---|
| Spider 1.0 | 干净学术 Schema、单库 | **91.2%** |
| BIRD | 真实脏数据、95 个库 | **73.0%** |
| Spider 2.0 | 真实企业仓库、1000+ 列、歧义问法 | **21.3%** |

**模型一个字都没变，变的只是 Schema 的真实度。**
2026-09 的 BIRD 榜单：最好系统 82.39%，人类专家基线 92.96%（差约 10.6 pp ≈ 每十个人类能答对的，机器错一个）。

> ⚠️ **两个数字要警惕**：
> ① 有文章写「加语义层后 86~95%」——**该来源后来自己撤回了这个数字**，理由是它来自厂商自报而非受控实验。方向可信，数字不可引用。
> ② Spider 2.0-Snow 榜单最高的 96.70 分，其金标准被审计出 **66.1% 标注错误率**（2026-01 的论文）。**榜单在争议中，别拿它当目标。**

**对我们的含义**：我们已经站在语义层这一支上 —— 这个选择是对的。要防的是「拿自己的 50 题 97.5% 当行业水平」，那是**自出题自己答**。
（→ 见第五节 A-4）

### ② 失败的大头是「找表和连接」，不是写 SQL 🟢

BIRD 的错误分析（按 DIN-SQL 分类法）：**schema linking ≈ 37%，JOIN 错误 ≈ 36%** —— 合计约 73%。
**写 SQL 语法本身反而很少错。**

**对我们的含义**：我们把「找表/连接」这件事**大部分消灭了** —— 语义层里表和连接是显式声明的（对应我们踩过的「度量必需连接须显式声明」）。
我们的错误因此集中在**口径与维度归属**（已在包 1 定量：口径分母含未到料差 14.1 pp）——**这是语义层的正确位置**。

### ③ 模型只做翻译，SQL 由确定性程序拼 🟡

多家企业实践（滴滴、腾讯音乐、招商银行）与三家产品（WrenAI / SuperSonic / 北极九章）都是这个结构。
理由是这个结构的两条硬性质：

- **同一问题永远同一个 SQL**（可复现 → 评测数字才有意义）
- **幻觉无处可钻**（模型不接触表名，改不了 JOIN）

**我们的状态**：✅ 已做（`D3`），且是包 0 实测 45% → 包 4 的 97.5% 的来源。

### ④ 澄清优先于硬猜 🟢

「confidence wrong」是最贵的错误 —— 提问有歧义时，模型默认编一个**看起来合理**的答案，而不是问。
（BIRD 里 B 档问题是 0% —— 恰好证明我们包 0 的那次摸底抓到的就是这个。）

**我们的状态**：✅ 已做（包 3）。但注意区分：
**我们的澄清是「同一次提问内」的**（意图拼不齐 → 反问），**不是「跨轮」的**（→ 见第五节 A-1）。

### ⑤ 护栏放在数据库和执行层，不放在 Prompt 里 🟢

2026 企业数据就绪度调查：**76% 的组织把「护栏」列为上生产的第一障碍**。
四层护栏：**数据库层**（只读角色 / 行级安全）→ **语句层**（白名单 + 成本闸）→ **数据层**（视图层脱敏）→ **Prompt 层**（字面值参数化，绝不字符串拼接）。

**明确反模式**：「在 Prompt 里告诉模型只读」「把 PII 检测做进 Prompt」——**会静默失败**。

**我们的状态**：✅ 已做前两层（`mode=ro` / 语句白名单 / `query_only` / 超时，自检 58 全绿）。
⚠️ **缺**：按行级的权限（我们按角色分档，不做行级）、PII/敏感列脱敏（→ 第五节 B-3、B-4）。

### ⑥ 评测：执行准确率是主指标，但要防「金标准自己错」🟢

- **主指标 = 执行准确率（EX）**：比结果集，不比 SQL 字符串（写法不同但结果对，算对）。
- **金标准会错**：2026-01 的审计发现 BIRD Mini-Dev 标注错误率 52.8%、Spider 2.0-Snow 62.8%。
- **样本量决定分辨力**：我们自己在 RAG 那边吃过亏 —— 33 题时「净胜 2 题」看着像结论，扩到 60 题变成 −2 题。
- **不可答的题不能从分母剔除**（那是该方案自己的失分）。

**我们的状态**：✅ 已有「列超集容忍」「拒答率/误拒率分开」两条判据（包 4）。
⚠️ **缺**：金标准的外部性 —— 出题人和语义层作者是同一个（→ 第五节 A-4）。

### ⑦ 数据飞轮：把用户确认过的「问法 → SQL」沉淀下来 🟡

WrenAI 的 memory、Vanna 的训练数据、SuperSonic 的 Chat Memory —— 三家都有。
做法一致：**用户确认/修正过一次的问答对，成为后续 few-shot 或微调样本**。
百度那篇给的量化：某物流企业靠「记录用户修正行为 + 沉淀样本」，准确率 68% → 91%。

**对我们的状态**：⚠️ **完全没有**。我们连「用户觉得这次答得对不对」这个信号都没收（→ 第五节 A-3）。

### ⑧ 指标口径要有版本与变更解释 🟡

指标口径改动后，**历史问答和看板都要能解释差异** —— 否则用户会看到「同一个问题两个答案」而不再信任系统。
这不是技术问题，是治理问题。

**对我们的状态**：⚠️ **半个**。`指标口径定义-v1.0.yaml` 有 `version` 字段，但没有「改了口径 → 哪些历史答案会变」的机制（→ 第五节 A-5）。

### ⑨ 结果不能只有表和数字 🟡

Vanna 2.0 输出五段（进度 / SQL / 表格 / 图表 / **自然语言摘要**），WrenAI 出洞察摘要，
北极九章做「你为何看到该图表」的可解释卡片。

**对我们的状态**：✅ 表 + 图（本轮刚加 ECharts）+ SQL 可折叠。⚠️ **缺一句话解读**（→ 第五节 A-2）。

## 五、我们该改的地方（三档分层）

> 原则：**全都在现有架构内补环节，不引入外部框架**（`选型决策.md` D7 及「被否决方案」不变）。
> 判据：**不做也能演示，做了才像产品** —— 这才是该补的。

### A 档 · 建议做（收益明确、成本可控）

| # | 要补的 | 现状证据 | 为什么值得 | 成本量级 |
|---|---|---|---|---|
| **A-1** | **多轮追问** | `/ask` 入参只有 `{"问题","执行"}`，无会话 id、无历史 | 外部三家全都有 follow-up。现在问完「各仓库库存总量」，想再问「只看华南的」就得重打一遍全句 | 中（会话态 + 指代消解） |
| **A-2** | **结果一句话解读** | 全仓库搜「摘要/解读」只命中动作单据的标题，无结果解读 | 与最佳实践 ⑨ 对齐；模型已经在链路里，是**加一次调用**的事 | 低 |
| **A-3** | **用户反馈入口（✅/❌ + 纠错）** | 无任何反馈字段（搜「反馈/纠错/点赞」零命中） | 这是最佳实践 ⑦ 数据飞轮的**唯一入口**。没有它，「越用越准」是空话 | 低（审计 JSONL 已有，加字段即可） |

| **A-5** | **口径变更影响面** | `version: "1.0"` 是静态字段，无变更记录 | 改口径要能回答「哪些历史答案会变」；否则用户遇到两个答案就失信 | 中 |

- **A-3 排第二**，成本最低且有复利：它同时给 A-4 提供题目来源（用户真实问法就是最好的盲测题）。

## 六、一句话总结

**架构没走偏，缺的是闭环。**

我们和 WrenAI / SuperSonic / 北极九章 在**同一条技术路线**上（模型出意图 + 语义层拼 SQL），
而且是这条路上实现最轻的一档。差距不在架构，而在**几个还没闭合的环**：

```
提问 → 意图 → SQL → 执行 → 表/图 → 一句话解读（A-2）
  │                           ↓
  │                    ✅ 反馈（A-3）
  │                           ↓
  │                    ✅ 沉淀样本（A-3）
  │                           ↓
  │           ✅ 口径演进 → 回到语义层（A-5）
  └─ A-1 多轮追问把「提问」接成连续对话
     A-4 盲测把「我们到底站在哪」变成可复核的数字
```

**（2026-10-13）这张图上的环已全部闭合** —— A/B 档十项落地：`自检-会话.py` **58/0**、
`自检-B档.py` **78/0**、探针 **117/0**、`自检-问数服务.py` **90/0/0**。

**但 A-4 给出的结论比「闭环补上了」更重要**：
内部 50 题 **97.5%** ≠ 真实水平 —— 换一批没见过的问法（同义改写 / 口语 / 错别字）掉到 **60.9%**。
**下一步的主线不是再加功能，是扩「问法覆盖面」**（语义层别名 / 口语映射），
而 A-3 的反馈台账正是喂它的原料 —— **这才是「越用越准」真正接上的那一环。**
