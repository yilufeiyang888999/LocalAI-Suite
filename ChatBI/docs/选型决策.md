# 作品二 · ChatBI —— 选型决策文档

> **这份文档回答一个问题：为什么是这么做，而不是那么做。**
>
> 每条决策固定写四段：**选了什么** / **备选是什么** / **依据（尽量是数字，不是道理）** /
> **什么情况下这条决策该被重估**。
>
> 前三段是给评审看的，第四段是给未来的自己看的 —— 没有第四段的选型文档，
> 会在环境变化后变成「祖传规矩」。
>
> 最后更新：2026-10-13（包 7 收尾）

---

## 0. 一句话结论

> **模型只出意图，数字与单据由确定性代码产出。**

这一句话决定了下面绝大部分选型。它来自一个实测结果：**让 4B 模型直接写 SQL，
40 题里只对 45%；让它只填槽位、由语义层模板拼 SQL，同一批题对到 97.5%。**
（见 D3）

## 一、引擎与运行形态

### D1 · 推理引擎：llama.cpp + GGUF

| | |
|---|---|
| **选了** | llama.cpp `llama-server`（OpenAI 兼容 HTTP 接口）+ GGUF 量化权重 |
| **备选** | vLLM / SGLang / Ollama / TGI |
| **依据** | ① 目标形态是**端侧 / 单机私有化**（8 GB 显存笔记本能跑 4B，16 GB P100 能跑 27B）；② GGUF 量化档位细（Q3_K_XL / Q4_K_M / Q6_K / Q8_0），7B 级模型 4bit 后进 8 GB 卡仍有上下文余量；③ 上游 `llama-server` 就是 OpenAI 兼容接口，**换引擎不用改业务代码**；④ 同一个 exe 跨 Windows / Linux，后端靠 `ggml-*.dll` 切换 |
| **重估条件** | 目标从「单机」变成「多人并发服务」→ vLLM 的连续批处理是数量级的优势，llama.cpp 的槽位模型比不了。**一旦并发用户数 > 2~3，就该换。** |

> 注：本项目**明确不是** vLLM 服务端路线。选它的唯一理由是「谁用这个系统」——
> 一个车间/一个办公室的单机助手，不是给几十人用的 SaaS。

### D2 · 服务形态：独立 Python 进程 + HTTP 接口

| | |
|---|---|
| **选了** | RAG / ChatBI 各自做成**独立的本地 Python 服务**，经 HTTP 暴露；Local-AI APP 只做探活与调用 |
| **备选** | ① 直接写进 Rust（Tauri）后端；② 打成 sidecar 随 APP 一起发；③ 用 PyO3 嵌进 Rust 进程 |
| **依据** | ① **跨语言边界是有成本的**：Rust 侧要重写一遍语义层解析、SQL 拼装、BM25 检索 —— 而 Python 侧已经有实测过的实现；② **进程隔离**：Python 服务崩了，APP 还在；反之亦然（APP 重启不打断问答）；③ 业务逻辑迭代快（一天一个包），不该每次都过 Rust 编译 + `cargo test`（152 项）；④ `sqlite3` / `yaml` / `http.server` 都在标准库，**零第三方依赖**就能跑 |
| **边界铁律** | **APP 只探活与调用，不负责拉起那个进程。** APP 管模型生命周期与显存调优（换模型 / 调上下文 / 卸显存），Python 管业务逻辑。**一个进程只能有一个主** —— 两边都写「起服务」的命令，就会出现「谁的版本对」这类查不清的问题 |
| **重估条件** | 如果要发给**零技术背景**的用户一键安装 → sidecar 打包（用户不该知道要开终端）。那一步做的是「分发包」，不是「改架构」 |

## 二、Text-to-SQL 的架构定案

### D3 · 模型只出意图，SQL 由语义层模板拼（**本作品最重要的一条**）

| | |
|---|---|
| **选了** | 模型负责把自然语言**映射成结构化意图**（指标 + 维度 + 过滤 + 时间），**SQL 由确定性模板拼出来** |
| **备选** | ① 模型直出 SQL（业界常见的 text-to-SQL）；② 模型出 SQL + 自动重试；③ 微调一个专用的 text-to-SQL 模型 |
| **依据** | 包 0 摸底，**同一批题、同一个模型**，按题型分档：<br>· A 档（单表简单聚合）直出 SQL **60%**<br>· B 档（多表连接 / 复杂口径）直出 **0%**<br>· C 档 **20%**<br>· D 档（本应拒答/澄清）**100%**（但那是过度作答）<br>**整体 45%**。<br>包 4（换成意图+模板）**执行准确率 97.5%（39/40）**，包 1 语义层对账 **15/15**。 |
| **关键洞察** | **B 档 0% 才是决策点。** A 档 60% 会让人误以为「模型能写 SQL」；但多表连接与口径计算这类**真正影响业务数字**的题，模型全错。而这类错** SQL 是合法的、数字是长得对的** —— 最危险的一类错。 |
| **重估条件** | ① 换到明显更强的模型（如 30B+ 且专门后训练过 SQL）后，自建评测集上直出 SQL 稳定 ≥ 90%；② 且有独立的**口径校验层**能挡住「合法但口径错」。两条同时满足才有资格重估 |

### D4 · 语义层是唯一事实来源（single source of truth）

| | |
|---|---|
| **选了** | 一个 YAML（`eval/指标口径定义-v1.0.yaml`）承载：5 个指标口径 + 3 个场景 SQL 模板 + 实体别名 + 时间表达式规则 + 护栏配置 |
| **备选** | 指标口径写在 SQL 里 / 写进代码常量 / 放进数据库元数据表 |
| **依据** | 口径是**业务概念**，不是实现细节 —— 它需要被人读、被人评审、被人改。YAML 满足这三点；写进代码常量则改口径要改代码 + 重跑测试。 |
| **配套铁律** | **凡「读配置 / 抽字段」的代码，先问一句「还有第二份吗」。** 同一份数据两处定义时，改一处跑另一处**不报错、只给错报告**（本项目已因此踩过一次：评测集曾同时存在脚本硬编码与 json 两份，已统一到 `eval/题目.json`） |
| **重估条件** | 指标数量到几百个、需要多人协作维护 → 该上元数据平台（cube / dbt 之类）。**当前 5 个指标，上平台是过度工程。** |

## 三、编排层

### D5 · 一个入口，三条链路

| | |
|---|---|
| **选了** | 8096 是**用户唯一的入口**；知识问答 / 数据问数 / 动作执行三条链路在它后面分流 |
| **备选** | 三个服务三个端口，用户自己选 |
| **依据** | 三条链路的**失败模式完全不同**（见下表）。用户不该先知道自己问的是哪类问题 —— 那是系统的责任。 |

| 链路 | 典型失败 | 为什么危险 |
|---|---|---|
| 知识问答 | 检索不到 / 编造引用 | 用户会去核对引用，**可发现** |
| 数据问数 | **SQL 合法但口径错**（数字看着对） | 数字长得正常，**不可发现** |
| 动作执行 | 单据数字与依据不一致 | **单子要发出去**，不可撤回 |

> **反过来**：正因为失败模式不同，**代码里也必须分开**（`编排.py` 里三条链路各自独立函数），
> 不能在 `send()` 里塞 `if` 一路写到底。合入口 ≠ 合实现。

### D6 · 路由：确定性优先 + 模型兜底

| | |
|---|---|
| **选了** | 七条规则先判（元问题短语 / 数据词表 / 制度词 / 动作动词 / 时间词 …）；都不命中才问模型三选一；**兜底必须留痕**（应答标 `路由.依据 = 确定性 \| 模型 \| 默认 \| 强制`） |
| **备选** | 全交给模型分类 |
| **依据** | **模型分类的答案不可复现。** 包 4 实测：同一提示词、同一请求体，开 / 关生成端前缀缓存会翻到另一个分支（根因：前缀缓存复用多少取决于上一条请求 → 预填充批组成变化 → 浮点路径不同 → 近 tie 的 token 翻分支）。**路由一旦不可复现，所有评测数字都失去意义。** |
| **附带收益** | 数据词表（表名 / 指标 / 维度 / 别名，**105 个词，由语义层自动收集**）命中即路由，**新增指标不用改路由** |
| **重估条件** | 规则表膨胀到维护不动（比如超过 50 条且有互相冲突）→ 该考虑「规则 + 小分类模型」的混合。当前 7 条规则 + 105 词自动收集，成本还很低 |

### D7 · 手写 ReAct，只用在动作链路

| | |
|---|---|
| **选了** | 动作链路手写 Thought → Action → Observation 循环，**最大步数 = 4**；知识 / 数据链路**单步委派**，不进循环 |
| **备选** | ① 引 LangChain / LlamaIndex 的 agent 框架；② 三条链路都走 ReAct |
| **依据** | ① **只有动作链路需要多步** —— 它需要「依据」才动手（查数据 → 判切题 → 生成），知识与数据链路是「一问一答」；② **框架会把关键路径藏起来**：本项目最贵的教训都是「判据自己出错 / 表现≠状态」，而框架的抽象层正好是这类问题的高发区。手写 40 行循环，每一步都能打日志、能断言、能单测；③ **预算必须按最坏路径给**：设成 3 的实测后果是「退回重查」把预算挤光，**最后什么都没交给用户** —— 护栏没错，但它把任务挤死了 |
| **重估条件** | 工具数量涨到十几个、或需要跨会话的长期规划 → 框架的价值才开始超过它的抽象成本 |

## 四、动作层（写动作最危险，规矩最多）

### D8 · 单据正文一律模板拼，绝不调模型

| | |
|---|---|
| **选了** | 补货申请 / 质量整改通知的**正文**由模板 + 依据数据拼出；模型只负责选动作、填参数 |
| **备选** | 让模型根据依据「起草」单据 |
| **判据** | **同一依据两次生成的正文逐字节相同**（幂等）。调模型的写法过不了这条 |
| **依据** | 单据是要发出去的公文。模型的措辞不稳定 = 同一批数据两次生成两份不同的通知，业务上无法接受；而且模型会把依据里没有的话写进去（编造） |

### D9 · 业务库永远只读，产物只写 `outbox/`

| | |
|---|---|
| **选了** | 三道锁：SQLite `mode=ro` 打开 / 语句白名单 + 黑名单 / `query_only` + 超时；产物一律写 `outbox/` 目录 |
| **依据** | 「只读」不能靠自觉 —— 必须由连接层强制。三道锁是**互相独立**的，任何一道单独失效都不致命 |
| **判据设计** | 护栏自检必须**双侧**：**必拒 12 + 必放 9**。只测拒会把「一律拒绝」当通过；只测放会把「一律放行」当通过 |

### D10 · 依据切题护栏

| | |
|---|---|
| **选了** | 动作表声明「要明细」；生成前**按下游应答里的 `意图.基础查询` 判定**（计数/枚举或单值 → 不切题）→ **退回重查一次** |
| **依据** | 真的出现过一张「**正文数字都对、但依据不支撑它**」的补货申请单。**这类错不报错、也不违反任何已有判据** —— 缺参数会报错、越界会报错，这个不会 |
| **踩过的坑** | 第一版判据打算匹配列名「物料名称」，结果实际列名 `["物料数"]` **含「物料」子串** → 误判切题（自检当场抓出）。**信息已经在了（意图），不要再造一个近似判据** |
| **取舍** | 最后一版选「**生成 + 显式警告**」而不是「拒绝产出」——**给一份看起来正常的废单据，比说「没生成」更危险**，所以必须显式标注，不能沉默产出 |

### D11 · 权限与审计收在 `动作.调用()` 一个关口

| | |
|---|---|
| **选了** | 权限判定与审计落盘都写在 `动作.调用()` 里 —— 它是所有动作的唯一入口 |
| **备选** | 权限在编排层判 / 审计在服务层记（两处） |
| **依据** | 收在一个关口 = **拿到这个函数就绕不过去**。分成两处则每加一个新调用点都要记得手动补，**漏一处不报错、只漏记**。两个关注点（谁能做 / 做了什么）放在同一个必经关口，是它们唯一的共同点 |

### D12 · 角色按「对外程度」分档，不按「职级」分

| | |
|---|---|
| **选了** | 操作员（只读留痕）/ 主管（+ 内部申请）/ 管理员（+ 对外发文） |
| **备选** | 按职级（专员 / 经理 / 总监）或按 RBAC 的「角色-权限」表 |
| **依据** | **职级是组织问题，对外程度才是风险问题。** 三个动作刚好构成「只读 / 对内 / 对外」三档，每档多一份「这份东西会不会流到公司外面」的风险。按职级分会出现「总监能发对外函但不管供应商」这种无法映射的格子 |
| **默认值** | HTTP 入口不传角色时 = **操作员**（`权限.默认角色`）。**默认放行是最常见的权限事故形态** —— 测试期没人传角色，看着一切正常 |

### D13 · 越权 = 硬拒 + HTTP 403 + 给出路

| | |
|---|---|
| **选了** | 越权时：不生成产物、不落盘、**不静默降级**、不换动作重试；HTTP 回 **403**；拒绝理由里写清「需要哪个角色」 |
| **备选** | ① 满足于「返回一个错误字段」；② 越权时降级成只读动作 |
| **依据** | ① **把「发整改通知」悄悄改成「查一下数据」比直接拒绝更危险** —— 用户以为自己的意图被执行了；② **状态码本身就得说明「你被拒了」**：「读 body 看有没有被拒」这种判据，漏写一处就静默当成功；③ **拒绝要给出路**（与包 3 的拒答同一条纪律）—— 否则用户下一步只能来问人 |

### D14 · 审计存 JSONL，不存数据库

| | |
|---|---|
| **选了** | 每天一个 `logs/审计-YYYYMMDD.jsonl`，append-only，一行一条 JSON |
| **备选** | ① SQLite 表；② 结构化日志（logging handler）；③ 可观测后端（Loki / ES） |
| **依据** | ① **append 即持久**，没有事务、没有并发写锁 —— 审计最怕的就是「因为写审计失败而影响业务」（所以 `记()` **永不抛异常**，写失败只降级为 stderr 一行）；② **零依赖**，标准库 `json` + `open`；③ **坏行跳过而不是崩** —— 审计文件可能被人工编辑；④ 人可读、`grep` 可查，出问题现场就能看 |
| **关键字段** | 除常规的角色/动作/参数摘要/落盘/被拒理由外，**必带 `依据切题`** |
| **为什么必带** | 白名单（D11）只防「不许做的事」；**留痕才防「做了但做错的事」**（D10 那张单子就是「谁都没违规，但结果错了」） |
| **重估条件** | 审计量到每天十万级、或需要跨机聚合查询 → 该进数据库 / 可观测后端。单机单用户场景下，JSONL 的简单性 > 数据库的查询能力 |

## 五、被否决的方案一览

| 方案 | 为什么否 | 什么条件下会重新考虑 |
|---|---|---|
| 模型直出 SQL | B 档 0%，错的是「数字看着对」的那类（D3） | 强模型 + 独立口径校验层同时到位 |
| 把业务逻辑写进 Rust | 跨语言边界要重写一遍已验证的实现（D2） | 需要单文件分发给非技术用户 → 那是打包问题 |
| sidecar 随 APP 分发 | 当前阶段迭代快，打包会拖慢每次改动 | 进入「交付给用户」阶段 |
| 引 Agent 框架 | 关键路径会被抽象层藏起来（D7） | 工具数 > 10 或需要跨会话规划 |
| 全交给模型做路由 | 分类不可复现 → 评测数字失效（D6） | 找到能稳定复现的分类方式 |
| 越权时降级为只读 | 用户会以为意图执行了（D13） | —— 不重估，这是价值判断 |
| 审计写 SQLite | 为审计引入事务与锁，违背「审计不影响业务」 | 需要跨机聚合 |
| 按职级分角色 | 职级与「对外风险」无法一一映射（D12） | 组织本身按对外权限设岗 |

## 六、已知取舍（诚实标注，不是遗漏）

| # | 取舍 | 说明 |
|---|---|---|
| 1 | **角色是调用方自填的标签，不是认证结果** | 真实部署要接 SSO / 网关注入。本项目只做「有这道关口 + 有留痕」，身份认证属部署范畴 |
| 2 | **单一角色，无继承、无并集** | 演讲够用。真实组织要加，只需扩展 `权限.角色表` |
| 3 | **权限只管动作链路** | 知识 / 数据链路是只读，不需要白名单（但审计仍覆盖） |
| 4 | **评测 / 自检必须 `CHATBI_NO_PROMPT_CACHE=1`** | 生成端前缀缓存会翻近 tie 的答案 → 数字不可复现。生产默认开（首 token 快 ~2 倍），评测关掉 |
| 5 | **下游服务的环境变量管不到** | 编排层控不了 8092 / 8095 进程的环境，它们要各自带 `CHATBI_NO_PROMPT_CACHE=1` 启动 |
| 6 | **`角色=None` = 内部直调** | 脚本 / 自检 / 单测不启用权限检查，但审计里记成「（内部）」—— 显式边界，不是静默放行 |

- **本文档** 回答「**为什么这么做、什么时候该改**」（决策记录，按决策组织）。

同一件事在两个文档里出现是**有意的**：README 里的数字是取证，本文档里的数字是论据。
若两者冲突，**以 README 的实测数字为准**（本文档的结论是那些数字推出来的）。
