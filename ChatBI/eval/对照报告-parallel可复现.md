# 作品二 · `--parallel` 对照报告（#200 / #201）

> 2026-10-17 ｜ 引擎：`llama-server-cuda.exe` ｜ 模型：`base-Q4_K_M.gguf` 裸基座 ｜ 提示词：精简（`ecb40bc1`）
> 产物：`盲测结果-40题-{可复现-A1,可复现-A2,parallel2}.json`、`并发对照-题数20-并发2.json`

## 一、结论（三句话）

1. **`--parallel 1` 连跑两次，40 题逐题一致**（意图 / SQL / 解读 / 结果 / 分类全同）—— 该配置可复现。
2. **`--parallel 2` 的配置本身不改变输出**：串行发请求时，40 题与 parallel=1 逐题一致（因为串行永远只用 1 个槽，这是**平凡结论**）。
3. **真并发（2 路同时发）会改变输出**：20 题文本 **20/20** 不一致、抽出意图 JSON **18/20** 不一致；且已排除 KV 截断 —— 原因只能是多序列同批前向的浮点路径差异。

## 二、串行可复现（#200）

| 轮次 | 结果集 | 处置 | 说明 |
|---|---|---|---|
| A1 | 6/23 = 26.1% | 17/17 = 100% | 同服务第 1 遍 |
| A2 | 6/23 = 26.1% | 17/17 = 100% | 同服务第 2 遍 |

逐题 diff：**40 题全部一致**（`可复现性-parallel1-连跑两次.md`）。

> 附带结清一个旧疑点：先前「完整提示词 21.7% vs 历史 26.1%」差的 1 题，**不是噪声**，是**提示词口径不同**（完整 vs 精简）。同口径下今天与历史都是 26.1%（6/23），分子分母逐位相同。

## 三、只换 parallel 这一个变量（#201）

起服务时刻意把总 ctx 提到 16384，使**每槽仍是 8192**（与 parallel=1 时相同）：

```
/props 回读：total_slots=2 ｜ n_ctx=8192（每槽）｜ model=base-Q4_K_M.gguf ｜ adapters=[]
显存：6588 MiB / 8151 MiB
```

串行跑 40 题：6/23 = 26.1%，**与 parallel=1 逐题一致**（`可复现性-parallel1-vs-parallel2.md`）。

**这一轮的价值在于限定范围**：它说明「配置 parallel=2」本身无害 —— 危险只在**真的并发**时出现。如果不做这一轮，很容易把「并发不安全」误写成「parallel=2 不能用」。

## 四、真并发会改输出（关键实验）

`scripts/对照-并发可复现.py` 三轮：串行第 1 遍 → 串行第 2 遍 → 并发 2 路。

| 对照 | 不一致题数 | 结论 |
|---|---|---|
| 一、串行 1 vs 串行 2 | **0 / 20** | 噪声下限 = 0，串行确定性成立 |
| 二、串行 vs 并发（文本逐字） | **20 / 20** | 并发改变文本 |
| 三、串行 vs 并发（抽出的意图 JSON） | **18 / 20** | **并发改变业务判断**，不只是措辞 |

对照一的作用是**归因**：没有它，20/20 的差异既可能来自并发、也可能来自引擎本来就不确定。串行两遍 0 差异 ⇒ 差异可归因于并发。

### 已排除的替代解释：KV 截断

| 检查 | 结果 |
|---|---|
| `truncated = 1` 出现次数 | **0** |
| `truncated = 0` 出现次数 | 142 |
| 最大 `n_tokens` | **1730**（每槽上限 8192，占用 21%） |

所以不是「上下文不够、prompt 被截断」，而是多序列同批前向的归约顺序变了。

### 典型差异（T02）

同一道题、同一提示词，两次抽出的 JSON **结构都不同**：

- 串行：`{"基础查询": {"维度": ["供应商"], "过滤": [{"值": "八月份", "字段": "供应商名称", "运算符": "模糊"}]}, "指标": "来料不良率"}`
- 并发：`{"参数": {"时间": "上月", "阈值": ""}, "可选槽位": {"排序": {...}, "过滤": [{"值": "东莞精诚", ...}]}, ...}`

（模型输出里含思维链与示例 JSON，`抽JSON` 取第一个可解析块 —— 并发下连「第一个示例」都变了，可见影响之深。）

## 五、业务含义与处置

1. **评测必须串行 + `--parallel 1`**：本轮所有评测都满足；`评测-盲测集.py` 是串行的，所以它的数字不受此影响。
2. **多用户并发时，「同一问题两次问可能得到不同答案」是引擎层事实，不是 bug**。对问数场景的含义：只要最终 SQL 命中同一语义就行；若两次 SQL 不同，属产品层要处理的问题（可用语义缓存把首答固定下来 —— 现有 `意图缓存` 正好是这个作用）。
3. 这与作品一「向量/重排服务 `--parallel` 必须为 1」是同一族：**只要下游要可复现（比对、缓存、审计），`--parallel` 就必须是 1**。区别是生成端的影响更隐蔽 —— 它不报错，只是换了说法。

## 六、诚实标注

1. 并发轮只测了 **20 题**（1 题 = 5pp），够判「一致/不一致」，不够给「不一致率」的精确值。
2. 只测了 **2 路**。4 路、8 路未测，影响方向预计相同但幅度未知。
3. 未定位到具体是哪一层浮点差异（cublas 归约 / flash-attn 分块 / batch padding 都可能）。**机理未查明，现象已复现**。
4. 「18/20 意图不一致」中，有一部分源于「模型输出了多个 JSON 块、取第一个」的抽取策略 —— 该策略本身对并发敏感。这是判据的已知脆弱点，不是新发现的缺陷。
