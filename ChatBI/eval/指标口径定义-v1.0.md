## 一、这份文件存在的理由（有实测数字）

包 0（`eval/摸底报告.md`）拿本地 4B 模型**裸直出 SQL** 跑了 20 题：**只过 9 题（45%）**。
其中 B 档（条件过滤 + 分组聚合）**0/5**。

11 次失败里，**9 次不是"模型不会写 SQL"，而是"模型不懂业务口径"**：

| 失败形态 | 条数 | 长什么样 |
|---|---|---|
| 口径错 | 3 | 对每行比率求平均、拿单仓库库存比安全库存、拿下单日期当到料日期 |
| 语法错（缺表前缀） | 3 | `ambiguous column name: 供应商编码` —— 它知道要 JOIN，但 SELECT 里写了裸列名 |
| 时间口径错 | 1 | 把「上月」算成了 **2026 年 5 月**（基准应是 2026-08） |
| 实体名精确匹配 | 1 | `供应商名称 = '东莞精诚'` → 库里是全称，**返回 0 行，不报错** |

**结论：错误集中在"口径"而不是"语法"。** 所以分工这么定 ——

```
模型只干一件事：自然语言 → { 指标, 维度, 过滤, 时间, 排序, 限制 }
本文件干活      ：{ 上面那个结构 } → SQL（口径、时间区间、表前缀、别名全由定义决定）
```

模型**不碰 SQL 语法，也不碰口径**。例（B09「宁波恒力的准时交付率是多少」）：

```json
{"指标": "准时交付率",
 "过滤": [{"字段": "供应商名称", "运算符": "模糊", "值": "宁波恒力"}]}
```
```sql
SELECT ROUND(SUM(CASE WHEN i.到料日期 <= p.约定交期 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) AS 准时率
FROM 采购订单 p
JOIN 到料检验 i ON i.采购订单号 = p.采购订单号      -- ← 这句是关键，模型 90% 会漏
JOIN 供应商 s ON s.供应商编码 = p.供应商编码
WHERE s.供应商名称 LIKE '%宁波恒力%'                -- ← 模糊匹配，精确匹配会返回 0 行
ORDER BY 准时率 ASC
```

**答案：62.1%（分母 58 张已到料订单）** —— 这是全库准时率最差的一家。

## 二、时间基准（这条不先定死，后面全错）

| 项 | 值 | 说明 |
|---|---|---|
| 锚点 | **2026-09-22** | 取**数据截止日**，不取真实当日 |
| 本月 | 2026-09（不完整，**不建议**作演示基准） | |
| **上月** | **2026-08** | 演示统一指这里 |
| 近 6 个月 | 2026-04 ~ 2026-09 | 本库跨度本来就是 6 个月 |

> **为什么不锚在真实当日？** 因为数据 9-22 就断更了。锚在真实当日会让「上月」指向数据残缺的 9 月，
> 结论不可比。这个选择写在 YAML 的 `时间锚点.理由` 里，**换数据源时必须重新确认**。

常用相对时间（全部由锚点推出，**不由模型自己算**）：

| 说法 | 区间 | 说法 | 区间 |
|---|---|---|---|
| 本月 | 2026-09-01 ~ 2026-10-01 | 今年 | 2026-01-01 ~ 2027-01-01 |
| 上月 / 上个月 | 2026-08-01 ~ 2026-09-01 | 近三个月 | 2026-07-01 ~ 2026-10-01 |
| 近 6 个月 / 近半年 | 2026-04-01 ~ 2026-10-01 | 近 30 天 | 2026-08-24 ~ 2026-09-23 |
| 本季度 | 2026-07-01 ~ 2026-10-01 | 上一季度 | 2026-04-01 ~ 2026-07-01 |
| 指定月份「2026 年 8 月」 | 2026-08-01 ~ 2026-09-01 | | |

区间一律**左闭右开**（`>= 起 AND < 止`），避免月末遗漏。

## 三、五个指标

> 每个指标下面都带一个**实测示例**（数字来自本库实跑，不是举例说明）。

### M1 来料不良率
**业务含义**：衡量供应商供货质量水平 ｜ **别名**：不良率、不合格率、IQC不良率、来料质量

| | |
|---|---|
| 数据源 | `到料检验`（JOIN `供应商` / `物料`） |
| 公式 | `SUM(不良数量) ÷ SUM(抽检数量) × 100%`，保留 2 位 |
| 可用维度 | 供应商、物料、物料类别、供应商类别、月份 |
| 时间字段 | `到料检验.到料日期` |

**两条硬护栏（都是踩过的坑）**
1. **分母必须走 `NULLIF`** —— 分母为 0 时返回 NULL，**不能返回 0**。「没有抽检」被显示成「0% 不良」是最典型的误读。
2. **必须先 SUM 再相除，禁止 `AVG(每行比率)`** —— 对行比率求平均会掉进辛普森悖论，大订单和小订单被同等对待。

**实测示例 · 2026 年 8 月不良率排名前 5**

| 供应商 | 不良率 |
|---|---|
| **东莞精诚五金制品有限公司** | **7.66%** |
| 宁波恒力精密铸造有限公司 | 2.03% |
| 东莞市佳合线材有限公司 | 2.00% |
| 青岛海利密封件有限公司 | 1.74% |
| 深圳市宝盈塑胶制品厂 | 1.61% |

**实测示例 · 东莞精诚近 6 个月趋势**（这条是全库埋好的故事线）

| 月份 | 04 | 05 | 06 | 07 | 08 | 09 |
|---|---|---|---|---|---|---|
| 不良率 | 2.92% | 1.82% | 2.23% | **5.46%** | **7.66%** | **7.98%** |

7 月跳变、8-9 月持续恶化未收敛，且 8 月不良原因里**镀层类占三分之二**（起泡 5 次、附着力不足 4 次）——
指向工艺变更，不是偶发质量问题。**这是演示"数字 → 原因 → 文档证据"三段式的起点。**

### M2 准时交付率
**业务含义**：衡量供应商按期交货能力 ｜ **别名**：准时率、交期达成率、OTD、交付及时性

| | |
|---|---|
| 数据源 | `采购订单` JOIN `到料检验` JOIN `供应商` |
| 公式 | `COUNT(到料日期 ≤ 约定交期) ÷ COUNT(已到料订单) × 100%`，保留 1 位 |
| 可用维度 | 供应商、物料、物料类别、月份 |
| 时间字段 | `采购订单.约定交期` |

**三条硬护栏**
1. **实际到料日期只能从 `到料检验.到料日期` 取** —— `采购订单` 表里**没有**这个字段。
   这是**刻意的数据模型陷阱**，也是真实 ERP 的常态。
2. **未到料的订单不进分母** —— 否则会把「还没到货」当成「已经延期」。
   本库 696 张订单里 **111 张未到料**，混进去会让准时率从 **88.4% 掉到 74.3%（差 14.1 pp）**。
3. 本库**一单一次到料**（585 张已到料订单 = 585 条检验记录，已实证）；多次到料的口径需业务确认。

**实测示例 · 各供应商准时率（最差在前）**

| 供应商 | 准时率 | 已到料订单 |
|---|---|---|
| **宁波恒力精密铸造有限公司** | **62.1%** | 58 |
| 佛山市南海区隆鑫金属制品厂 | 79.4% | 34 |
| 青岛海利密封件有限公司 | 82.8% | 29 |
| 东莞市佳合线材有限公司 | 83.3% | 48 |
| 东莞精诚五金制品有限公司 | 87.7% | 57 |
| 苏州瑞恒电子科技有限公司 | 93.3% | 60 |
| 常州金禾标准件有限公司 | 98.3% | 58 |

（全库合计 **88.4%**，分母 585）

### M3 库存安全水位
**业务含义**：识别库存低于安全库存的物料 ｜ **别名**：库存偏低、缺料风险、安全库存、库存预警

| | |
|---|---|
| 数据源 | `库存` JOIN `物料` |
| 公式 | `SUM(库存数量) ÷ 安全库存 × 100%`；**结果 < 100% 即触发预警** |
| 可用维度 | **只开放「物料」**（见下方说明） |
| 时间字段 | `库存.更新时间` |

**两条硬护栏**
1. **必须先按物料 SUM 全部仓库** —— 本库 67 条库存记录挤在 30 个物料上（平均每物料 2.2 个仓位）。
   直接比单条库存记录会得出 **10 个假预警**，真预警只有 **3 个**。
2. **预警过滤必须走 `HAVING`**（聚合后），写成 `WHERE` 是逻辑错误。

> **为什么只开放「物料」维度？** 分母「安全库存」是**物料级**的量。按类别/仓库分组会让分母失去意义
> （SQLite 会静默取任意一行的值，不报错）。「各仓库库存总量」是另一个问题，走基础查询。

**实测示例 · 真的低于安全库存的 3 个物料**（附上原始数字，方便业务自己复核）

| 物料编码 | 物料名称 | 库存合计 | 安全库存 | 水位 |
|---|---|---|---|---|
| A10023 | 不锈钢法兰盘 | 61 | 450 | **13.6%** |
| A10018 | 骨架油封 | 271 | 1,200 | **22.6%** |
| A10009 | 轴承座 | 123 | 350 | **35.1%** |

### M4 生产工单达成率
**业务含义**：衡量生产计划执行能力 ｜ **别名**：工单达成率、计划达成情况、生产完成率

| | |
|---|---|
| 数据源 | `生产工单` JOIN `物料` |
| 公式 | `SUM(完工数量) ÷ SUM(计划数量) × 100%`，保留 1 位 |
| 可用维度 | 物料、物料类别、工单状态、月份 |
| 时间字段 | `生产工单.计划完工日` |

**护栏**：达成率看**数量**；「按期完工率」看**时间**。客户说「达成」时**必须先问清是哪个** —— 这是两个指标。
另外「在制」工单（本库 12 张）是否计入分母需业务确认（v1.0 默认计入）。

**实测示例 · 各类别达成率（最低在前）**

| 物料类别 | 铸件 | 线材 | 机加工件 | 轴承 | 包装材料 | … | 弹簧 |
|---|---|---|---|---|---|---|---|
| 达成率 | **72.7%** | 79.1% | 80.5% | 81.9% | 89.4% | … | 98.6% |

**物料级最低**：A10025 传动轴，**56.7%**。

### M5 采购金额
**业务含义**：衡量供应商/物料/品类的采购规模（常与不良率并列看性价比）

| | |
|---|---|
| 数据源 | `采购订单` JOIN `供应商`（JOIN `物料`） |
| 公式 | `SUM(订单金额)`，保留 2 位 ｜ 单位：元 |
| 可用维度 | 供应商、物料、物料类别、供应商类别、月份 |
| 时间字段 | `采购订单.下单日期` |

**护栏**：时间字段是**下单日期**，与 M1/M2 的到料日期不同 —— **并列使用时要说明**，否则对不上账。

**实测示例**：采购金额第一的是 **东莞市佳合线材有限公司（3,925,371.60 元）**，
而它 2026 年 8 月的不良率只有 2.00% —— 金额大不等于质量差，这两个指标要分开看。

## 五、实体别名与口语映射

**要治的病**：客户说「**东莞精诚**」，库里存的是「**东莞精诚五金制品有限公司**」。
精确匹配 → **0 行，不报错**（实测：0 行 vs 模糊匹配 57 条检验记录）。

| 策略 | 内容 |
|---|---|
| 默认匹配 | **模糊包含**（`LIKE '%值%'`） |
| 规范化 | 去后缀（有限公司 / 有限责任公司 / 制品厂 / 公司 / 厂 …）、去空白、统一全半角 |
| **唯一性** | 模糊命中 **>1 条时不得任选**，必须把候选返回给用户澄清 |
| 兜底 | 命中 0 条时**明说**「库里没有匹配」，不猜、不退回全表 |

另外还有**表级口语别名**：「质检 / 检验 / IQC / 验货」→ `到料检验`，「订单 / 采购单」→ `采购订单`，
「工单」→ `生产工单`。

## 六、护栏（渲染器与服务层共同执行）

| 层 | 规则 |
|---|---|
| 连接 | 只读打开（`mode=ro`），任何写操作在连接层就被拒 |
| 语句 | 只允许**单条 SELECT**；出现分号或 `INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/ATTACH/PRAGMA/VACUUM/REPLACE` 一律拒绝 |
| 口径 | 比率分母一律 `NULLIF`；禁止 `AVG(行比率)`；库存必须按物料 SUM 后再比（`HAVING`）；**时间一律来自本文件的映射，不接受模型自算日期** |
| 结果 | 行数上限 200（超出提示收窄条件，不静默截断）；空结果必须区分「条件无匹配」与「实体不存在」 |
| 呈现 | 答案**必须随附口径说明**（哪个指标、哪个时间区间、哪个维度）；阈值类结论必须把阈值写出来 |

## 七、对账与对照实验（全部实测）

### 7.1 逐题对账：15/15 通过

语义层按定义渲染 SQL，与题集（`eval/问数题集-20题.json`）的标准 SQL 逐题比数值：
**A01-A05、B06-B10、C11-C15 全部通过**（20 题减去 D 档 5 题 —— D 档判据是「应反问」，不该产出 SQL）。

> 对账口径：**列名不同不算错**（「供应商」vs「供应商名称」是表述差异），
> 但**数值必须一致**。对账一律走**显式列映射**，不做自动列名猜测（猜错了会静默放过）。

### 7.2 三类错对照实验：错口径 vs 对口径，差多少

| 组 | 错误类别 | 错口径 | 对口径 | 差 |
|---|---|---|---|---|
| 1 | 口径 | 对每行比率求平均：**7.56%** | 先 SUM 再相除：**7.66%** | 0.10 pp |
| 2 | 口径 | 按单仓库比较：**10 个物料** | 按物料 SUM 全部仓库：**3 个** | 7 个假警报 |
| 3 | 口径 | 分母含 111 张未到料订单：**74.3%**（分母 696） | 只算已到料：**88.4%**（分母 585） | **14.1 pp** |
| 4 | **时间** | 「上月」锚成 2026-05 → **宁波恒力 3.48%** | 锚成 2026-08 → **东莞精诚 7.66%** | **答案换人了** |
| 5 | **实体名** | `= '东莞精诚'` → **0 行** | `LIKE '%东莞精诚%'` → **57 行** | 静默返回空 |

> **组 4 最值得看**：两条 SQL 都合法、都能跑、都给出像模像样的百分比 ——
> **不报错，只给错答案**，而且最高不良供应商直接从东莞精诚变成了宁波恒力。
> 演示时若没人核对月份，这种错误能骗过一屋子人。这就是「相对时间必须由语义层展开成确定日期」的理由。

## 八、拒答与澄清（能答什么 / 答不了什么）

> **这一节比前面几节都重要。** 前面的规则管「答对了没有」，这一节管「**该不该答**」。
> 问一个本库没有的主题（比如「上月工资总额」），模型不会说不知道 ——
> 它会挑一张真实表硬答：SQL 合法、数字来自真实数据、**只有主题是错的**，而且无从对照检查。
> 所以「该不该答」必须在**调用模型之前**由确定性规则判掉。

### 8.1 四类处置

| 类型 | 含义 | 用户下一步 | 是否调模型 |
|---|---|---|---|
| **元问题** | 问「数据本身」（准不准 / 多新 / 覆盖什么） | 无 —— 已直接回答 | ❌ 不调 |
| **拒答·超范围** | 问的对象本库没有（人力 / 销售客户 / 财务 / 设备 / 售后 / 外部信息） | **换主题**（补充信息没用） | ❌ 不调 |
| **澄清·有歧义** | 问句里的词在库内有两解 | 说明要哪一个（**同时已按默认给出答案**） | 调 |
| **澄清·缺信息** | 能答但条件不全（指代不明 / 没点名对象） | 补充信息 | 调 |

> **拒答与澄清在界面上必须长得不一样。** 二者混着显示，用户会一直补充信息，
> 而系统永远答不出来 —— 比直接说不支持更让人恼火。

### 8.2 本库的边界（一句话）

本库是「**供应链 + 生产**」数据，回答的是**采购、到料质量、库存、工单**这四件事：

- 覆盖：供应商(12) · 物料(30) · 采购订单(696) · 到料检验(585) · 库存(67) · 生产工单(147)
- 可问示例：各供应商的来料不良率 / 准时交付率 · 低于安全库存的物料 · 各物料类别的工单达成率 · 各供应商的采购金额排名
- **不支持**：人力（员工/考勤/工资）· 销售与客户（销售订单/回款/合同）· 财务（利润/成本/报损）· 设备（停机/维修/稼动率）· 售后（退货/投诉）· 外部信息（汇率/行情）

### 8.3 两条纪律（都是被实测逼出来的）

| 纪律 | 为什么 |
|---|---|
| **拒答必须给出路** | 只说「答不了」，用户的下一步是随机换一种问法，而系统永远答不出 —— 与「功能不存在」没区别。所以拒答一定附「本库能答什么」+ 4~5 条可问示例。 |
| **宁可多一句提醒，不可少答一次** | 库外词与库内词**同时命中**时不拒答，走正常链路 + 强提示。「客户让我们查东莞精诚的不良率」含「客户」，主体却是供应商质量 —— 把能答的问题变成答不出，是另一种错误，而且用户无从察觉。 |

### 8.4 歧义：默认 + 说明，而不是拦下

「五金件」**既是物料类别也是供应商类别**（12 个物料类别里 11 个与供应商类别同名，运行时从库里算交集，不手写词表）。

v1.0 草案原写「必须澄清」，**包 3 改判为「默认物料类别 + 同时把另解说出来」**：

> 本库「五金件」既是一个物料类别，也是一个供应商类别；本次按**物料类别**理解。
> 若你要看的是供应商类别，把话说明白（例如「五金件的供应商」）即可。

理由：口语里「五金件的不良率」九成指的是**料本身**的质量。硬澄清会把九成能答的问题变成答不出 —— 那是另一种错误；而且用户会觉得系统在装傻。**答案照给，理解方式明说。**

另一处歧义是「达成」：默认指**数量**达成（完工数 ÷ 计划数）。问「按期完工」是时间口径，是另一个指标 —— 这个会提示，但**不会替用户改口径**。

### 8.5 元问题：诚实边界

被问「数据准不准」时，**不允许**用「数据准确可靠」这类话糊弄。实际回答：

> 本库是**演示数据** —— 由 `建库脚本.py`（固定种子 20260923）生成，不是生产库导入的，
> 所以它不存在「准不准」的问题：它是自洽的，但不代表任何真实企业的经营情况。
> …（然后给出时间跨度、锚点、各表行数、以及**怎么自查**：页面上的 SQL 就是实际执行的那一条）

### 8.6 反问要能收敛

模型给的反问如果只写「请补充更多信息」，用户的下一步是**随机猜一次**，猜不中就再猜 —— 与不答没有区别。
所以反问必须给出**可选方向**，缺了会由确定性兜底补上：

> 你可以从这几类里挑一个：各供应商的**质量**（来料不良率）、**交期**（准时交付率）、
> **库存**（低于安全库存的物料）、**工单**（生产计划达成率）、**采购**（金额排名）。
