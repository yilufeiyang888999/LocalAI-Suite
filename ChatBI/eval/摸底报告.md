# 作品二 · 包 0 摸底报告：本地 4B 模型「裸直出 SQL」的真实水平

> 生成时间：2026-10-12 下午｜模型：**Spark-X2.5-4B-Q6_K** @ `127.0.0.1:8000`（llama.cpp server）
> 题集：`eval/问数题集-20题.json`（20 条，A/B/C/D 四档）｜结果：`eval/摸底结果.json`
> **这份报告的任务是回答一个问题：架构走「模型直出 SQL」还是「模型只出意图 + 语义层模板拼 SQL」。**

---

## 一、结论摘要

**裸模型直出 SQL：20 题通过 9 题（45%）。**

| 档 | 题型 | 通过 | 通过率 | 失败形态 |
|---|---|---|---|---|
| **A** | 单表聚合 | 3/5 | **60%** | 漏 DISTINCT ×1、跨表编造字段 ×1 |
| **B** | 条件过滤 + 分组聚合 | **0/5** | **0%** | 缺表前缀语法错 ×3、实体名匹配 ×1、口径错 ×1 |
| **C** | 多表 JOIN + 口径 | 1/5 | **20%** | **口径错 ×3**、编造字段 ×1 |
| **D** | 模糊提问（应反问） | **5/5** | **100%** | — |

**一句话结论：4B 会写 SQL 语法，但不会懂业务口径 —— 而这恰好证明语义层是必需的，不是多余的一层。**

## 二、方法（可复现）

```bash
python scripts/摸底-Text2SQL.py --只列标准答案   # 先校验题集标准 SQL 能跑
python scripts/摸底-Text2SQL.py --档 A,B         # 分批跑（≤12 题/批）
python scripts/摸底-Text2SQL.py --档 C,D
```

- **提示词策略：不给任何业务提示。** 只给表结构 DDL + 数据时间范围，就是"裸测"。给了口径提示就不是摸底线，而是摸背书了。
- **判据：结果集比对** —— 忽略列名与行序，逐格比较（数值保留 2 位、字符串精确）。行数或列数不同即判失败。
- D 档判据单列：**不得产出可执行 SQL**，且输出必须含澄清语义；硬答即失败。
- **分母固定**：不可执行的题不从分母剔除（它们正是该方案自己的失分）。

## 三、五个关键发现（全部有实证）

### 1. 三个口径陷阱，模型全踩

Demo 库里刻意埋的两处陷阱 + 一处模型自己造的，**无一幸免**：

| 题 | 模型的写法 | 为什么错 | 正确答案 |
|---|---|---|---|
| **C11** | `(d.不良数量 * 1.0 / d.抽检数量) > 0.05` | **对每行比率**判断 → 辛普森悖论 | 先 `SUM` 再相除 |
| **C13** | `WHERE i.库存数量 < m.安全库存` | **单仓口径** → 10 个假预警 | 先按物料 `SUM` 全部仓库 → 3 个 |
| **B09** | `COUNT(CASE WHEN p.约定交期 <= p.下单日期 ...)` | 拿**下单日期**当到料日期，**完全没 JOIN 到料检验** | 实际到料日只能从 `到料检验.到料日期` 取 |

C11 实测 5 行 vs 基准 3 行、C13 实测 8 行 vs 基准 3 行 —— **SQL 全部合法执行、数字看着合理，只有口径是错的**。这正是 ChatBI 与通用 NL2SQL 的分界线，也是语义层存在的理由。

### 2. 时间口径错是最危险的一类（B06）

```sql
WHERE 到料日期 BETWEEN '2026-05-01' AND '2026-05-31'   -- 模型认为「上月」= 2026-05
```

**模型把「上月」理解成了 2026 年 5 月**（本库基准应是 2026-08）。这类错的可怕之处：SQL 合法、能跑、结果是个像模像样的百分比 —— **不报错，只给错答案**。演示时如果没人核对月份，能骗过一屋子人。

→ 对应草案里的 `时间表达式` 段：中文相对时间必须由语义层映射成确定日期，**不能让模型自己推算「今天是几号」**。

### 3. 实体名称精确匹配 → 静默返回 0 行（B07）

```sql
WHERE 供应商.供应商名称 = '东莞精诚'      -- 库里是全称「东莞精诚五金制品有限公司」
```

**结果 0 行，不报错。** 客户说「东莞精诚」，库里存的是全称 —— 而且模型还顺手把「近 6 个月」算成了从 2026-03 起。

→ 对应草案里的 `实体别名` 段：需要「客户口语名 → 库内名称」的映射 + 模糊匹配策略。这一条**靠提示词很难根治，靠映射表才稳**。

### 4. 纯语法错占 B 档的大头（3/5），而且最好治

B06 / B08 / B10 三题清一色报 `ambiguous column name: 供应商编码` —— 模型**知道**要 JOIN（JOIN 子句写对了），但 SELECT 列表里写了裸列名。

**这类错是模板拼 SQL 天然消除的**：列引用由模板生成，永远带表前缀。

### 5. D 档 100% —— 与直觉相反的好消息

5 条模糊提问（「这个月怎么样」「帮我看看有没有问题」「那家企业还行吗」…）**全部正确反问，无一硬答**。

**这是本次摸底最有价值的正面发现**：4B 小模型在「该澄清时澄清」上表现很好 → **Agent 的意图路由与澄清层可以直接跑 4B，不必上大模型。**

## 四、对架构的决策

**✅ 走「模型只出结构化意图 + 语义层模板拼 SQL」，不是「模型直出 SQL」。**

理由是算得出来的 —— 20 题的 11 次失败里：

| 失败类型 | 条数 | 语义层能否根除 |
|---|---|---|
| 口径错（行比率 / 单仓 / 到料日期） | 3 | ✅ 口径写死在模板里 |
| 缺表前缀语法错 | 3 | ✅ 模板生成列引用 |
| 时间口径错 | 1 | ✅ 时间表达式映射 |
| 实体名精确匹配 | 1 | ✅ 别名映射 + 模糊匹配 |
| 漏 DISTINCT / 编造字段 / 少一跳 | 3 | 🟡 部分（靠指标定义 + Schema 约束） |

**9/11 的失败是语义层能根除的。** 剩下 3 条属于 Schema 理解，用「表结构 + 指标定义」喂给模型可以改善，但不该指望根治。

**同时保留一条兜底**：C14（各物料类别不良率）模型**直出就对** → 模板覆盖不到的问题，允许「模型直出 + 护栏执行 + 结果校验」。**两条路线并存，不是二选一。**

**分工定案**：

| 环节 | 谁做 | 依据 |
|---|---|---|
| 意图识别（指标 / 维度 / 过滤 / 时间） | **4B 模型** | D 档 5/5，A 档 60% |
| 模糊提问澄清 | **4B 模型** | D 档 5/5 |
| SQL 生成（口径、时间、别名） | **语义层模板** | 9/11 失败由此根除 |
| 结果校验（行数 / 列数 / 口径） | 服务层 | 兜住模型直出那条路 |

## 五、判据的已知问题（诚实标注）

1. **「列数必须与标准一致」偏严。** 如果模型给出「正确内容 + 多余的列」，会被判失败。本批 20 题**没有因此误判**（C11/C12/C13 虽列数不符，但内容确实错；B07 经复核是真错 —— 返回 0 行）。**但这是运气**，包 4（正式评测集）要加一条：「标准列全对且是列超集 → 记『表述差异』，不计失败」。
2. **归因只取「第一个遇到的错误」，不是「唯一错误」。** 例如 B06 同时有时间口径错和语法错，被记为语法错。报告里的「主要失败形态」是首错分布，不是全部错误清单。
3. **样本量 20 条**，每档 5 条 —— **分档通过率（尤其是 0% 和 100%）的分辨力只有 ±20 pp**。结论方向可信，「精确百分比」不可外推。扩到 50 条后要重算。

## 六、本轮附带产出与一个自身 bug

- **修了一道题的口径**：C11 原题面漏了时间范围 → 按全期算东莞精诚不良率只有 **4.79%**（<5%，答案 0 行），按 8 月单月才是 **7.66%**（答案 3 行）。**答案在 0 与 3 之间摆动，取决于题面没写的东西** —— 这本身就是最典型的口径歧义，题面已补「2026 年 8 月」。
- **修了脚本一个真 bug**：分批跑时结果文件互相覆盖（第二批把第一批冲掉，`累计` 只剩 10 题）。已改为**合并写入**（同一题集下按编号更新）。**这个 bug 不报错，只让报告悄悄少一半样本** —— 与「不报错只出错」同一族。
