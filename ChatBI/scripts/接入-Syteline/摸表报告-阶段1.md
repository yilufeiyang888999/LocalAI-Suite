**结论：按行数排序在 Syteline 上没有参考价值。** 前 10 名里 8 张是 Syteline 应用框架的元数据表（表单渲染、脚本、对象属性），把它们当业务对象会做出一堆毫无意义的问数。

真正该看的是**命名规范**：

| 后缀 | 含义 | 例 |
|---|---|---|
| `_mst` | master，主数据/单据主档 | `item_mst`、`co_mst`、`ledger_mst` |
| `_log_mst` | 日志表（历史快照） | `coitem_log_mst`、`poitem_log_mst` |
| `_all` | 汇总/合并视图 | `co_all`、`artran_all`、`po_mst_all` |
| `_v` / 无后缀视图 | Syteline 自带扁平化视图 | `artran_open`、`arinv_item` |

另有大量扩展包前缀：`AU_`、`CLM_`、`ESB_`、`CN_`、`FR_`、`ERS_`、`ZIT*`、`PL_`、`NL_` —— 这些是 ISV 或客户定制，**问数范围要先划清，别默认全都要**。

## 四、五张核心表（已逐个核过字段）

### 4.1 `co_mst` — 销售订单头，8,097 行 / 166 列
```
site_ref、cust_num、cust_seq、cust_po、order_date、stat、close_date、
eff_date、exp_date、disc_amount、pricecode、credit_hold_date、projected_date、ack_stat
```
- `stat` = 单据状态（**必须白名单过滤，作废单不能算**）
- `ack_stat` = 确认状态，与 `stat` 是两回事，别混
- 无金额合计字段 → 金额要从 `coitem_mst` 聚合

### 4.2 `coitem_mst` — 销售订单行，11,290 行 / 148 列
```
site_ref、co_num/co_line（订单键）、item、qty_ordered、qty_shipped、qty_invoiced、
qty_returned、qty_ordered_conv、price、price_conv、due_date、ship_date、stat、cust_num
```
**这张表是 UOM 坑的解药**：`qty_ordered` 是订单单位数量，`qty_ordered_conv` 是**换算到基本单位**的数量。同理 `price` / `price_conv`。跨物料汇总必须用 `_conv` 结尾的字段，否则 EA 和 KG 直接相加。

### 4.3 `item_mst` — 物料主档，2,532 行 / **278 列**
```
site_ref、item、stat、qty_allocjob、qty_used_ytd、qty_mfg_ytd、
u_ws_price（自定义字段）、alt_item、stat、CreateDate/RecordDate/UpdatedBy
```
**278 列是这批表里最宽的**。语义层里必须显式列字段，`SELECT *` 会拖回一堆没用的列。
`u_` 前缀是**客户自定义字段**（`u_ws_price`），这类字段的语义只有业务方知道，不要猜。

### 4.4 `custaddr_mst` — 客户地址/主档，504 行 / 55 列
```
site_ref、cust_num、cust_seq、state、curr_code、corp_cust、credit_hold_date、days_over_inv_due_date
```
- **客户主键是 `cust_num` + `cust_seq` 复合**（一个客户多地址），只按 `cust_num` 统计会重复计数
- `curr_code` 在客户主档上，可作为币种默认值

### 4.5 `ledger_mst` — 总账分录，450,660 行 / 79 列 ← **最大业务表**
```
site_ref、trans_date、dom_amount、for_amount、curr_code、consolidated、vend_num、check_date
```
**这张表一锤定音了多币种坑**：
- `dom_amount` = 本币金额（domestic）
- `for_amount` = 原币金额（foreign）
- `curr_code` = 币种

两个金额字段同时存在、量级不同。**任何金额类问数必须先定「本币还是原币」，写进口径定义。** 混用或随手取一个，出来的数字看着合理但完全错。这条我在建议里反复强调，现在有字段级证据了。

## 五、多站点：不是可选项

**1,765 张表带 `site_ref`，5 张核心表全部带。** 演示库只有一个站点所以看不出问题，接上多站点生产库后会立刻出现「销售额凭空翻倍」。

语义层里 `site_ref` 应当作为**默认过滤条件**，而不是每个查询临时加 —— 加漏一次就是一次错数，且不会报错。

## 六、视图体系：可以省力，但要挑

2,435 个视图，命名模式：2,370 个无后缀、46 个以 `_view` 结尾。

**有价值的**：Syteline 自带的扁平化视图，如 `artran` / `artran_all` / `artran_open` / `arinv_item` / `itemvend` —— 它们已经把主档和明细 JOIN 好了，做问数比手写多表 JOIN 更稳。

**要警惕的**：
- `ido` 架构只有 30 个对象（19 视图 + 11 存储过程），且全是**框架元数据**（`DataRules`、`Collections`、`AccessAs`），**不是业务 IDO**
- 大量 `Z*`、`AU_`、`CLM_` 视图是 ISV/客户定制，含业务方私有逻辑，**不要默认可用**

**建议**：前 5 个验证问题先用**基表**写清楚（可控、可解释），跑通后再看哪些视图能替代多表 JOIN。别一上来就用视图 —— 视图定义里可能有你不认识的过滤条件，出错时无法定位。

## 附：本次踩到并已修的三个脚本 bug

记在这里，避免下次重复：

| 问题 | 现象 | 根因 |
|---|---|---|
| SQL 里的中文字面量 | 返回 `'?'`，判定「0 张表」但退出码 0 | `'表'` 经 ODBC 转单字节字符集时丢失。**类型标记必须用 ASCII（T/V），中文只在 Python 侧映射** |
| 行数虚高 1.5 倍 | `FormComponents01` 报 231 万，实际 77 万 | `SUM(p.rows)` 与 `allocation_units` 同 JOIN → 一个 partition 对应多个 allocation_unit，笛卡尔放大。行数与页数拆成两个子查询 |
| 视图掉进差集 | 「2435 张表只出现在列清单里」 | 表查询只查 `USER_TABLE`，列查询覆盖表+视图。两边口径必须一致 |
