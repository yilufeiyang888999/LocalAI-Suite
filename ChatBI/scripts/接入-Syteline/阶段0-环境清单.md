## 三、建只读账号（在虚机里、用 SSMS 或 sqlcmd 执行）

> 本次实际建在 **`Demo`** 库上；接生产库时换成生产库名重做一遍（同名登录 `chatbi_ro` 可复用，
> 只需在新库里 `CREATE USER ... FOR LOGIN` 再挂 `db_datareader`）。

```sql
-- 1) 服务器级登录（密码换成你自己的，别用本文示例）
CREATE LOGIN chatbi_ro WITH PASSWORD = N'换成强密码', CHECK_POLICY = ON;

-- 2) 映射到 Syteline 库（库名按实际填）
USE [你的Syteline库名];
CREATE USER chatbi_ro FOR LOGIN chatbi_ro;
ALTER ROLE db_datareader ADD MEMBER chatbi_ro;

-- 3) 明确拒绝写（双保险：datareader 本来就不含写权限）
DENY INSERT, UPDATE, DELETE, ALTER, CONTROL ON SCHEMA::dbo TO chatbi_ro;
```

为什么**不用 sa**：`sa` 是 sysadmin。护栏再怎么写，也挡不住「配置写错一行」这类事故；
而 `db_datareader` + `DENY` 是**库层面**的兜底，脚本写崩了也改不动一个字节。
这是「纵深防御」，和 ChatBI 里 `mode=ro` + `PRAGMA query_only` 两层是同一个思路。

## 四、Default Switch 的 IP 会变

虚机重启后 DHCP 可能分到别的地址。两种处理：

| 方案 | 做法 | 代价 |
|---|---|---|
| 短期（现在） | IP 变了就改命令参数 | 改一处，30 秒 |
| 长期（跑通后） | 换 Internal Switch，宿主机与虚机各设静态 IP | 虚机断网（Internal 不通外网），且 Syteline 若绑了主机名要复核 |

**别和「跑通验证」同时做**：一次只改一个变量，否则出问题分不清是哪一步引起的。

## 六、实测踩到的两个坑（都属于「静默型」）

### 1. 连接串里的超时键会被驱动吞掉

`ODBC Driver 18.7` 对串里的 `Connection Timeout=15` 和 `LoginTimeout=8` **都回一句
`Invalid connection string attribute (0)`，但连接照常进行** —— 也就是说超时根本没设上，
而唯一的迹象是错误消息里多一段噪声。第一次遇到时只看到 18456，差点以为是别的问题。

**改法**：超时走 pyodbc 的参数，不写进串。

```python
pyodbc.connect(串, readonly=True, timeout=15)   # timeout 是登录超时
连接.timeout = 180                               # 这是查询超时，两回事
```

判据：串里出现任何超时键，就应该怀疑它没生效。

### 2. Syteline 用的是自签名证书

去掉 `TrustServerCertificate=yes` 立即变成 `08001`（TLS 失败）。这不是配置错，
是服务端证书链不完整导致的正常现象。

**推论**：换任何客户端（另一个 Python 库、ODBC 驱动版本、BI 工具）都要带同等的信任参数，
否则会看到一堆看似无关的连接失败。SSMS 21+ 里对应的勾选是「信任服务器证书」。

## 七、只读账号验证（`验-只读账号.py`，2026-10-21 15:58 实测）

「账号建了」和「账号确实只读」是两件事。后者唯一的可信判据是**服务端拒绝一次写**，
且拒绝理由必须是权限不足 —— 不是语法错、不是客户端拦的。

```bash
P="C:/Users/Ivan/AppData/Local/Programs/Python/Python314/python.exe"
"$P" 验-只读账号.py --主机 172.16.11.254 --用户 chatbi_ro --库 Demo
```

实测输出（6 项全过）：

| 检查项 | 结果 |
|---|---|
| 登录 | PASS —— `chatbi_ro` 连上 `172.16.11.254:1433/Demo` |
| 身份 | PASS —— `SUSER_SNAME()` = `chatbi_ro` |
| 不是超管 | PASS —— `IS_SRVROLEMEMBER('sysadmin')` = 0 |
| 读元数据 | PASS —— `sys.tables` = 2,864 张 |
| 读业务表 | PASS —— `dbo.item_mst` 首行 `item = 30F` |
| **写被拒** | PASS —— `[42000] 拒绝了对对象 'item_mst' 的 UPDATE 权限 (229)` |

### 探针为什么这样写

- **写探针用独立连接、`readonly=False`**。`readonly=True` 的连接会在客户端就把写语句拦下，
  那样测的是 pyodbc，不是账号权限。要验权限就必须让它真的发到服务端。
- **`UPDATE ... WHERE 1 = 0` + 显式 `ROLLBACK`**。SQL Server 在**编译阶段**就做权限检查，
  不匹配任何行也照样报 229 —— 所以探针能验出权限，同时一个字节都不改。
- **退出码分级**：全过 0 / 未达标 1 / 连不上或环境缺失 2。别让「连不上」和「连上但权限不对」
  落进同一个码里，否则排查时得重新猜。
