# 作品一 · 企业知识库问答（RAG）

> 三作品统一载体 `Local-AI` 的**知识库模块**。独立 Python 本地服务 + HTTP 接口、  
> **不写进 Rust**（APP 管模型生命周期与显存，Python 管业务逻辑）。  
> 场景与作品二（智能问数）、作品三（部署助手）共用同一虚构制造企业  
> —— 语料从 `资产-制造业Demo库/` 的 6 张表反推，不是凭空编。

## 交付物清单（评审导读）

> **一句话**：把 18 份企业内部制度文档做成**私有化问答** —— 本地检索 → 本地小模型作答 →
> 每条答案**可溯源到原文**，查不到就明确说「不在本知识库中」。全链路本机运行，**不出网、不调云端 API**。

### 四、技术选型结论（全是实测出来的，不是默认值）

| 环节 | 结论 | 依据 |
|---|---|---|
| 分块 | 标题切节 + 上限 1200 字 | 16 方案 × 60 库内题 |
| 检索 | **纯 BM25**（本语料上强于向量；向量仅作可选） | 5 通道 × 60 题 |
| 重排 | **唯一真实增益**：Top-50 → rerank → Top-3，R@3 **0.9833** | 10 方案 × 60 题 |
| 拒答 | **三层互补**：类1 分数阈值 −3.0 ｜ 类2 Top-1 库外信号 ｜ 类3 生成端（判据 = 位置 ∨ 类2 信号 ∨ 库外拒答词） | 见报告 §七 |

## 扩充语料：五种格式入库 + 影子预检（D11 增量，2026-10-12）

> 一句话：**往 `corpus/raw/` 加文档，不能直接丢文件进去。**
> 有四种失败方式，其中**三种不报错** —— 只有影子预检能把它们变成"看得见的判据"。

### 为什么不能直接丢文件（两条实测出来的坑）

`实验-分块对照.读语料()` 只扫 `corpus/raw/`、只要 `.md`、而且**硬编码 UTF-8 读**：

| 放进去的东西 | 实际行为 | 后果 |
| --- | --- | --- |
| `.md` + UTF-8 + 文件头信息表 | ✅ 正常入库 | — |
| `.md` + **GBK/GB18030** | 🔴 `UnicodeDecodeError` **上抛**（`open()` 没有 try） | **整个服务起不来** |
| `.pdf` / `.docx` / `.txt` | 🔴 **静默丢弃**（`endswith(".md")` 过滤） | `/health.docs` 不涨，**不报错** |
| 文号抽不到（文件名带空格/括号） | ⚠️ 只警示、不阻断；**但若文件名里嵌着另一个合规号**（`19-新制度-QW-QA-01 (2).md`）→ 🔴 阻断 | 后者让每次命中都判「引用库外」→ 类2 库内误拒，**不报错** |
| 参考资料（无体系文号，如外部标准/行业报告/客户资料） | ⚠️ 按参考资料处理，**可正常入库** | 本来就不该有体系文号，判据不该拦 |
| 补上"故意留白"的文号 | 🔴 库外拒答题失效 | O03/O03b 从"该拒答"变成"该答"，**不报错** |

> **判据**：入库是否生效，只能看 `/health` 的 `docs` / `blocks` 变化 —— **`status: ok` 什么也证明不了**（旧基座同样是 ok）。

### 支持矩阵

| 格式 | 转换方式 | 依赖 |
| --- | --- | --- |
| `.md` | 原样（**不改编码**，非 UTF-8 要让它原形毕露） | 无 |
| `.txt` / `.csv` | 多编码探测（utf-8 / utf-8-sig / gb18030 / gbk / big5 / latin-1） | 无 |
| `.docx` | `zipfile` + XML 解 `w:pStyle` → 标题层级、`w:tbl` → 表格 | **无**（纯标准库） |
| `.xlsx` | 每工作表 → `## 表名` + Markdown 表格 | `openpyxl` |
| `.pdf`（文本层） | pdfplumber 抽文本 + 表格，并判是否扫描件 | `pdfplumber` |
| `.pdf`（扫描件） | 🔴 **不处理** —— 每页均 < 20 字即判"无文本层"，明确报错要求先 OCR | 需 OCR 通道 |

### 两步操作（CLI）

```bash
# ① 转换（产物落 corpus/_待入库/ —— 暂存区，读语料不扫这里）
python scripts\转换-语料.py D:\下载\新制度\  --输出目录 corpus\_待入库

# ② 影子预检（复制现有 18 份 + 候选 → 临时目录 → 用服务同一套代码重算）
python scripts\自检-新增语料.py --写基线          # 首次/语料变更后建基线
python scripts\自检-新增语料.py --预检 corpus\_待入库

# ③ 预检通过后再入库（或直接用管理页）
#    入库 = 拷进 corpus\raw\ + 重启服务（或管理页热重建）
```

### 六项预检（每项都能区分「通过」和「没检查」）

| # | 检查 | 说明 |
| --- | --- | --- |
| ① | **编码** | 严格 UTF-8。不通过时**后续五项一律标「未检查」而非「通过」** |
| ② | **标题** | 有没有 `# ` 一级标题（它进块前缀） |
| ③ | **文号** | 是否在文件头信息表显式声明 + 形态与前缀是否属**本企业体系文号**（`QW-/QP-/JC-/JS-/CSR-`）。**不合规只出 ⚠️ 不阻断** —— 白名单本身等于"本库只装本企业体系文件"，但**参考资料**（外部标准、行业报告、客户资料）本来就不该有体系文号。真正的风险见 ⑥ |
| ④ | **留白冲突** | 是否撞上那 6 个有意留白的文号 |
| ⑤ | **库外引用** | 本文档净新增了哪些悬空引用 |
| ⑥ | **类2 误判风险** | 注册文号里是否**嵌着**另一个合规文号（如 `QW-QA-01 (2)` 嵌 `QW-QA-01`）→ 会触发类2 库内误拒。**这是文号相关的唯一阻断项** |

**口径自证**：预检起步先"复算现状"，结果必须等于基线（在线时还比对 `/health`）。对不上就明说**「本次结论不可信」**并返回退出码 2 —— 不装作通过。

### 启动向量服务

```powershell
cd D:\workspace\10-LocalAI-Installer\engine\backends
.\llama-server.exe --model D:\workspace\7-AI-Code\RAG-Embedding\models\bge-m3-Q8_0.gguf --embedding --pooling cls --port 8082 -b 4096 -ub 4096 --parallel 1
```

> **🔴 `-b 4096 -ub 4096` 不能省。** 服务端默认 `n_ubatch = 512`，  
> **单个输入的 token 数超过 512 会直接返回 HTTP 500**，而报错只在服务端日志里  
> （`input (516 tokens) is too large to process`），客户端只看到一个 500。  
> 1200 字的中文块 ≈ 1500+ token，必然踩到。
>
> **🔴 `--parallel 1` 更不能省。** 多槽并行时服务按**最长公共前缀**复用槽位  
> （日志原文 `selected slot by LCP similarity`）→ 同一段文本可能落到不同槽、带不同缓存前缀  
> → 池化向量差 **1e-3**，且**不是确定误差、是竞态**（同一批连打两次都可能不同）。  
> 后果是**结果不可复现**：近似并列处的名次会在两次运行之间漂移，而 60 题下 1 题 = 1.7pp。  
> **自检**：`python scripts\诊断-向量可复现性.py 8082` 必须全绿（8081 实测 2.282e-03，不一致）。

**刻意不加 `-ngl`（跑 CPU）**：568M 模型 24 线程单条 <100ms，索引是离线批处理；  
省下 0.6 GiB 显存与一个 CUDA context 留给 4B 生成端。  
（llama.cpp 惰性初始化 —— 不写 `-ngl` 就压根不碰 CUDA，**不报错也不警告**。）

### 启动重排服务（默认检索链需要）

```powershell
.\llama-server.exe --model D:\workspace\7-AI-Code\RAG-Embedding\models\bge-reranker-v2-m3-Q8_0.gguf `
    --reranking --port 8085 -b 2048 -ub 2048 -t 24 --parallel 1
```

> **🔴 `--parallel 1` 不能省**（2026-10-09 实证，与向量服务同一个病根）：默认 4 槽时，  
> **FP16 版重排的分数跨请求不稳定** —— 同一批 (问句, 块) 连打两次就差 **2.5e-02 ~ 3.0e-02**，  
> 全序 **3/3 题**挪动；批量从 16 拆成 8+8 差到 **6.9e-02**。  
> **Q8_0 因走整数点积而免疫槽数**（8085 与 `--parallel 1` 的 8088 逐位相同 60/60），  
> 所以对这行命令是**保险**，对任何 FP16/浮点权重是**必需**。  
> **自检**：`python scripts\诊断-重排可复现性.py --端口 8085` 必须全绿。  
> 量化对照（Q8_0 有没有伤质量）见 `eval/重排量化对照-报告.md`。
>
> **🔴 `-ub` 是物理批硬上限**：本语料最长块 1188 字，超过 512 会让**整批**返回 HTTP 500  
> （`input (529 tokens) is too large to process`），不是只丢那一条。  
> 客户端另加了**二分降级**：一批失败就对半拆开重试，长尾块不该让整批陪葬。  
> 返回的 `results` 是**按分数降序**的，必须用 `index` 回填原位置 —— 想当然按返回顺序对齐会张冠李戴，**且不报错**。
>
> **⚠ 起服务前先看内存**：每个重排服务要 ~1 GiB 输出缓冲（FP16 单槽实测 `failed to allocate
> buffer of size 728.72 MiB` → `decode() failed: Compute error.`）。  
> 同时挂 5 个以上 llama-server 会把 32 GB 机器挤爆，症状是**随机的 HTTP 500**，不是模型问题。

### 🔴 最重要的发现：「块大小」这个说法是误导

| 块上限    | 节完整率  | 被切的节 | 实得块数 | 平均块长  | R@1        |
| ------ | ----- | ---- | ---- | ----- | ---------- |
| 350 字  | 76.0% | 69   | 401  | 195 字 | 0.6833     |
| 700 字  | 96.5% | 10   | 301  | 260 字 | 0.7333     |
| 1200 字 | 99.7% | 1    | 289  | 271 字 | **0.7833** |

上限涨 **3.4 倍**，平均块长只涨 **1.4 倍** —— 因为 287 个自然节的中位数只有 **232 字**。

**上限不是在放大块，是在决定「要不要在语义单元中间下刀」。** 所以正确的调参动作是  
**让上限大到绝大多数自然节不需要被切**（本语料 1200 字），而不是去找某个"合适的块大小"。

> **⚠ 撤回一条"反直觉"**：多槽版曾显示**定长-1200 在长文档子集上全场最差（0.5909）**、  
> 并据此推出"上限的价值完全依附于切分方式"。**重建后不成立** ——  
> 定长-1200 是 **0.6818**（与定长-700 并列），全场最差是定长-350（0.6364）。  
> 正确表述：**上限 350 → 1200 对两个族都是正收益**（定长族 +4.5pp、标题族 +13.6pp），  
> 只&#x662F;**"结构边界"是它的乘数**：块大而边界乱，收益会被摊薄。

> 🔴 **2026-10-10 修掉一个「判据与执行各走各的」的坑**
>
> `重排命令()` 原先第 0 段写的是**裸名字** `llama-server.exe`，靠 `cwd=引擎目录` 指望它被找到。
> 但 **Windows 的 `CreateProcess` 不用 `lpCurrentDirectory`（子进程 cwd）去找 exe**，
> 用的是**父进程 cwd + PATH**。于是：
>
> | 环节 | 结果 |
> |---|---|
> | `检查前置条件()` 查 `引擎目录/llama-server.exe` 在不在 | **✅ 全绿** |
> | 真正 `Popen(["llama-server.exe", …], cwd=引擎目录)` | **❌ `FileNotFoundError: [WinError 2]`** |
>
> **判据检查的路径 ≠ 实际执行的路径，判据就成了摆设** —— 与「同一份数据有两处定义」同一个毛病。
> 修法：只留一处定义（`引擎程序路径()`），前置条件改成直接查**命令里真正会执行的那一段**
> （`重排命令()[0]`，必须绝对路径且存在）；`起一个()` 把 `WinError 2` 转成一句人话再返回 `None`。
>
> ⚠️ **这个分支此前从未被真正执行过** —— 10-09 只验了 `--状态` / `--演练` / 「已在跑 → 跳过」。

**四个设计要点（都是踩过的坑）：**

1. **三态，不是二态** —— ✅通过 / ❌失败 / **⏭跳过（未检查）**。跳过必须显式出现，

3. **读旧产物不算证据** —— `--全量` 跑完会核对 `知识库服务-验收.json` 的 mtime  
   是否**新于本次启动**，否则判 ❌（防「把上次的结论当这次的结果」）。
4. **基线写死是故意的** —— `docs=18 / blocks=290 / 阈值-3.0 / 类2软` 直接断言，  
   语料或配置一变就红。**红了是设计意图，不是脚本太严。**

> **判据有效性已验证**（不是摆设）：注入三类错误 —— 基线改 999 → ❌、把 P01 的期望反转成「应拒」→ ❌、

> 脚本末尾会打印**它代劳不了的那一步**：在 APP 里切到「知识库问答」点一次，看答案 + 引用卡片。

1. **拒答必须三层，且三层互补**（这是本服务最核心的设计）：

## Web 问答页：D6 交付（2026-10-09 完成）

作品一原本只能在 Local-AI 桌面 APP 里用。加了这个页面之后，**浏览器直接打开
`http://127.0.0.1:8092/` 就能问**，不依赖桌面端 —— 演示、截图、给别人看都不用装 APP。

### 怎么起

### 三个设计选择

| 选择 | 理由 |
|---|---|
| **页面内嵌进服务**（`GET /`），不另起静态服务 | **同源**：页面 fetch `/ask` 不跨域 —— APP 侧那套 CORS 前提在这里直接消失 |
| **HTML 独立成文件**（`web/index.html`），服务启动时读进内存 | 服务本体已 ~500 行，再塞 400 行 HTML 就没法读；独立文件还能用浏览器打开调样式 |
| 响应带 `Cache-Control: no-store` | 防「改了页面没生效」—— 本项目已在服务实例上栽过一次同类问题 |

### 页面能力

- 输入问题 → 答案 + **3 张引用卡片**（文号 / 章节 / 重排分 / 原文摘要）
- **拒答态专门样式**：显示拒答类型与原因；类2/类3 还会列出「提到的库外文档」，让用户知道该去查哪份
- 顶部状态徽标读 `/health`：语料规模 + 依赖地址；耗时（检索/生成/合计）与最高分随答案显示
- 4 个示例问题（3 道库内 + 1 道库外，用来看拒答长什么样）

### 安全

- **模型输出一律 `textContent`，不拼 `innerHTML`** —— 语料内容不可信，拼 HTML 就能被注入
- 无外链资源（不依赖 CDN），离线可用
- 只监听 `127.0.0.1`（与现服务一致）。要局域网演示得显式改绑定地址，并接受**服务无鉴权**这一事实

### 判据

```powershell
python scripts\探测-问答页.py       # 34 项：HTTP 层 + JS/DOM 静态一致性 + 客户端断连容错
```

覆盖：`/` 200 + HTML + `no-store`、`/index.html` 与 `/` 逐字节等价、`favicon` 204、
未知路径 404 且列出可用路径、`/health` 与 `/ask` 未被破坏（库内题 3 条引用 / 库外题正确拒答）、

**答案未拼 innerHTML**、无外链资源、**客户端半途断连后服务照常**（见下）。

### 🔴 客户端半途断连是**正常事件**，不该打一整页堆栈（2026-10-09 修）

浏览器**预连接**（连上不发请求，或发完就关）、刷新、关标签页，以及任何「只读响应头就走」的
调用方，都会在服务端写响应体写一半时把 socket 掐掉 —— 默认 `socketserver` 会为此打完整堆栈：

```
ConnectionAbortedError: [WinError 10053] An established connection was aborted ...
ConnectionResetError:   [WinError 10054] An existing connection was forcibly closed ...
```

**服务本身完全正常**，但看日志的人会以为它崩了。**根因有一半是我们自己造的**：
`启动-服务.py --状态` 里那版「只取 `Content-Type` 就把 response 丢下不管」的 `urllib` 用法，
socket 被 GC 回收时发 RST，正好打在服务端写 14 KB 页面的那一刻。**客户端偷懒伪装成了服务端故障。**

两处都修了：

| 修哪 | 怎么修 |
|---|---|
| **客户端**（`启动-服务.py`、`探测-问答页.py`） | 一律 `with urlopen(...) as r: r.read()` —— **读完再关**，不把 socket 丢给 GC |
| **服务端**（`容忍断连的服务器`） | 只吞 `ConnectionError` 家族，打**一行带时间戳的说明**（前 3 条，之后静默）；**其它异常照旧保留完整堆栈** —— 真 bug 不能被这层顺手盖掉 |

🔴 **判据的支点**：吞掉堆栈后，「服务扛住了断连」和「根本没触发到断连」在控制台上**长得一模一样**。
所以把次数暴露到 `/health` 的 **`client_aborts`**，让判据能区分这两件事：

```
[8] 客户端提前断开（浏览器预连接 / 刷新 / 关标签页都会发生）
  ✅ 有 client_aborts 计数（判据的支点）  缺该字段 = 服务端还是「照默认打完整堆栈」的旧壳
  ✅ 断连被吞掉且计数上涨                 client_aborts 0 → 5（5 次 RST）
  ✅ 断连后服务照常发整页                 200 ｜ 16052 字节（与基线逐字节相同）
```

（探针用 `SO_LINGER=0` 主动发 RST，且**只发不读** —— 若先读一部分，14 KB body 可能已被内核
缓冲收下，服务端 `sendall` 直接成功，就**根本触发不到**，「通过」会变成「没测」。）

### 🔴 请求日志不能直接写控制台：窗口一被拖选，服务就被「冻死」（2026-10-10 修）

**现象**：服务「活着但不应答」—— 端口仍在 `LISTENING`、CPU 0%、**所有请求超时（连 `/health` 都挂）**，
看上去跟服务崩了没区别。

**根因**：Windows 传统控制台（conhost）**被鼠标拖选就进入「标记」模式**，
此时**进程的下一次控制台输出会永久阻塞**。而服务每个请求都要往控制台打一行日志
→ 冻死在那一行。拖选窗口是很自然的动作 —— **想复制启动横幅到剪贴板，就够把它冻住了**。

**实测铁证**（同一 PID、没重启，所以排除了「崩了」和「卡在启动」）：

| 时刻 | 控制台窗口标题 | `/health` |
|---|---|---|
| 冻结中 | `Select C:\...\python.exe` | ❌ 6 s 超时（CPU 0%） |
| 标题恢复干净后 | `C:\...\python.exe` | ✅ **200，0.03 s** |

`Select ` 前缀正是 conhost 进入「标记/拖选」模式时加的（`启动-服务.py` 从没设过标题，
python.exe 的默认标题就是它自己的路径）。**进程没死，只是卡在控制台 I/O 上。**

**修法**：把「上屏」从请求路径上摘下来。

| 环节 | 谁做 | 会不会被窗口冻住 |
|---|---|---|
| **落盘** `logs/知识库-YYYYMMDD.log` | **调用线程**直接写（本地追加，有界） | 不会 → **日志一行不少** |
| **入队** | 调用线程 `put_nowait`（满了丢**屏幕**行并计数） | 不会 |
| **上屏** | 一根后台守护线程 | **会**，但只冻它自己，请求照常 |

⚠️ **第一版修法是错的**（被下面的判据当场抓出来）：把「落盘 + 上屏」放**同一根线程**
（先落盘、再上屏）—— 控制台一冻，这根线程卡在上屏上，**文件也跟着不再增长**。
实测 6 个请求只落盘 **1 行（42 字节）**。**「先落盘」只保证「卡住那一刻之前」的行不丢；
要一行不少，落盘就不能和上屏在同一根线程上。**

**判据**：`python scripts\诊断-控制台冻结.py`（常驻 · 6 项 · 须一个空闲端口）

```
✅ 开日志文件() 给出落点
✅ 冻结前 /health 可用（对照基线）   200 ｜ console_dropped=0
✅ 冻结下 /health 全部 200          6/6 ｜ 单次最慢 0.016 s
✅ 日志文件一行不少                  新增 6 行 / 期望 6 行
✅ 冻结真的发生了（假控制台被写过）   假控制台 write 次数 = 1
```

不必真去拖选窗口：把 `sys.stdout` 换成一个 `write` **永不返回**的假对象即可。
🔴 最后一条是**判据的判据** —— 「控制台压根没冻」和「冻了但服务扛住了」表现一模一样，
不先证明「冻结真的发生了」，上面两条就等于没检查。

**启动器也会当场点名这个病因**：`/health` 不通时它先看端口上有没有进程 ——
**有进程却在 `LISTENING` 下不应答 = 「进程没死，是被卡住了」**，并直接给出
「到那个窗口按一下 **Esc**」的处置（**不用重启**）。`/health` 同时新增
`log_file` / `console_dropped`：**字段缺失 = 跑的是「只上屏」的旧实例**，启动器判 ❌。

**两条可复用的教训**：
1. **别把「UI 状态」放进服务的关键路径**。窗口有没有被选中，与服务该不该应答毫无关系 ——
   但只要关键路径上还剩一次「写控制台」，它就能把服务冻死。
2. **「日志里有没有红字」都不等于「服务状态」**。上一轮是「有报错 ⇒ 以为故障」，
   这一轮是「没报错、进程还在 ⇒ 以为服务好好的」，同一类错误的两面。

### 评分口径（三条，全部可自动判定）

1. **要点命中** —— 答案里有没有出现本该出现的关键事实（题库 `参考要点`，
   已用护栏逐条校验「能在语料中逐字查到」）。命中 ≠ 答对，但**不命中基本等于没答到**。
2. **数值无编造** —— 答案里的数值（百分比 / 文档编号 / **带单位的量**如 °C、μm、h）
   必须逐字出现在服务返回的 `context` 里。分母 = **数值个数**，不是题数。
3. **拒答正确** —— 库外题必须拒答；库内题不得被误拒。

库内题得分 = `70×要点率 + 15×数值忠实 + 15×未误拒`（答案无数值时，忠实度的 15 分并入要点）；
库外题 = 拒答 100 / 未拒 0。**生成失败不计入分母**并显式标注。

### 🔴 本轮踩到的三个坑（都是「判据本身出错」，不是系统出错）

1. **「数值无编造」首版几乎没有取样**。初版沿用了 `评测-引用忠实度.py` 的抽取规则
   （只抽 `%` 与文档编号），100 题**只抽出 17 个数值** —— 温度、厚度、时长这些
   实测值全漏了。`0/17 = 0% 编造` 看着漂亮，其实是**没检查**。
   补上「带单位的量」后取样 **17 → 46**。
2. **我自己设的「参考要点」错了 4 条**，被这一轮跑成了「系统答错」：
   Q010（只要了「不得返工」，模型答「直接报废」其实正确）、Q040（问「哪张表」却把要点设成
   机制词「反推」）、Q066（只要编码 `S012`，模型答公司全名「东莞市佳合线材有限公司」）、
   Q080（只要 `L1/L4` 代号，模型答中文名「入门…可带徒」）。
   **教训：要点的粒度必须与问法对齐 —— 问「哪一家」就别只要编号，问「几级」就别只要代号。**
3. **`string.Template` 只认 ASCII 占位名**，中文占位符（`$生成时间`）会抛
   `Invalid placeholder`；而 `%` 格式化又会炸在 CSS 的 `width:100%` 上。
   最终用 `Template` + ASCII 占位名。

### 复用机制（省掉重复打服务）

`python scripts\评测-问答评分.py --复用` → 从 `问答100题-结果.json` 读回**答案与 context**
只重算评分，**不访问服务**（秒级）。改要点定义 / 改判据口径时用它，
避免为了改一个词就把 100 题重打一遍（每轮 ~5.5 min）。结果 JSON 里保存了 `context`，是为了让评分可审计。

## 对接 Local-AI APP：D5 交付（2026-10-09 完成）

在 APP 的「聊天」页加了**模式切换：通用对话 / 知识库问答**。知识库模式下提问走本服务，

### 对接方式：前端直连，**不经过 Rust**

APP 里原有的聊天就是前端直接 `fetch` 本机 `http://127.0.0.1:<port>/v1/chat/completions`  
（见 `ChatView.vue`），知识库这一路**沿用同一模式** —— 与「RAG/ChatBI 做成独立 Python 服务 +  
HTTP 接口、**不写进 Rust**」的既定分工一致。Rust 侧只加了一个设置字段 `kb_base_url`。

> 🔴 **由此推出一个硬前提：服务必须发 CORS 头。** WebView 里跨域 fetch 缺了它，  
> 前端只能看到一个**笼统的失败**（既没有状态码也没有响应体），排查时极易误判成"服务没起来"。  
> 服务已开 `Access-Control-Allow-Origin: *` + `OPTIONS` 预检（只监听 127.0.0.1、不用凭证，放开 `*` 不增加暴露面）。

### 改了三处

| 位置                | 改动                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------- |
| 本服务               | 加 CORS（`do_OPTIONS` + 三个响应头）；加 `--生成端/--重排端` 参数                                       |
| APP `settings.rs` | `AppSettings` 加 `kb_base_url: String`（`#[serde(default)]`，默认 `http://127.0.0.1:8092`） |

**知识库会话用哨兵 `model_id = __kb__`**（`create_chat_session` 只校验非空、不查模型表），  
让两种模式的聊天记录在同一个列表里自然分开，**不新增表、不动 schema**。

### 一个必须显式核对的静默失败路径

本服务**默认写死生成端 `http://127.0.0.1:8000`**，而 **APP 的 `service_port` 是用户可配的**。  
两边不一致时：服务照常返回 200，只是每次答案都变成「资料不足 / 生成失败」—— **不报错，只是没结果**。

所以 `/health` 会返回 `deps.generate`，聊天页拿它和 APP 实际端口比对，不一致就红字提示该按哪个端口重启。  
（这就是为什么加了 `--生成端` 参数 —— 光有提示不改配置，用户还是卡着。）

### 引用的持久化：一个有意选择的降级

`chat_messages` 表只有 `(id, session_id, role, content, created_at)`，  
而且 `database.rs` 用的是 `execute_batch(CREATE TABLE IF NOT EXISTS …)`，**没有版本化迁移机制**  
—— 往已存在的库里加列不会生效。为一个 UI 展示引入迁移基建不划算，所以：

- **内存态**：助手消息带 `kb` 字段（结构化 citations），渲染成卡片；
- **落库**：只存纯文本（答案正文 + 文末「依据（N 条）：1. 【文号】章节」）。

刷新后卡片降级为文本，**信息不丢但结构没了**。要做成可持久化卡片，是一个独立任务：加迁移 + `ALTER TABLE` + 兼容分支。

## 环境坑：GPU 引擎槽位挂死（**高频复发** —— 10-12 一天内第 4 次）

  若不加 assert 会把「原版表现」当「实验版表现」。**实验必须能区分「改了」和「没改」**。
