## 一、服务设计

### 1.1 检索链：为什么起手是 BM25 而不是向量

| 理由          | 依据                                                                   |
| ----------- | -------------------------------------------------------------------- |
| 四项指标全高      | 扩集后 **B 纯 BM25 = 0.8333** > C RRF 0.8000 > A 向量 0.7667（`混合检索-报告.md`） |
| 长文档短板已补     | cross-encoder 把它从 0.73 拉回 **0.93**（`重排对照-报告.md` §三.1）                |
| **启动零外部依赖** | BM25 是纯 Python 自实现（字符 bigram），**不用向量服务、不用 290 次嵌入** → 建基座 **0.05 s** |

> 如果起手用向量，服务启动就必须依赖 8082，且要跑 290 次嵌入（约 30 s）——
>
> 而它对最终指标是**负贡献**（R@1 0.7667 < 0.8333）。**这就是「先验证再落地」的价值。**

### 1.2 接口

```
GET  /health
  → {"status":"ok","docs":18,"blocks":290,"pool":50,"top_k":3,
     "score_threshold":-3.0,"class2_enabled":true,"class2_scope":1,
     "chain":"BM25 Top-50 -> rerank -> Top-3","deps":{...}}

POST /ask   {"question":"...", "top_k":3, "generate":true}
  → {"question":..., "answer":..., "refused":bool, "refusal_type":ascii|null,
     "refusal_reason":..., "off_library_refs":[...], "top_score":...,
     "citations":[{"rank","doc_no","section","score","excerpt"}],
     "context":"...",                       # 送进生成端的原文
     "timings":{"retrieve","generate","total"}}
```

**🔴 对外字段一律 ASCII**（`answer` / `refused` / `refusal_type` / `citations` …）。

Tauri 侧的 serde `rename_all` 对**中文变体名完全无效且不报错** —— 跨边界一律 ASCII 是本项目的铁律。

内部变量名照常用中文（Python 里可行），只有**序列化出口**收窄成 ASCII。

### 1.3 引用溯源怎么做的

引用**不靠模型标注**（4B 模型做标注会错），而是**结构化的**：

- 分块时每块天然带 `(文号, 章节路径, 正文)`，前缀形如

  `QW-JS-01 表面处理通用技术条件 > 5. 镀层要求 > 5.1 镀层厚度`；
- 服务直接把**检索到的 Top-3** 按这个结构返回，**100% 与实际送进去的块一致**；
- 另给 `context`（完整原文）—— 前端可展示"依据"，验收脚本用它核对数值忠实度。

## 二、拒答：为什么必须三层（每一层都是量化的）

### 2.1 类1 分数阈值 —— 拦「完全没线索」

重排分是**原始 logit**，可直接当判据。每题取全库最高分（= 池内 Top-50 最高分，**已验证 10/10 等价**）：

```
库内 60 题最高分：最低 -2.37   中位 3.69   最高 6.87
库外 6 题最高分 ：O03=2.65  O06=0.18  O01=-4.39  O05=-5.37  O02=-8.43  O04=-9.06
```

**阈值取 −3.0**（库内最低 −2.37 留 0.63 余量、库外最近 −4.39 留 1.39 余量）：

| 阈值处实测 | 结果                       |
| ----- | ------------------------ |
| 库内误拒  | **0/60** ✅               |
| 库外拦截  | **4/6**（O01/O02/O04/O05） |

**为什么不是 0.0 或 3.0**：库外 O03（2.65）比多数库内题还高 —— 语料里 QW-DD-03 确实在讲废液收集，

只是处置流程指向库外的 QW-DD-05，**分数本身没错**。要拦住全部库外题得把阈值提到 3.0，

代价是**误拒 33% 库内题**。→ 阈值只能拦"没线索"这一类。

### 2.2 类2 引用链闭合 —— 拦「有线索但指向库外」

判据：**Top-1 块内出现「本文档体系前缀」的编号，且不在库内文号表**。

```
文档前缀白名单 = QW- / QP- / JC- / JS- / CSR-
```

**为什么要白名单**：`QR-` 是记录表单（不入库是正常的），`ISO-` / `GB-` 是外部标准 ——

它们混进来只会制造假阳性。

**为什么要收窄到 Top-1**：第一版用 Top-3，**库内误拒 4/60**（L03/L05/P05/P06）——

库内文档正常地交叉引用库外文档（如 QP-01 的程序文件清单里列了 QP-04）。

看块级证据（`scripts/查看-拒答题块.py`）后发现：真线索在库外的题（O03）**库外号就在 Top-1**，

而误伤的 3 题库外号都只在 Top-2/Top-3。收到 Top-1 后误伤降到 **1/60**。

| 口径               | 库内误拒     | 库外拦截 |
| ---------------- | -------- | ---- |
| 类2（Top-3 宽）      | **4/60** | 1/6  |
| **类2（Top-1 收窄）** | **1/60** | 1/6  |

**O03 的物理形态**（`scripts/查看-拒答题块.py` 的输出）：

```
 Top-1  2.65  QW-DD-03   8.2 废水处理   🔴 QW-DD-05
       正文：8.2.1 漂洗水按含铬废水（三价铬）单独收集… 8.2.2 处理流程见 QW-DD-05。
```

### 2.3 类3 生成端 —— 兜底

提示词要求「资料不足时只回答资料不足」，输出命中拒绝词即判拒答。

它兜住了**类1、类2 都拦不住的 O06**（最高分 0.18、Top-1 无库外号）：

```
O06「S001 东莞精诚的注册资本是多少」
  → 检索到 QR-QC-07-01（供应商质量月度评级表），有 S001 但没有"注册资本"字段
  → 生成端：资料不足 ✅
```

### 2.4 三层是**互补**的（这是本节最重要的一张表）

| 配置               | 库内误拒                 | 库外拦截    | 漏网                  |
| ---------------- | -------------------- | ------- | ------------------- |
| 只类1              | 0/60                 | 4/6     | O03、O06             |
| 只类2(Top-1)       | 1/60                 | 1/6     | O01、O02、O04、O05、O06 |
| 类1 + 类2          | 1/60                 | 5/6     | O06                 |
| **类1 + 类2 + 类3** | **0/60**（软）/ 1/60（硬） | **6/6** | **无** ✅             |

**任何单层都不够。** 这不是设计冗余，是三段互不重叠的失败模式。

## 三、类2 硬拒答 vs 软警示：一个被实测推翻的直觉

直觉上"命中就拒答"更安全，但**实测相反**。

| 配置           | 库内误拒          | 库外拦截    | 数值总数 | 编造 | 正常答中位耗时 |
| ------------ | ------------- | ------- | ---- | -- | ------- |
| 类2 **硬**拒答   | **1/60**（P06） | 6/6     | 30   | 0  | 2.92 s  |
| **类2 软警示** ✅ | **0/60**      | **6/6** | 35   | 0  | 3.19 s  |

软模式的做法：**不拦**，只把「资料引用了库外文档 X」注入提示词，**让生成端自己判断**。

**理由不止"少误伤 1 题"** —— 拒答质量本身提高了：

|     | 拒答答案                                   |
| --- | -------------------------------------- |
| 硬拒答 | `资料不足`                                 |
| 软警示 | `资料不足。处理流程见 **QW-DD-05**，但该文档不在本知识库中。` |

**软模式把类2 从「拦截面」变成了「信息渠道」**：用户不仅知道答不了，还知道**该去查哪份文档**。

代价只是 O03 从"直接拦"变成"多跑一次生成端"（0.8 s → 2.1 s）。

> **这是本次最值得记的一条**：拒答不只是"要不要答"，还有一&#x4E2A;**「拒答时说多少」**&#x7684;维度。
>
> 把结构化信号（库外文档号）透给生成端，比在上游一刀切更值钱。

## 四、端到端验收（四判据）

`scripts/验收-知识库服务.py` —— 直接 import 服务模块，与 HTTP 路径共用同一份 `回答()`。

### 判据① 拒答矩阵（分母固定，按层拆分）

| 集合 | 题数 | 拒答      | 类1 | 类2 | 类3(生成端) |
| -- | -- | ------- | -- | -- | ------- |
| 库内 | 60 | **0** ✅ | 0  | 0  | 0       |
| 库外 | 6  | **6** ✅ | 4  | 0  | 2       |

**库外漏网：无。**

### 判据② 数值忠实度

**分母 = 数值个数，不是题数**（否则「一个数值都没有」会被算成通过）。

```
答案里百分比/编号总数：35（其中 38 题一个数值都没有）
编造 0 / 35 = 0.0%
```

> ⚠ 与 `混合检索-报告.md` §八 的 30~35 同量级，但**不是同一链路**（那里是 C RRF Top-3，
>
> 这里是 BM25→重排 Top-3）。**不能混着引用。**
>
> ⚠ 38/60 题的答案压根不含数值 —— 这个判据的**有效样本只有 22 题**，不能外推为"永不编造"。

### 判据③ 引用可核对性

```
引用有问题的题：0 / 66 ✅      # 文号全在库内、章节非空、rank 从 1 连续
未返回引用的题：0
```

### 判据④ 耗时

```
正常答（60 题）：总 中位 3.19 / p90 5.21 ｜ 检索 0.90/0.98 ｜ 生成 2.41/4.32
拒答（6 题）  ：总 中位 0.88 / p90 2.52  ｜ 检索 0.86/0.95 ｜ 生成 —
```

**拒答比正常答快 3.6 倍**（省掉生成）—— 拒答不只是安全网，也是**性能优化**。

## 五、工程坑（本轮踩的）

### 1. 🔴 编号正则漏掉数字段 → 库内题被误判成"引用库外"

第一版 `[A-Z]{2,6}(-[A-Z]{2,6}){1,2}-\d{2,6}` 会把 `JC-GY-2026-006`

截成 **`JC-GY-2026`**，于是一份**库内**文档的编号不在库内文号表里 → 假阳性一片。

修正：`[A-Z]{2,6}(?:-[A-Z0-9]{1,6}){1,3}` + **前缀白名单**。

**教训：从文本里抽结构化字段的代码，必须对所有样本做一次穷举核对**（这条已踩第 N 次）。

### 2. 🔴 编号抽取必须**单一实现**

`实验-拒答规则.py` 与服务各写一份 = 迟早漂移。已把 `抽文档号` / 编号正则 / 前缀白名单

统一放到 **`检索-混合.py`**（它本来就是"共用检索工具"），其余模块转发调用。

### 3. 🔴 Python 标识符不能含 `①`

`命中① = ...` → `SyntaxError: invalid character '①' (U+2460)`。

**汉字可以做标识符，带圈数字不行**（不属于 XID_Continue）。

### 4. `BaseHTTPRequestHandler.protocol_version` 只能 ASCII

写成中文属性名会被**静默忽略**（不报错，退化成 HTTP/1.0）—— 与 serde 那个坑同源。

### 5. `nohup ... &` 在本项目 shell 里会被清理

`cmd && nohup python x.py > log 2>&1 &` 之后 shell 退出，**子进程与日志一起消失**。

改用「后台任务」方式启动（本项目已多次踩到）。

### 6. 🔴 客户端偷懒会**伪装成服务端故障**（2026-10-09 追加）

加了 Web 问答页之后，服务端控制台开始零星打出一整页堆栈：

```
ConnectionAbortedError: [WinError 10053] An established connection was aborted by the software ...
ConnectionResetError:   [WinError 10054] An existing connection was forcibly closed by the remote host
```

**看着像服务崩了，其实服务从头到尾正常。** 根因两个，而且**有一半是自己造的**：

| 来源      | 机制                                                                                                                 |
| ------- | ------------------------------------------------------------------------------------------------------------------ |
| 浏览器     | **预连接**：连上先不发请求、或发完就关（刷新 / 关标签页 / 换页都会）。写 14 KB 页面写到一半被掐                                                           |
| 自己的探针脚本 | `启动-服务.py --状态` 那版「只取 `Content-Type` 就把 response 丢下不管」的 `urllib` 用法 —— socket 被 GC 回收时发 RST，**正好打在服务端写 body 的那一刻** |

修法两边都要动：

- **客户端**：一律 `with urlopen(...) as r: r.read()` —— **读完再关**，不把 socket 丢给 GC。
- **服务端**（`容忍断连的服务器`）：只吞 `ConnectionError` 家族，打**一行带时间戳的说明**（前 3 条，

  之后静默）；**其它异常照旧保留完整堆栈** —— 真 bug 不能被这层顺手盖掉。

🔴 **这里最容易犯的判据错误**：吞掉堆栈之后，「服务扛住了断连」和「压根没触发到断连」在控制台上

**长得一模一样** —— 按「表现相同 = 没有判据」的原则，这等于没测。所以把次数暴露到 `/health` 的

`client_aborts`，并让探针用 `SO_LINGER=0` 主动 RST（且**只发不读**，否则 body 会被内核缓冲收下、

`sendall` 直接成功、根本触发不到）：

```
✅ 有 client_aborts 计数（判据的支点）  缺该字段 = 服务端还是「照默认打完整堆栈」的旧壳
✅ 断连被吞掉且计数上涨                 client_aborts 0 → 5（5 次 RST）
✅ 断连后服务照常发整页                 200 ｜ 16052 字节（与基线逐字节相同）
```

教训一句话：**「日志里有报错」不等于「有故障」** —— 判状态要看现场（服务是否照常出整页），

而不是看日志里有没有红字。这与「把日志表现当状态」是同一类错误，只是方向反过来了。

### 7. 🔴 判据检查的路径 ≠ 实际执行的路径（2026-10-10 追加，启动器暴露）

作者跑 `python scripts\启动-服务.py`，在 ① 起重排那一步直接崩：

```
File "...\启动-服务.py", line 519, in 起一个
    subprocess.Popen(命令, cwd=工作目录, creationflags=旗标)
FileNotFoundError: [WinError 2] The system cannot find the file specified
```

**而 `检查前置条件()` 刚刚全绿。** 根因：`重排命令()` 第 0 段写的是**裸名字** `llama-server.exe`，

靠 `cwd=引擎目录` 指望它被找到 —— 但 \*\*Windows 的 `CreateProcess` 不用 `lpCurrentDirectory`

（子进程的 cwd）去找 ex&#x65;**，用的是**父进程 cwd + PATH\*\*。

| 环节                    | 检查/执行的对象                       | 结果                 |
| --------------------- | ------------------------------ | ------------------ |
| `检查前置条件()`            | `引擎目录/llama-server.exe` 存不存在   | **✅ 全绿**           |
| `Popen(命令, cwd=引擎目录)` | `命令[0]` = `"llama-server.exe"` | **❌ `WinError 2`** |

**判据查的是一份路径、执行走的是另一份路径 —— 判据就成了摆设。**

与「同一份数据有两处定义」是同一个毛病（改一处、跑另一处，不报错，只出错）。

**修法（三步，缺一不可）**：

1. **只留一处定义**：新增 `引擎程序路径()` 返回绝对路径，`重排命令()` 与前置条件都从它取。
2. **判据改成查真正会执行的那一段**：`检查前置条件()` 直接取 `重排命令()[0]`，

   先断言「必须绝对路径」，再断言「文件存在」—— 顺序不能反，前者才是这次的真病因。
3. **错误降级成人话**：`起一个()` 捕获 `FileNotFoundError` / `OSError`，打印

   `argv[0] = …` 与「Windows 不会用 cwd 找 exe」的说明后返回 `None`，不再甩裸 Traceback。

   顺带：**新增 `验引擎可执行()`**，起重排前真跑一次 `<exe> --version`

   （0.37 s），把「新窗口一闪就没」（缺 DLL 时起进程立刻退出）也变成可读的报错。


**实测（同机、同 exe、同 cwd，只换 argv[0]）**：

```
裸名字   + cwd=引擎目录 → FileNotFoundError: [WinError 2]   ← 稳定复现作者的报错
绝对路径 + cwd=引擎目录 → 正常，version: 0.4.0-dev (build 10853)，0.37 s
端到端（临时端口 8086） → Popen OK，2.0 s 后 /health 200 {"status":"ok"}
错误分支（故意用裸名字）→ 一句人话 + 返回 None，无 Traceback
```

🔴 **为什么 10-09 交付时没发现**：那时只验了 `--状态` / `--演练` / 「已在跑 → 跳过」——

**真正 spawn 进程的分支一次都没跑过**。**「演练通过」不等于「执行通过」**；

`--演练` 打印的正是这行命令，只是当时没人盯 `argv[0]` 是不是绝对路径。

### 8. 🔴 服务「活着但不应答」：控制台被拖选 → 进程被冻死（2026-10-10 追加）

作者跑启动器，体检里 8092 明明在跑，自证却报 `❌ 知识库 /health 不通`。

**现场量到的三件事**（都是反直觉的）：

```
netstat  : 8092 仍在 LISTENING（PID 313876），另有多个连接卡在 CLOSE_WAIT / ESTABLISHED
tasklist : PID 313876  CPU Time = 0:00:00，进程 Status = Running
probe    : /health 6.02 s 超时（TimeoutError），而 8085 / 8000 都是 0.0x s 秒回
```

**根因**：Windows 传统控制台（conhost）**被鼠标拖选就进入「标记」模式**，

此时**进程的下一次控制台输出会永久阻塞**。而服务每个请求都要往控制台打一行日志

（`log_message`）→ 冻死在那一行。端口照旧在听、CPU 0%、**所有请求超时**。

**铁证**（同一 PID、没重启 —— 这一点才排除了「进程崩了 / 卡在启动」）：

| 时刻      | 控制台窗口标题                    | `/health`        |
| ------- | -------------------------- | ---------------- |
| 冻结中     | `Select C:\...\python.exe` | ❌ 6 s 超时         |
| 标题恢复干净后 | `C:\...\python.exe`        | ✅ **200，0.03 s** |

`Select ` 前缀正是 conhost 进入「标记/拖选」模式时加的。**推导过程中先排除了两个错误假设**：

（a）进程崩了 —— 不通，netstat 显示它还在听；

（b）卡在启动自检 —— 不通，`serve_forever()` 之前的最后一次 `print` 在 **bind 之前**，

若冻在那儿端口根本不会 LISTENING。\*\*能同时解释「在听 + 不应答 + CPU 0」的只有

「已进入服务循环，但某次控制台写被冻住」。\**

**修法**：把「上屏」从请求路径上摘下来 —— 落盘由**调用线程**直接写，上屏交给一根后台线程。

| 环节                             | 谁做                               | 会被窗口冻住吗           |
| ------------------------------ | -------------------------------- | ----------------- |
| **落盘** `logs/知识库-YYYYMMDD.log` | 调用线程直接写（本地追加，有界）                 | 不会 → 日志一行不少       |
| **入队**                         | 调用线程 `put_nowait`（满了丢**屏幕**行并计数） | 不会                |
| **上屏**                         | 一根后台守护线程                         | **会**，但只冻它自己，请求照常 |

⚠️ **第一版修法是错的，被新判据当场抓出来**：把「落盘 + 上屏」放**同一根线程**（先落盘、再上屏）——

控制台一冻，这根线程卡在上屏上，**文件也跟着不再增长**。

实测：冻住时打 6 个请求，文件只长了 **42 字节（1 行）**，期望约 240 字节（6 行）。

**「先落盘」只保证「卡住那一刻之前」的行不丢；要一行不少，落盘就不能和上屏在同一根线程上。**

**判据**：`python scripts\诊断-控制台冻结.py [空闲端口]`（常驻 · 6 项）。不必真去拖选窗口 ——

把 `sys.stdout` 换成 `write` **永不返回**的假对象即可。🔴 其中一条是**判据的判据**：

「假控制台确实被写入过」—— 不先证明「冻结真的发生了」，

「控制台压根没冻」和「冻了但服务扛住了」表现一模一样，前两条就等于没检查。

**顺带把病因变成启动器能点名的话**：`/health` 不通时，先看端口上有没有进程 ——

**有进程却在 LISTENING 下不应答 = 「进程没死，是被卡住了」**，并给出「到那个窗口按 Esc」

的处置（**不用重启**）。`/health` 新增 `log_file` / `console_dropped`：

**字段缺失 = 旧实例（请求日志只上屏）**，启动器判 ❌ —— 否则「✅ 服务就位」会盖住

「你跑的是旧代码」这件事（又一次「判据不能区分新旧 = 没有判据」）。

**两条可复用的教训**：

1. **别把「UI 状态」放进服务的关键路径**。窗口有没有被选中，与服务该不该应答毫无关系 ——

   但只要关键路径上还剩一次「写控制台」，它就能把服务冻死。

   （触发动作极其平常：**想复制启动横幅到剪贴板**。）
2. **「日志里有没有红字」都不等于「服务状态」**。坑 6 是「有报错 ⇒ 以为故障」，

   这条是「没报错、进程还在 ⇒ 以为服务好好的」—— 同一类错误的两面。

## 六、对接 Local-AI APP（2026-10-09 完成 · 原 §六.1 已落地）

APP 的「聊天」页现在有**模式切换：通用对话 / 知识库问答**。知识库模式下提问走本服务。

### 6.1 对接方式沿用「前端直连」，不经过 Rust

APP 原有聊天就是前端直接 `fetch` 本机 `http://127.0.0.1:<port>/v1/chat/completions`，

知识库这一路**照抄同一模式** —— 与既定分工一致（RAG/ChatBI = 独立 Python 服务 + HTTP 接口，

**不写进 Rust**）。Rust 侧只多了一个设置字段 `kb_base_url`。

> 🔴 **这条决定直接推出一个硬前提：服务必须发 CORS 头。**
>
> WebView 里跨域 fetch 缺了它，前端只能拿到一个**笼统的失败** ——
>
> 既没有状态码也没有响应体，排查时会被误判成"服务没起来"。
>
> 已开 `Access-Control-Allow-Origin: *` + `OPTIONS` 预检（只监听 127.0.0.1、不用凭证）。
>
> 验证脚本：`scripts/探测-知识库HTTP.py`（专测这一层；`探测-知识库服务.py` 直接 import
>
> 函数、不走网络，**验不到 CORS 和状态码** —— 前端踩的坑恰好都在那一层）。

### 6.2 一个必须显式核对的静默失败路径

本服务**默认写死生成端 `http://127.0.0.1:8000`**，而 **APP 的 `service_port` 是用户可配的**。

不一致时：服务照常返回 200，只是每次答案都变成「资料不足 / 生成失败」——

**不报错，只是没结果**，是最难查的那一类。

处置：加 `--生成端/--重排端` 参数；`/health` 返回 `deps.generate`；

聊天页拿它与 APP 实际端口比对，不一致时红字提示**该按哪个端口重启**（光提示不改配置等于没说）。

### 6.3 会话归属：用哨兵 `model_id`，不新增表

知识库问答的历史放在 `chat_sessions` 里，`model_id` 写哨兵值 `__kb__`

（`create_chat_session` 只校验非空、不查模型表）。前端按它过滤，两种模式的记录自然分开。

**不动 schema、不加迁移** —— 项目当时也没有版本化迁移机制。

### 6.4 引用的持久化：一个有意选择的降级

`chat_messages` 表只有 `(id, session_id, role, content, created_at)`，

且 `database.rs` 是 `execute_batch(CREATE TABLE IF NOT EXISTS …)`，

**往已存在的库里加列不会生效**。为一个 UI 展示引入迁移基建不划算，于是：

- **内存态**：助手消息带 `kb` 字段（结构化 `citations`），渲染成卡片；
- **落库**：纯文本（正文 + 文末「依据（N 条）：1. 【文号】章节」）。

**刷新后卡片降级为文本：信息不丢，结构没了。** 要持久化卡片是个独立任务

（加迁移 + `ALTER TABLE` + 兼容分支），已记在 `types.ts` 的 `kb` 字段注释里。

## 七、提示词：覆盖度是实测调出来的（2026-10-09 追加）

### 7.1 现象：一个「真问题」被用户的一次追问挖出来

用户在 APP 里问「宁波恒力不良率」，答案说 `2.03%，未达到 5% 的标准…需提交交付改善计划`；

而同一问题在服务层复跑时，另一次答案里多一句 `累计准时交付率为 56.9%（< 70%）`。

**这句才是 S002 被点名的真正原因**（它质量没问题，是**交付**不达标）——

只看到前者会误判成「S002 没事」。

先排除的两个假设（都排除了）：

- **不是检索**：同一问句连问 3 次，引用**逐位相同**（5.43/4.98/4.59），指纹只有 1 种；
- **不是缓存**：服务 `回答()` 每次现算，没有 `lru_cache`；APP 层另发一问「宁波恒力不良率」

  也答对了 2.03% → **端到端是干净的**。

### 7.2 根因：提示词只要求「简洁」，没要求「覆盖」

服务早就传了 `temperature: 0.1`（很低），**降温度治不了它** ——

`scripts/诊断-生成确定性.py` 实测：**同一份提示词、temperature=0.0，5 次里出现 2 种输出**。

非确定性来自引擎层（kernel / KV 复用），不是采样参数能关掉的。

> 🔴 **由此推翻了我自己上一轮的结论**：我先用 **n=5** 测了「加一条'多条结论必须全部列出'」的效果，
>
> 得到 新=3/5 vs 旧=4/5，判「改了没用甚至更差」。**n=20 后结论反过来**（满分率 5/20 → 14/20）。
>
> **教训：生成端不是确定函数时，n=5 的对比就是没有判据 —— 「差 1 题」在这个场景里连方向都指不准。**

### 7.3 四版写法的二维对照

判据 = **多事实计数**（质量 2.03 / 交付 56.9 / 动作），并要求**配一道非目标题型**

（「记录写错了应该怎么改」），因为供应商维度的改动会污染无关题型。

| 第 3 条写法            | 供应商题覆盖（n=20） | 非供应商题（n=10）        | 类3 误触    |
| ------------------ | ------------ | ------------------ | -------- |
| 原版（只要求简洁）          | 10/20        | 无污染，52 字           | 0/10     |
| 抽象「多条结论必须全部列出」     | 14/20        | —                  | —        |
| 点名供应商维度，**不加条件**   | 20/20        | **有污染**（硬塞「要求动作」等） | 1/10     |
| **点名维度 + 条件化（现行）** | **20/20**    | **无污染，51 字**       | **0/10** |

### 7.4 三条都是踩出来的

1. **不要用否定式。** 试过「资料里没有的维度不要提、不要写'未提及'」——

   只提"缺失"这个概念，模型反而更爱吐 `资料不足`，覆盖度崩到 **2/20**。肯定式「已有的用一句话带出」才行。
2. **必须条件化。** 不加条件时，「记录写错怎么改」这类**与供应商无关**的题也会被跑一遍供应商维度清单，

   末尾硬加「资料**未提及**任何不良率…故无法评估」。这句既冗余，又**撞上类3 拒答词表里的 `未提及`**

   → 正常答案被判成拒答。**66 题验收当场抓出两例**（L02 长文档题、T06 表格题），

   改成条件化后**库内误拒回到 0/60**。
3. **改提示词必须跑全量验收。** `/health` 看不出提示词变了，只有 66 题验收能证明「没伤其它口径」：

   改后复测 **库外 6/6 ✅ · 库内误拒 0/60 ✅ · 编造 0/37 ✅ · 引用问题 0/66 ✅**。
4. **✅ 简洁度这个轴已于 2026-10-10 补上（第五版提示词）—— 结论：覆盖度与简洁度**有权&#x8861;**，本轮把票投给精准度。**

   用户体感「答案偏长、覆盖面超出所问」→ 第 3 条从「无条件逐个核对全部维度」改为**分级展开**：

   问单一指标只答那一项；问整体情况才**点名式逐项**展开（质量 → 交付 → 评级 → 动作）。

   实测对照（同题同检索）：「东莞精诚的不良率」**61 → 30 字**，不再附带没问的不合格批数；

   「宁波恒力的情况」（问整体）保持全维度 **5/5**（均长 128 字）。

   🔴 **泛写"逐项"不够**：不点名维度时模型实测质量维度 **0/5** —— 点名式列举（旧版拿 20/20 的同一手法）才有效。

   🔴 **当场抓到一次真回归**：只收紧第 1 条时库外拒答 O03b 从 10/10 掉到 **0/5** ——

   模型把「该文档不在库中」的声明当冗余剪掉。修法 = 警示模板加粗「必须声明缺失」
   - `库外拒答词` 第三组词（"不在本知识库"等，**仅类2 信号时启用**）。

   ↔ `警示 + 尾注`（仅**有**库外信号时注入 → 管库外）。

**验证**：实验 17/17 全对（O03b 8/8 + 库内 6/6 + O03 3/3）→ 落码 → 三条验收全绿：

| 验收                        | 结果                                                                          |
| ------------------------- | --------------------------------------------------------------------------- |
| `自检-全链路.py --全量`（229.8 s） | ✅ 13 通过 / 0 失败 / 1 跳过：**库内误拒 0/60**、库外漏网 0/6、引用问题 0/66、编造 0/11、重排 0.000e+00 |
| `探测-问答页.py 8092`          | ✅ 34 项全绿                                                                    |
| `诊断-库外拒答率.py 8`           | ✅ **O03 8/8 ｜ O03b 8/8 ｜ O06 8/8**（O03b 从第六版的 1/8 完全恢复）                     |

> **可复用结论**
>
> 1. **「稳定复现」≠「能力边界」** —— 判一个失败是能力问题还是回归，**必须做版本对照实验**。
> 2. **同一根绳的两端要靠「条件化」解，不能靠「删语义」解**：把无条件语义搬进
>
>    **靶向位置**（有/无库外信号互斥），两边才能同时满足。
> 3. **小模型对提示「末尾」更敏感**（近因）：同一条规则放【问题】之后再说一遍，比只放开头有效。
> 4. **验证集必须包含已知最脆弱的样本**：这轮一次实验只测 O03 不测 O03b，就误判成「两全」。
