## 摘要：第一条真正有增益的检索路径

RRF 调参（F1~F4）被证伪之后，**cross-encoder 重排是目前唯一拿到增益的路径**。
做法：BM25 召回 Top-50 → bge-reranker-v2-m3 逐对打分 → 重排。

| 指标 | B 纯 BM25（原最优） | **RB50 = 重排×BM25Top50** | 变化 |
|---|---|---|---|
| R@1 | 0.8333 | **0.8500** | +1 题 |
| R@3 | 0.9333 | **0.9833** | **+3 题** |
| R@5 | 0.9500 | **0.9833** | **+2 题** |
| MRR | 0.8855 | **0.9115** | +0.026 |

**R@3 / R@5 的跃升才是重点** —— RAG 是把 Top-3/Top-5 喂给生成端的，
而 0.9833 意味着 **60 题里只有 1 题的正确块不在 Top-3**。

> **⚠ 证据强度的诚实说明**：把 RB50 与 B 做**精确排名**配对，是 **8 胜 / 4 负**，
> 双侧符号检验 **p = 0.388（不显著）**。但换成 **Top-3 成员**配对就是 **3 胜 / 0 负（单边）**，
> 且 R@1/R@3/R@5/MRR **四项同向**、机制明确。
> 结论：**值得采用，但要把"证据强度中等"写在脸上** ——
> 1 题 = 1.67pp 的分辨率下，60 题样本本就撑不起强显著性。

## 一、实验设置

| 项 | 值 |
|---|---|
| 基座分块 | S13 软表保-1200（290 块），与五通道/分块实验**同一基座** |
| 评测集 | 66 题（60 库内 + 6 库外）；**1 题 = 1.67pp** |
| 重排模型 | bge-reranker-v2-m3-**Q8_0**（606 MiB） |
| 重排服务 | `llama-server --reranking`，**CPU**（8085），`-b 2048 -ub 2048 -t 24` **`--parallel 1`** |
| 向量服务 | bge-m3-Q8_0，**单槽 8082**（见 §五.3，本轮改的） |
| 规模 / 耗时 | 66 × 290 = **19,140 对**，290.5 s，**15 ms/对** |

### 核心设计：一次重排全库，离线派生所有方案

重排打分是**逐 (问句, 块) 对独立**的，所以

    先给全库 290 块打分、再取某通道 Top-N 按分数重排
    ≡
    只把那个 Top-N 送去打分

（子集内的相对顺序不变。）因此只跑一遍重排，就能派生任意池深、任意基线通道的方案。

**这不只是省时间，更是判据要求**：各方案的重排分必须来自**同一次打分**，
否则「方案甲比乙好」里会混进「两次打分的批次差异」这个额外变量。

### 方案的构造（池外不丢块）

```
序 = 池内按重排分降序  +  池外按原序接在后面
```

**池外必须接上**，否则「正确块不可召回」与「被池截断」表现相同 —— 又是「没有判据」。

### 护栏（全部通过）

| 护栏 | 结果 |
|---|---|
| A/B/C 三通道与 `混合检索-结果.json` **逐题一致** | ✅ 66/66 × 3 |
| 金标准逐字存在 | ✅ |
| 证据组在语料中确实存在 | ✅ |
| **护栏放在重排之前** | 基座漂移 15 秒内暴露，不用跑满 5 分钟才知道作废 |

## 三、五条发现

### 1. 重排的机制：**修好 BM25 的长文档短板**，而不是"整体提升"

逐题看得失（RB50 vs B）：

| 方向 | 题 | 类别 | B → RB50 |
|---|---|---|---|
| **收益** | **L02** | 长文档 | **21 → 1** |
| | L06 | 长文档 | 3 → 1 |
| | L11 | 长文档 | 2 → 1 |
| | T06 | 表格 | 7 → 2 |
| | K05 | 短小关键 | 4 → 2 |
| | K07 / T10 | 短小关键 / 表格 | 2 → 1 |
| | P01 | 跨文档 | 41 → 40 |
| **损失** | T07 | 表格 | 1 → 2 |
| | K02 | 短小关键 | 1 → 3 |
| | P04 / P05 | 跨文档 | 1 → 2 |

**8 题改善、4 题变差**。收益集中在**长文档**（3 题进 Top-1），
且 **L02 从第 21 名直接救到第 1 名** —— 这是 BM25 或向量单路都做不到的
（L02 向量排 1、BM25 排 21，正是报告 §八.3 那对"等权 RRF 互相拖累"的镜像题之一）。

### 2. 池深：**10 / 20 不够，50 到顶**

| 池深 | R@1 | R@3 | 说明 |
|---|---|---|---|
| 10 | 0.8333 | 0.9667 | 太浅：L02（B 第 21 名）根本不在池里 |
| 20 | 0.8333 | 0.9667 | 同上 |
| **50** | **0.8500** | **0.9833** | ✅ 与"全库重排"同分 |
| 全库 | 0.8500 | 0.9833 | 天花板 |

**关键**：L02 在 BM25 里排第 21 名 —— **池深必须 ≥ 21 才可能救它**。
选 10/20 的方案不是"重排不行"，而是"池太浅"。

### 3. 🔴 「跨文档退步」是误读：只是 2 题从第 1 掉到第 2

跨文档类 R@1 从 B 的 **0.86 掉到 0.57**，看上去是重排的严重代价。查现场：

| 题 | A | B | RB50 | RA20 |
|---|---|---|---|---|
| P01 | 21 | 41 | 40 | 21 |
| P02 | 1 | **1** | **1** | **1** |
| P03 | 2 | **1** | **1** | **1** |
| P04 | 6 | **1** | 2 | 2 |
| P05 | 12 | **1** | 2 | 2 |
| P06 | 1 | **1** | **1** | **1** |
| P07 | 4 | **1** | **1** | **1** |

**7 题里 5 题仍是第 1；掉的 2 题只是 1 → 2。** B 的 0.86 是 6/7，重排后 4/7，差 2 题。

而更值得注意的是 **P01 的「同块齐备」排名**（语义等价判据，见混合检索报告 §三.5）：

| 通道 | A | B | C | RA10/20 | RB10~50 | RG |
|---|---|---|---|---|---|---|
| 同块齐备排名 | 3 | 2 | 3 | **1** | **1** | **1** |

**重排把 P01 的"真实可答块"顶到了第 1 名** —— 严格判据（连续串）下它仍显示 21/40，
但这正是我们在五通道报告里已经判定为**评测集缺陷**的那个判据。

> **教训**：一个指标掉 29pp，未必是"严重退步"，可能只是 **2 题在 Top-1/Top-2 之间挪了一下**。
> **必须下钻到逐题**，否则会把"抖动"读成"结论"。

### 4. 🔴 拒答阈值：单一全局阈值**做不到**（量化了）

重排分是**原始 logit**（非 sigmoid），可以当拒答判据用。每题取全库最高分：

```
库内题最高重排分（降序）：6.87  6.40  5.50  5.47  5.46  5.41  5.32  …  最低 -2.37
库外题最高重排分        ：O03=2.65  O06=0.18  O01=-4.39  O05=-5.37  O02=-6.02  O04=-8.95
```

| 阈值 | 库内接答 | 库内误拒 | 库外误答 |
|---|---|---|---|
| 0.0 | 58/60 | 2/60 | **2/6** |
| 0.5 | 58/60 | 2/60 | 1/6 |
| 1.0 | 57/60 | 3/60 | 1/6 |
| 1.5 | 54/60 | 6/60 | 1/6 |
| 2.0 | 53/60 | 7/60 | 1/6 |
| 2.5 | 47/60 | 13/60 | 1/6 |
| 3.0 | 40/60 | **20/60** | 0/6 ✅ |
| 3.5 | 34/60 | 26/60 | 0/6 ✅ |

**两段区间重叠**：库外 O03 = 2.65、O06 = 0.18 落在**库内分数区间内部**；
而要拦住全部库外题（阈值 3.0），代价是**误拒 20/60 = 33% 的库内题**。

- **O03 正是那个已知的"有线索但答案在库外"的题**（语料里 QW-DD-03 确实在讲废液收集，
  只是处置流程指向库外的 QW-DD-05）—— 它的最高分比多数库内题还高，**分数本身没错**。
- → **拒答必须分两类**（这与五通道报告的预判一致，现在有了量化依据）：
  1. **完全没线索** → 阈值可拦（O01/O02/O04/O05 全部 ≤ −4.39，远低于库内最低 −2.37）；
  2. **有线索但指向库外** → 阈值拦不住，**必须靠"线索链是否闭合"**（如引用到的文档号在不在库里）
     这类**结构化判据**，不能靠分数。

> **✅ 2026-10-09 后续（D4 落地时修正）**：这两类之外**还需要第三层「生成端」兜底** ——
> O06（最高分 0.18、Top-1 无库外号）两类都拦不住，靠提示词约束才拦住。
> 且第 2 类落地时做的不是"硬拒答"而是"**软警示**"（把库外文档号透给生成端），
> 实测库内误拒 1/60 → **0/60** 且拒答质量更高。
> 完整三层与端到端数据 → `eval/知识库服务-报告.md`。

### 5. 与 RRF 融合的正面对比：**重排赢**

| 做法 | R@1 | R@3 | MRR | 长文档 R@1 |
|---|---|---|---|---|
| C 等权 RRF | 0.8000 | 0.9333 | 0.8628 | 0.80 |
| F1~F4（RRF 调参） | ≤0.8000 | ≤0.9333 | ≤0.8656 | ≤0.80 |
| **RB50 重排** | **0.8500** | **0.9833** | **0.9115** | **0.93** |

RRF 调参四轮全部**没能超过单通道 B**（0.8333）；重排**四项指标全高**，
且修好了 RRF 一直没治好的长文档亏损。**"在融合权重上继续调"这条路的性价比已被证伪。**

## 五、工程坑（本轮踩的，都值得记）

### 1. 🔴 `--reranking` 的物理批是**硬上限**，超了会让**整批** 500

第一次跑，第一批就 `HTTP 500`。日志里写着：

```
E srv send_error: input (529 tokens) is too large to process.
        increase the physical batch size (current batch size: 512)
```

而启动日志里早有伏笔：

```
W srv llama_server: embeddings enabled with n_batch (2048) > n_ubatch (512)
W srv llama_server: setting n_batch = n_ubatch = 512 to avoid assertion failure
```

**本语料最长块 1188 字**（33 块 > 500 字）→ 必然撞墙。

- 修复：`--batch-size 2048 --ubatch-size 2048`。
- **并给客户端加了二分降级**：一批失败就把这一批对半拆开重试，真剩单块才报硬失败。
  **长尾块不该让整批陪葬。**
- 顺带：返回的 `results` 是**按分数降序**的，必须用 `index` **回填到原位置** ——
  想当然按返回顺序对齐会张冠李戴，**而且不报错**。

### 2. 护栏必须放在最贵的步骤**之前**

第一版把「A/B/C 与旧结果逐题一致」的护栏放在重排**之后** ——
结果基座一有漂移，5 分钟算力白烧。改成 15 秒的 `--仅护栏` 前置校验。

### 3. 🔴 向量服务是多槽并行 + LCP 槽位复用 → **同一段文本两次可能不一样**

护栏报「只有 P01 差 1 题」时，我没有把容差放宽了事，而是去查现场。结论：

| 观测 | 8081（默认多槽） | 8082（`--parallel 1`） |
|---|---|---|
| 同进程、同批、连打两次 | **2.282e-03**（且**时有时无**） | **0.000e+00** |
| 两个独立进程的指纹 | **不一致** | **完全一致** |
| 批量 vs 逐条请求 | 6/8 不一致 | **8/8 一致** |

机制：服务日志里明写着 `selected slot by LCP similarity` —— **多槽按最长公共前缀复用 KV**，
请求到来时若另一槽还在算，就落到不同槽 → 复用不同前缀 → CLS 池化输出差在 1e-3 量级。
**"连打两次有时同有时不同" = 竞态。**

后果：**近似并列处的名次会在会话之间漂移**（P01 的 21/22；
报告 §五.4 记的 T10 分差 0.00016 也是同一回事）。

处置：**默认向量服务切到 8082（单槽）**，并把整条检索链路的基线全部重建。
复现实验：`scripts/诊断-向量可复现性.py 8081` vs `... 8082`。

> **通用教训**：**"差 1 题"不要习惯性当成噪声放过去。**
> 放宽容差是"让判据闭嘴"，查清机制才是"让判据有意义"。
> 这一次查下去，挖出的是**一个污染了整个评测的未受控变量**。

### 4. bash 变量名不能用中文（第 N 次）

下载 reranker 时写了 `for 名 in ...` → `not a valid identifier`，
**863 毫秒就退出、一个字节没下**，而日志看着"跑完了"。
**shell 里变量名与函数名一律 ASCII（Python 里才可以用中文）。**
